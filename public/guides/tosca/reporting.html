BEGINNER1. What Happens During a Run

Definition

When an Execution List runs, Tosca records every step's outcome in real time — not just a final pass/fail per Test Case, but a full audit trail down to the individual Test Step level: the value sent, the value actually found, and the verdict.

Real-world analogy: Tosca's reporting is like a flight data recorder (black box). Every action taken during the flight (test run) is captured in chronological order. When something goes wrong, you replay the recording — you see exactly what was done, what was expected, and what actually happened, right down to the millisecond.

All of this is stored in the central repository database, not in scattered local log files, so any team member with TCM access can review any historical run.

BEGINNER2. Result States Explained

// Result states
Passed           ✓  all steps succeeded
Failed           ✗  a Verify/Checkpoint step mismatch
Error            !  unexpected exception (element not found, timeout)
Skipped          –  step skipped by Condition or steering
NotExecuted      ○  not yet run in this execution
State What It Tells You
Passed Every assertion in the Test Case held true — the feature behaved as expected
Failed A Verify step's expected value did not match the actual — investigate as a potential functional defect
Error Something prevented the step from even completing — usually an automation/environment issue, not necessarily a product bug
Skipped A Condition (steering) or manual exclusion prevented this entry from running at all
NotExecuted Placeholder state before any run has touched this entry

BEGINNER3. Step-Level Execution Logs

The most valuable diagnostic artifact Tosca produces is the per-step log — it shows exactly which step in a multi-step Test Case broke, and what the expected-vs-actual mismatch was.

TestCase: TC001_Login  → FAILED
  Step 1: Navigate URL       → Passed   | Got: 200 OK
  Step 2: Enter Username     → Passed   | Typed: alice@test.com
  Step 3: Enter Password     → Passed   | Typed: ****
  Step 4: Click Login        → Passed   | Button clicked
  Step 5: Verify Welcome     → FAILED
    Expected: "Welcome, Alice"
    Actual:   "Account locked. Contact admin."
    Screenshot: step5_fail_2024-11-01_14-23-11.png
💡 Tip: Reading the step log from top to bottom pinpoints the exact failure boundary — everything before it worked correctly, so investigation time should focus on the failing step and what changed around it, not the whole scenario.

INTERMEDIATE4. Screenshots and Evidence Capture

Tosca can automatically capture screenshots (and, depending on configuration, short video) at the moment a step fails, or on every step if configured for maximum evidence. These are attached directly to the step's log entry.

Capture Mode Trade-off
On failure only Minimal storage overhead; sufficient for most regression suites
Always (every step) Rich audit trail useful for compliance-heavy industries, but significant storage growth over time
⚠️ Common Pitfall: Enabling "always capture" screenshots across a large nightly suite without a retention/cleanup policy can silently balloon the repository database size over months, degrading TCM performance. Set a retention window or archive older execution results periodically.

INTERMEDIATE6. JUnit XML for CI Pipelines

When Tosca is triggered from a build server via ToscaCI, results are also written as a JUnit-compatible XML file — a format essentially every CI tool (Jenkins, Azure DevOps, GitHub Actions) already knows how to parse and render natively in its own test-results UI.

// Tosca CI — results directory
ToscaCI.exe run ... --resultdir "C:\\CI\\Results"
// Produces: ExecutionResults.xml  (JUnit-compatible)


  
  
    
      Expected: Welcome, Alice | Actual: Account locked
Why JUnit XML matters: it lets Tosca slot into a pipeline exactly like any developer unit-test framework — no custom parsing plugin needed, and build servers can show pass/fail trends over time in their standard dashboards.

ADVANCED7. Defect Tracker Integration

Tosca integrates natively with defect trackers such as Jira, Azure DevOps, and ServiceNow. Failed Test Cases can automatically create a defect ticket carrying the step-level failure detail, screenshots, and environment metadata — closing the loop between "test failed" and "someone is tracking the fix."

Auto-Created Defect Contents Source
Failure summary and expected/actual values Step log
Screenshot at time of failure Evidence capture
Environment/agent used Execution List configuration
Linked requirement Requirements traceability matrix
💡 Tip: Auto-created defects are most valuable when paired with de-duplication logic (or a human triage step) — otherwise a flaky test that fails every night can spam the tracker with dozens of near-identical tickets.

ADVANCED8. Using TQL to Query Results

Tosca Query Language (TQL) can be used against execution history, not just against Modules and Test Cases — letting you answer questions like "which Test Cases have failed in the last 5 runs" or "which requirements currently have failing coverage" directly, without manually clicking through the Execution tree.

// Conceptual TQL query against execution history
SELECT TestCase.Name, Result.State, Result.ExecutionDate
FROM ExecutionResults
WHERE Result.State = "Failed"
  AND Result.ExecutionDate >= LAST_7_DAYS
ORDER BY Result.ExecutionDate DESC
When this earns its keep: on suites with hundreds of Test Cases, manually browsing execution history to spot a flaky test pattern is impractical. A saved TQL query can surface "Test Cases failing intermittently over the last 2 weeks" as a standing health-check.

INTERMEDIATE9. Common Pitfalls

  • Treating every non-Passed result the same: conflating Error (automation/environment issue) with Failed (genuine assertion mismatch) skews triage priorities.
  • No screenshot retention policy: unlimited evidence capture growing the repository unchecked over months.
  • Auto-creating duplicate defects: flaky tests spamming the tracker with near-identical tickets night after night.
  • Ignoring stakeholder reporting: relying solely on TCM's technical views when non-technical stakeholders actually need the HTML/PDF summary report.

BEGINNER10. Best Practices

1. Read Failures Before Errors

Prioritise triaging genuine Failed assertions (likely real defects) before chasing Error entries (often flaky automation/environment issues) unless Errors dominate the run.

2. Capture Screenshots on Failure by Default

Reserve "always capture" for specific compliance-driven suites; use failure-only capture as the default to control storage growth.

3. Wire JUnit XML into Every CI Pipeline

ToscaCI.exe run --executionList "Smoke" --resultdir ".\results"
// Then in CI:
junit '.\results\ExecutionResults.xml'

4. Distribute the Right Report to the Right Audience

Engineers get TCM drill-down; stakeholders get the HTML/PDF report; CI gets JUnit XML.

5. De-Duplicate Auto-Created Defects

Add a triage step or de-duplication rule before defect auto-creation goes fully unattended in production pipelines.
