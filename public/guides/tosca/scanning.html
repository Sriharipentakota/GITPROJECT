BEGINNER1. What Is TBox?

Definition

The TBox is Tosca's recognition engine — the component that knows how to "see" and interact with a specific technology's control tree. There isn't one universal TBox; there's a family of TBox engines, each specialised for a UI technology (web browsers, WinForms, SAP GUI, Java Swing, mobile, PDF, and more).

Real-world analogy: Think of TBox engines like different pairs of glasses. TBox Web lets Tosca "see" HTML DOM elements clearly. TBox SAP lets it "see" SAP GUI screen fields. Put on the wrong pair of glasses and the same physical pixels look like meaningless shapes — Tosca needs the matching TBox to correctly identify controls in that technology.

What Scanning Actually Produces

When you scan an application, TBox inspects its live control tree and produces a Module — a persisted, structured record of each control's type, hierarchy path, and identifying technical properties. The Module is stored in the repository as a first-class asset, independent of whether the application is currently running.

BEGINNER2. The Scanning Workflow

Scanning is an interactive process performed once per screen (or reused/updated as the screen evolves):

1. Open TCM → Modules section → right-click → Scan Application
2. Choose TBox engine (Web, WinForms, SAP…)
3. Hover control → green highlight → click to add to module
4. Rename Module Attribute with a business-friendly name
5. Set ActionMode: Input / Output / Verify / Wait / Count

Walkthrough: Scanning a Login Page

Step by step: 
1. Launch the application under test (e.g. open the login page in Chrome)
2. In TCM, right-click the Modules folder → Scan Application
3. TCM shows a translucent overlay; hover the username field → it highlights green
4. Click it → TBox records: control type = TextBox, XPath/selector, hierarchy
5. Repeat for the password field and the Login button
6. Stop scanning → TCM creates Module "LoginPage" with 3 attributes
7. Rename attributes: txtUser → Username, txtPass → Password, btnGo → LoginButton

Resulting Module Structure

Module: LoginPage
├── Attribute: Username
│     TechnicalParam: Value
│     ActionMode: Input
│     BusinessParam: Username
├── Attribute: Password
│     TechnicalParam: Value
│     ActionMode: Input
│     BusinessParam: Password
└── Attribute: LoginButton
      TechnicalParam: (none needed)
      ActionMode: Input  ← click action
💡 Tip: You don't need to scan every control on a screen up front. Scan what your first test cases need; come back and extend the Module later as new test cases require new attributes. Modules grow incrementally with the test suite.

BEGINNER3. Anatomy of a Module

A Module is a tree of Module Attributes, each attribute corresponding to one recognised control. Each attribute carries several pieces of metadata:

Property Meaning Example
Technical Parameter Engine-level property read/written on the control Value, Checked, SelectedItem, Text
Business Parameter Human-readable name mapped to the technical parameter Username, OrderQty
ActionMode What the engine does with the value at execution time Input, Output, Verify, Wait, Count
Identification properties The selector data used to relocate the control at runtime XPath, ID, Name, control index

Business Parameter Mapping

// Technical Parameter (TBox-defined, maps to control property)
Module: UsernameField
  TechnicalParameter: Value   ← what you type into the field

// Business Parameter (created by tester, maps to technical param)
Module: UsernameField
  BusinessParameter: Username → maps to → Value

// Test Step uses business parameter
Step: Enter credentials
  Username = "alice@test.com"

INTERMEDIATE4. ActionModes: Input, Output, Verify, Wait, Count

The ActionMode set on a Module Attribute determines what happens to that attribute when a Test Step using it executes. This is the single most important setting to understand when scanning, because it decides whether a step performs an action, reads a value, or makes an assertion.

ActionMode Behaviour Typical Use
Input Writes the supplied value into the control (type text, click, select) Filling a text box, clicking a button, choosing a dropdown item
Output Reads the control's current value and stores it into a Buffer Capturing a generated order ID, a confirmation number
Verify Reads the control's value and asserts it equals the expected value; fails the step on mismatch Checking a welcome message, a validation error, a total price
Wait Pauses execution until the control reaches a specified condition or state Waiting for a spinner to disappear, an element to become visible
Count Counts the number of matching controls Verifying a search returns exactly 5 results 
ActionMode:
  Input   → write value into control
  Output  → read value from control into Buffer
  Verify  → assert control value equals expected
  Wait    → pause until control meets condition
  Count   → count matching controls
⚠️ Common Pitfall: The same Module Attribute can be reused with different ActionModes in different test steps. Forgetting to switch ActionMode from Input to Verify on a step that is meant to be an assertion is one of the most common causes of a test case that "passes" without ever actually checking anything.

INTERMEDIATE5. Classic Modules vs Checkpoint Attributes

Tosca practitioners often distinguish between attributes used to drive the application (Classic, ActionMode = Input) and attributes used to assert against it (Checkpoint, ActionMode = Verify). Both live in the same Module — the distinction is about intent and usage, not a different asset type.

Classic Module Attribute (ActionMode = Input):
  → performs an action (type, click, select)

Checkpoint Attribute (ActionMode = Verify):
  → asserts the control's current value
  → test step fails if actual ≠ expected

// Usage in test step
Step: Verify welcome message
  WelcomeLabel [Verify] = "Welcome, Alice"
  ↓ TOSCA checks the DOM text matches "Welcome, Alice"
Classic (Input) usage: 
Module: LoginPage
Step: LoginPage.Username [Input]
  Value = "alice@test.com"
→ Types text into the field
Checkpoint (Verify) usage: 
Module: Dashboard
Step: Dashboard.WelcomeLabel [Verify]
  Value = "Welcome, Alice"
→ Fails step if text doesn't match

INTERMEDIATE6. Common TBox Engines

Tosca ships dozens of TBox engines. Knowing which one matches your application under test is a prerequisite to a successful scan.

TBox Engine Technology Covered
TBox Web HTML/DOM in Chrome, Edge, Firefox
TBox WinForms / WPF Windows desktop applications
TBox SAP SAP GUI screens and transactions
TBox Java Java Swing / SWT desktop applications
TBox Mobile Native iOS (XCUITest) and Android (UIAutomator2) apps
TBox PDF PDF document content and form fields
TBox Mainframe Terminal-emulated 3270/5250 screens
💡 Tip: A single Test Case can chain steps from multiple TBox engines — for example, submit a form in TBox Web, then verify the resulting record in TBox SAP. This cross-technology reach is one of Tosca's biggest differentiators against single-technology frameworks.

ADVANCED7. XScan and Anchoring Strategies

Not every control has a stable, unique identifier (e.g. dynamically generated IDs in some web frameworks). Tosca's engines resolve this using a combination of identification properties and, where necessary, anchoring — identifying a control relative to a nearby, more stable sibling or parent element.

// Example: a row of "Delete" buttons with no unique IDs, one per grid row
// Anchor strategy: locate by the sibling "Order Number" cell text, then
// navigate relative to it to find that row's Delete button

Module Attribute: DeleteButton
  Anchor: nearest preceding cell with text = {P:OrderNumber}
  Relative path: ../following-sibling::td[last()]/button
When to anchor: repeating grid rows, dynamically generated element IDs, list items without stable attributes. Anchoring trades a small amount of setup complexity for a Module Attribute that keeps working even as row order or generated IDs shift between runs.

XScan for Bulk/Automated Scanning

For applications with many repetitive screens, Tosca's XScan feature can scan structurally similar screens in bulk (for example, every SAP transaction screen sharing a template), dramatically speeding up initial Module creation on large legacy estates.

ADVANCED8. Module Folders, Inheritance & Reuse

Modules are organised in folders that typically mirror the application's screen/page structure. Common patterns for larger projects:

Modules/
├── Common/
│   ├── NavigationMenu
│   └── HeaderBar
├── Login/
│   └── LoginPage
├── Orders/
│   ├── OrderListPage
│   └── OrderDetailPage
└── Admin/
    └── UserManagementPage

Shared elements that appear on many screens (a header, a navigation bar, a cookie banner) should be scanned once into a "Common" Module and referenced by every Test Case that needs them, rather than being re-scanned per page.

⚠️ Common Pitfall: Re-scanning the same shared control (e.g. a global search bar) into multiple different Modules creates duplicate attributes that all need to be fixed independently when the control changes — exactly the maintenance problem Tosca's model is meant to eliminate. Always check whether a shared Module already exists before scanning a new one.

INTERMEDIATE9. Common Pitfalls When Scanning

  • Scanning too much, too early: capturing every control on a screen before you know which ones your test cases actually need bloats the Module and makes it harder to navigate.
  • Leaving default technical names: attributes named TextBox1, Button2 instead of Username, LoginButton destroy the business-readability benefit of the model.
  • Wrong ActionMode by default: newly scanned attributes often default to Input — remember to switch to Verify/Output where the test step's intent is to assert or capture, not act.
  • Ignoring dynamic content: scanning a control whose identifying property changes on every page load (e.g. a session-specific ID) without anchoring produces a Module Attribute that only works once.

BEGINNER10. Best Practices

1. Rename Every Attribute Immediately

Never leave scan-generated technical names in place. Rename to the business term a tester or stakeholder would use.

2. Set ActionMode Deliberately

Decide, for each attribute, whether it will primarily be used to act, capture, or assert — and set a sensible default ActionMode accordingly.

3. Group Shared Controls into Common Modules

Headers, navigation, and cross-cutting widgets belong in a shared Module, scanned once.

4. Use Anchoring for Repeating Elements

Don't fight dynamic IDs with hard-coded selectors — use relative/anchored identification instead.

5. Revisit and Extend Modules Over Time

// Good ongoing practice:
Sprint 1: Scan LoginPage with 3 attributes needed for TC001
Sprint 3: Extend LoginPage with "Remember Me" checkbox for TC015
Sprint 5: Extend LoginPage with "Forgot Password" link for TC022
// Module evolves incrementally alongside real test needs
