BEGINNER1. Test Suites vs Execution Lists

Two Different Groupings, Two Different Purposes

Tosca deliberately separates organising test cases from running them. A Test Suite is a logical grouping of Test Cases used for organisation and reporting; it lives in the TestCases section and can be linked to Requirements for traceability. An Execution List is the ordered queue of Test Cases that Tosca actually executes in one run; it lives under the Execution section.

Aspect Test Suite Execution List
Location in TCM TestCases section Execution section
Primary purpose Organisation, requirement traceability, reporting scope Actual execution — the ordered run queue
Can be run directly? Not on its own Yes — right-click → Run
Contains setup/teardown? No Yes — via Test Events
Real-world analogy: A Test Suite is like a playlist you curate on a music app — a labeled grouping for browsing. An Execution List is like pressing "Play" — an actual ordered performance, with a defined start, defined stops between tracks (Test Events), and a recorded listening history (results).

BEGINNER2. Anatomy of an Execution List

ExecutionList: Regression_Sprint12
├── [Test Event: Setup]  ← runs before every TC
│   └── TC_ClearTestData
├── TC001_Login
├── TC020_PlaceOrder
├── TC021_CancelOrder
├── [Test Event: Teardown]  ← runs after every TC
│   └── TC_Logout
└── ExecutionCondition: OnError=Continue

Each item in the list — a Test Case, a folder of Test Cases, or a Test Event — becomes an ExecutionEntry when the list runs. Every entry gets its own result state, log, and (optionally) screenshots.

BEGINNER3. Building Your First Execution List

Step by step in TCM: 
1. Right-click the Execution folder → New ExecutionList → name it "DailySmoke"
2. Drag Test Cases (or entire folders) from TestCases into the list
3. Reorder entries by drag-and-drop if sequence matters
4. Set properties: agent, browser/device config, error handling
5. Right-click the ExecutionList → Run
6. Review results under Execution → [list name] → Results

Running from the Command Line

// Running an Execution List
- Right-click ExecutionList → Run
- Or: Tosca CI command line
  ToscaCI run --executionList "Regression_Sprint12"

INTERMEDIATE4. Test Events: Setup and Teardown

Test Events are special entries that wrap every Test Case in the list with common setup/teardown logic, so you don't need to embed the same login/logout or environment-reset steps into every Test Case individually.

ExecutionList: DailySmoke
  Test Event (Before each): TC_OpenBrowser
  Test Event (After each):  TC_CloseBrowser

  Entry 1: TC001_Login
  Entry 2: TC002_Search
  Entry 3: TC003_Checkout

// Execution Order:
// TC_OpenBrowser → TC001_Login → TC_CloseBrowser
// TC_OpenBrowser → TC002_Search → TC_CloseBrowser
// TC_OpenBrowser → TC003_Checkout → TC_CloseBrowser
Test Event Type Runs Typical Use
Before each Before every Test Case in the list Open browser, reset test data, log in
After each After every Test Case in the list Log out, close browser, clean up created records
Before/after list Once, at the start/end of the whole run One-time environment provisioning or teardown
💡 Tip: Test Events keep individual Test Cases focused purely on the business scenario they verify, while the Execution List owns cross-cutting run mechanics like environment prep.

INTERMEDIATE5. Result States

After a run, every ExecutionEntry is assigned one of a fixed set of result states, visible in the Execution → Results view:

// Result states
Passed   ✓  all steps succeeded
Failed   ✗  at least one step failed
Error    !  unexpected exception
Skipped  –  marked to skip or condition not met
State Meaning Typical Cause
Passed Every step, including all Verify assertions, succeeded Expected outcome
Failed A Verify/Checkpoint step's actual value didn't match expected Genuine functional defect, or stale expected value
Error An unexpected exception occurred (element not found, timeout, connection lost) Environment issue, broken selector, unrecovered popup
Skipped The entry was deliberately excluded or a Condition prevented execution Steering condition evaluated false; manually marked to skip

INTERMEDIATE6. Partial Runs and Re-Running Failures

// Select specific entries to run
Right-click entry → Mark for execution → Run Marked

// Re-run only failed entries
After full run → Filter by Status = Failed
Right-click failed entries → Re-run
When this matters: a 300-test-case nightly regression that has 4 failures shouldn't require a full 2-hour re-run to confirm a fix. Marking and re-running just the 4 failed entries turns verification into a 2-minute check.

ADVANCED7. ExecutionEntries and Ordering

Internally, every item dragged into an Execution List becomes an ExecutionEntry — a lightweight reference back to the underlying Test Case, plus run-specific metadata (order position, agent assignment, last result). This indirection is what allows the same Test Case to appear in multiple Execution Lists (e.g. both "Smoke" and "Full Regression") without duplicating its steps.

TestCase: TC001_Login (single definition)
  ├── Referenced by ExecutionEntry in "DailySmoke"
  ├── Referenced by ExecutionEntry in "Full_Regression"
  └── Referenced by ExecutionEntry in "PreRelease_Gate"

// Editing TC001_Login's steps updates behaviour
// in all three Execution Lists simultaneously

Ordering matters when later entries assume state left behind by earlier ones (e.g. a "Create User" entry must run before an "Edit User" entry that expects that user to exist). Where entries must be order-independent, design each Test Case to set up and tear down its own state.

ADVANCED8. Error Handling and Execution Conditions

Execution Lists expose configuration for how the run should behave when an entry fails, and which agent/environment to target:

Setting Options Effect
ExecutionCondition (OnError) Continue / Stop Whether remaining entries still run after a failure
ExecutionMode Local / Distributed (DEX) Run on this machine, or dispatch across agent pool
Retry count 0–N Automatically re-attempt a failed entry before marking it Failed
⚠️ Common Pitfall: Setting OnError=Stop on a large nightly regression means one early failure prevents hundreds of unrelated, healthy Test Cases from ever running — hiding real information about the state of the build. Most CI regression lists should use Continue, reserving Stop for critical smoke gates where there is no value in continuing past a broken build.

INTERMEDIATE9. Common Pitfalls

  • Confusing Test Suites with Execution Lists: trying to "run" a Test Suite directly — Test Suites organise, Execution Lists execute.
  • No Test Events, duplicated setup: embedding login/logout steps in every Test Case instead of using Before/After Test Events on the Execution List.
  • Order-dependent entries without documentation: a later entry silently depends on data created by an earlier one, breaking as soon as someone reorders or partially re-runs the list.
  • Ignoring Error vs Failed distinction: treating every non-Passed result as "the feature is broken" when many Error results are actually environment or automation issues, not product defects.

BEGINNER10. Best Practices

1. Use Test Events for Cross-Cutting Setup

Keep environment prep and teardown out of individual Test Cases; centralise it in Before/After Test Events.

2. Separate Smoke from Full Regression Lists

ExecutionList: Smoke_Gate       (5 min, blocks bad deploys)
ExecutionList: Full_Regression (2 hrs, runs nightly)

3. Choose OnError Deliberately

Use Stop only for gates where continuing has no value; use Continue for broad regression runs so you get complete information.

4. Re-Run Failures, Not Everything

After investigating a failure and applying a fix, re-run just the failed entries to confirm before triggering a full re-run.

5. Design Test Cases to Be Order-Independent Where Possible

Minimise hidden dependencies between entries so the list can be partially run, reordered, or parallelised via DEX without breaking.

📋 Quick Reference Summary

Concept Key Points
Test Suite Logical grouping for organisation/reporting; not directly executable.
Execution List Ordered, runnable queue of Test Cases with agent/error-handling config.
Test Event Setup/teardown wrapper run before/after every entry, or once per list.
Result states Passed / Failed / Error / Skipped — each with a distinct root cause profile.
ExecutionEntry A reference to a Test Case within a specific Execution List's run queue.
OnError setting Continue keeps running remaining entries; Stop halts the whole list.
