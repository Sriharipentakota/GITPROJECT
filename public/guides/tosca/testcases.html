BEGINNER1. What Is a Test Case?

Definition

A Test Case in Tosca is a container holding an ordered list of Test Steps. Each Test Step references a Module Attribute and supplies the value to use when that step executes. The Test Case captures what should happen and with what data — the how (which control, which technology, which selector) lives entirely in the Module.

Real-world analogy: A Tosca test case is like a recipe card. The ingredients (data values) are listed on the card, but the cooking instructions (how to whisk eggs, how to click a button) live in the module — the "kitchen manual." You can write a hundred recipes that reference "whisk eggs" without redefining how whisking works each time.

Why Separate Test Cases from Modules?

  • Test Cases stay readable by business stakeholders — no technical selectors visible.
  • A single Module can be reused across dozens of unrelated Test Cases.
  • Changing test data or scenario ordering never touches the underlying UI model.

BEGINNER2. Anatomy of a Test Step

Every Test Step consists of, at minimum: a reference to a Module (or Module Attribute), and a value. Optionally it may also carry a description, a Condition, and an attached Recovery Scenario.

TestCase: TC001_Login
  TestStep 1: Navigate to Login
    Module: Browser → Goto URL
    Value: {P:BaseURL}/login
  TestStep 2: Enter credentials
    Module: LoginPage.Username
    Value: {P:TestUser}
  TestStep 3: Enter password
    Module: LoginPage.Password
    Value: {P:TestPassword}
  TestStep 4: Click Login
    Module: LoginPage.LoginButton
  TestStep 5: Verify welcome
    Module: Dashboard.WelcomeLabel [Verify]
    Value: "Welcome, {P:TestUser}"
💡 Tip: Step 4 has no value because clicking a button is an action, not a data entry — the LoginButton attribute's ActionMode (Input) is enough to trigger the click at execution time.

BEGINNER3. Building Your First Test Case

Step by step in TCM: 
1. Right-click the TestCases folder → New TestCase → name it "TC001_Login"
2. Drag the "LoginPage" Module onto the TestCase → TCM creates one Test Step per attribute
3. Delete/reorder steps you don't need for this scenario
4. Fill in values for each step (literal text, or {P:...} / {B:...} references)
5. Drag "Dashboard" Module in for the final Verify step
6. Right-click the TestCase → Run to execute it standalone

Reading a Test Case Like a Story

A well-built Test Case should read almost like a numbered set of user instructions:

1. Go to {P:BaseURL}/login
2. Enter Username = {P:TestUser}
3. Enter Password = {P:TestPassword}
4. Click Login
5. Verify Welcome message = "Welcome, {P:TestUser}"

INTERMEDIATE4. Value Sources: Literals, Parameters, Buffers

A Test Step's value can come from three sources, and mixing them within the same string is fully supported:

Value Source Syntax Use Case
Literal "admin@test.com" Fixed, hard-coded value that never changes
Configuration Parameter {P:ParamName} Environment-specific or reusable constants (URL, credentials)
Buffer {B:BufferName} Runtime value captured from an earlier step 
// Mixed value: literal text + parameter + buffer in one string
Value: "Order {B:OrderID} confirmed for {P:TestUser}"
⚠️ Common Pitfall: Hard-coding environment URLs or credentials as literals directly in Test Steps means every test case needs manual editing when the environment changes. Always prefer {P:...} references — see the Configuration Parameters guide for the full parameter hierarchy.

INTERMEDIATE5. Reuse via Embedded (Nested) Test Cases

A Test Step can reference an entire other Test Case instead of a single Module attribute. This lets you build a library of reusable flows — a "Login" Test Case used as a step inside "Place Order" and "Reset Password" — without duplicating logic.

// Referencing another test case as a step
TestCase: TC002_PlaceOrder
  TestStep 1: [TestCase] TC001_Login   ← reuse
  TestStep 2: Add item to cart
  ...
TestCase: TC_SearchProduct
  ├── Step 1: Login (embedded TC001_Login)
  ├── Step 2: SearchBar.SearchInput
  │     Value: {B:ProductName}   ← from Buffer
  ├── Step 3: SearchBar.SearchButton
  ├── Step 4: ResultsGrid.FirstResult [Verify]
  │     Value: {B:ProductName}   ← assert same value
  └── Step 5: Logout (embedded TC_Logout)
Why this matters: if the login flow gains a new "Accept Cookies" step, you fix it once inside TC001_Login. Every Test Case that embeds TC001_Login — potentially hundreds — picks up the fix automatically the next time it runs.

INTERMEDIATE6. Test Case Folder Organisation

As a project grows past a handful of test cases, folder structure becomes essential for navigation, execution scoping, and reporting.

TestCases/
├── Smoke/
│   ├── TC001_Login
│   └── TC002_HomepageLoad
├── Regression/
│   ├── UserManagement/
│   │   ├── TC010_CreateUser
│   │   ├── TC011_EditUser
│   │   └── TC012_DeleteUser
│   └── Orders/
│       ├── TC020_PlaceOrder
│       └── TC021_CancelOrder
└── Shared/
    ├── TC_Login          ← reusable building block
    └── TC_Logout
Folder Convention
Smoke Fast, critical-path checks run on every deployment
Regression Full feature coverage, organised by business area
Shared Reusable embedded test cases (login, logout, navigation)

ADVANCED7. TestStepValues and TestSheets

Under the hood, each Test Step's data lives in a structure Tosca calls a TestStepValue, and the full grid of steps for a Test Case is its TestSheet. Understanding this distinction matters once you start data-driving Test Cases with multiple partitions (see Test Data Management).

TestSheet: TC001_Login
┌───────┬──────────────────────┬────────────────────────┐
│ Step  │ Module.Attribute      │ TestStepValue           │
├───────┼──────────────────────┼────────────────────────┤
│ 1     │ Browser.GotoURL       │ {P:BaseURL}/login       │
│ 2     │ LoginPage.Username    │ {P:TestUser}            │
│ 3     │ LoginPage.Password    │ {P:TestPassword}        │
│ 4     │ LoginPage.LoginButton │ (no value — click)      │
│ 5     │ Dashboard.WelcomeLabel│ "Welcome, {P:TestUser}" │
└───────┴──────────────────────┴────────────────────────┘

When a Test Case is bound to an Excel or database data source (TDM), Tosca effectively creates one instance of this TestSheet per data row — each becomes an independent execution partition with its own pass/fail result.

ADVANCED8. Conditions and Recovery on Steps

Individual Test Steps (and whole Test Cases) can carry two kinds of resilience logic layered on top of the base step definition:

  • Condition: a Buffer/Parameter comparison that determines whether the step executes at all (see the Steering guide for full syntax).
  • Recovery Scenario: a fallback Test Case that runs automatically if this step fails, potentially retrying it (see the Recovery Scenarios guide).
TestStep: LoginPage.LoginButton
  Condition: {B:AlreadyLoggedIn} = "false"
  RecoveryScenario: TC_ClosePopup (Priority 1)
💡 Tip: Conditions and Recovery are optional properties on any step — you don't need to touch them until a real scenario calls for conditional branching or resilience against known intermittent failures.

INTERMEDIATE9. Common Pitfalls

  • Duplicating flows instead of embedding: copy-pasting login steps into every Test Case instead of embedding a shared TC_Login means every UI change requires editing dozens of Test Cases again.
  • Over-long Test Cases: a single Test Case with 80 steps covering five unrelated scenarios is hard to debug and re-run selectively — split it into focused, embeddable pieces.
  • Hard-coded values everywhere: literals sprinkled through steps instead of Parameters/Buffers make environment switches and data-driving painful later.
  • Missing final assertions: a Test Case with only Input steps and no Verify step "passes" even if the feature is completely broken, because nothing was actually checked.

BEGINNER10. Best Practices

1. One Test Case, One Scenario

Keep each Test Case focused on verifying a single business scenario end-to-end.

2. Always End with a Verification

Every meaningful Test Case should include at least one Verify step — otherwise a passing run proves nothing.

3. Extract Shared Flows Early

// Instead of repeating login steps in 20 test cases:
Shared/TC_Login   ← build once
TC020_PlaceOrder  → Step 1: [TestCase] TC_Login
TC030_ViewProfile → Step 1: [TestCase] TC_Login
TC040_Logout      → Step 1: [TestCase] TC_Login

4. Name Steps for Readability

Give each Test Step a clear description ("Click Login", not "Step 4") so logs and reports are self-explanatory.

5. Favor Parameters and Buffers Over Literals

Reserve literal values for things that genuinely never change (e.g. a fixed expected label text); use {P:...} and {B:...} for anything environment- or run-dependent.
