BEGINNER1. What Are Configuration Parameters?

Definition

Configuration Parameters (often just "parameters" or "Config Params") are reusable, named values that can be referenced anywhere in a test suite using the syntax {P:ParameterName}. They act like global or local constants — store a URL, a username, a database connection string, or an environment flag once, and reference it everywhere it's needed.

Real-world analogy: Config Parameters work like environment variables in software development. You define DATABASE_URL=postgres://prod/db once; every service that needs it reads the variable — you don't embed the connection string inside each service's code. Swapping environments means changing one variable, not editing dozens of files.

BEGINNER2. Reference Syntax

// Reference syntax
{P:ParameterName}         → resolves parameter value
{P:BaseURL}/login         → concatenation supported
{B:BufferName}            → read a captured buffer value
{B:BufferName|default}    → buffer with fallback

Parameter references can be embedded inside larger strings, combined with literal text, and even combined with Buffer references in the same value.

// A single value combining a parameter and literal text
Navigate: {P:BaseURL}/dashboard
Enter URL in SearchBar: {P:BaseURL}/api/search

BEGINNER3. Parameter Scopes and Precedence

Parameters live in a hierarchy, and a parameter defined at a lower (more specific) level overrides a same-named parameter defined at a higher (broader) level:

Scope Applies To Precedence
Global Parameter Entire workspace — all Test Cases Lowest (overridden by anything more specific)
Folder Parameter A folder and everything nested inside it Middle
TestCase-level Parameter One specific Test Case only Highest — always wins if defined 
// Parameter scopes (precedence: local > folder > global)
Global Parameter:  MyWorkspace → Parameters → BaseURL = https://prod.example.com
Folder Parameter:  QA_Env → Parameters → BaseURL = https://qa.example.com
TestCase Param:    TC001 → Parameters → BaseURL = https://local.example.com
💡 Tip: When a Test Step resolves {P:BaseURL}, Tosca looks for the closest-scoped definition first — TestCase, then containing Folder, then Global — and uses the first one it finds. This lets you define sensible defaults globally while allowing surgical overrides where needed.

INTERMEDIATE4. Switching Environments with Parameters

// Global parameter
BaseURL = https://qa.example.com

// Test step using parameter
Navigate: {P:BaseURL}/dashboard
Enter URL in SearchBar: {P:BaseURL}/api/search

// To switch to staging — change ONE parameter:
BaseURL = https://staging.example.com
// All test steps pointing to {P:BaseURL} now hit staging
Why this is transformative for maintenance: without parameters, "switching to staging" means finding and editing every literal URL scattered across hundreds of Test Steps. With parameters, it's a single field edit — the same underlying principle as the Module abstraction, applied to data instead of UI structure.

INTERMEDIATE5. Parameter Container Definitions (PCDs)

A PCD (Parameter Container Definition) is a template that groups related parameters together — for example, a "Browser" PCD containing URL, browser type, and timeout — so an entire configuration bundle can be swapped as one unit rather than editing individual parameters one at a time.

// PCD (Parameter Container Definition) example
PCD: BrowserConfig
  BaseURL      = https://qa.example.com
  Browser      = Chrome
  Timeout      = 30000
  Username     = test_user
PCD: QA_Config
  BaseURL  = https://qa.example.com
  Username = qa_admin
  Password = qa_pass123

PCD: Staging_Config
  BaseURL  = https://staging.example.com
  Username = stg_admin
  Password = stg_pass456

INTERMEDIATE6. Attaching a PCD to an Execution List

// Attach PCD to Execution List
ExecutionList → Properties → PCD = QA_Config
// → All {P:BaseURL} in this run resolve to QA values

Because the PCD is attached at the Execution List level, the exact same Test Cases can run against QA today and Staging tomorrow purely by swapping which PCD is attached — no edits to any Test Case or Module required.

Without PCDs With PCDs
Edit multiple individual Global/Folder parameters per environment switch Swap one PCD reference on the Execution List
Risk of forgetting to update one related parameter All related parameters travel together as one unit

ADVANCED7. Parameters vs Buffers

Parameters and Buffers both use a curly-brace reference syntax, and it's easy for newcomers to conflate them. The distinguishing factor is when the value is known.

{P:Parameter} — known before run: 
Defined ahead of time in TCM
Same value for the whole run
  (or per environment/PCD)
Example: {P:BaseURL}, {P:TestUser}
{B:Buffer} — known during run: 
Captured live from the application
  via an Output step
Value differs every execution
Example: {B:OrderID}, {B:AuthToken}
⚠️ Common Pitfall: Attempting to hard-code a dynamically generated value (like an auto-incrementing order number) as a Parameter will always be wrong the moment the real application generates a different number. Values that only exist once the application runs must be captured with a Buffer, not stored as a Parameter.

ADVANCED8. Sensitive Parameters (Passwords, Secrets)

Parameters holding credentials or secrets deserve special handling. Tosca supports marking parameters so their values are masked in logs and the TCM UI, reducing the risk of secrets leaking into execution reports, screenshots, or shared repositories.

// Conceptual masked parameter
Parameter: Password  (marked as "Encrypted"/"Hidden")
  Value stored encrypted in repository
  Displayed as ******** in TCM UI and execution logs
  Resolved to real value only at execution time
💡 Tip: Even with masking, avoid granting broad repository read access to anyone who doesn't need it — encrypted-at-rest is not the same guarantee as access-controlled. Combine parameter masking with proper repository permissions for genuinely sensitive credentials.

INTERMEDIATE9. Common Pitfalls

  • Literal URLs/credentials scattered in Test Steps: defeats the entire purpose of parameters and makes environment switching a manual hunt-and-replace exercise.
  • Overriding at the wrong scope: setting an override at the Global level when it was only meant for one Test Case, silently affecting unrelated tests.
  • Forgetting precedence rules: being surprised that a Global change had no effect because a Folder or TestCase-level override was already in place.
  • Storing secrets as plain, unmasked parameters: exposing credentials in logs and screenshots unnecessarily.

BEGINNER10. Best Practices

1. Default to Parameters, Never Literals for Environment Data

URLs, hostnames, credentials, and environment flags should always be Parameters, never literal values baked into Test Steps.

2. Group Related Parameters into PCDs

If two or more parameters always change together (e.g. BaseURL and its matching Username/Password), bundle them into a PCD.

3. Use Consistent Naming

BaseURL, ApiBaseURL, DbConnectionString
TestUser, TestPassword, AdminUser, AdminPassword

4. Mask Sensitive Parameters

Mark passwords, API keys, and tokens as encrypted/hidden parameters rather than plain text.

5. Document Scope Intent

When overriding a parameter at Folder or TestCase level, add a short description explaining why — future maintainers will otherwise be puzzled why a Global change "isn't taking effect" for that branch.
