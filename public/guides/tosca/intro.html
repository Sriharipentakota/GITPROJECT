BEGINNER1. What Is Tricentis Tosca?

Definition

Tricentis Tosca is a model-based, mostly no-code/low-code enterprise test automation platform. Instead of writing lines of code to drive a browser, desktop application, or API, testers scan the application under test once to build a reusable model of its controls, then assemble test cases visually by dragging those modelled controls into an ordered sequence of steps.

Who uses it and why: Tosca is popular in large enterprises (banking, insurance, SAP-heavy organisations, healthcare) because it lets manual testers, business analysts, and QA engineers — not just developers — build and maintain automated regression suites, and because a single UI-model change can repair dozens of test cases at once.

What Tosca is NOT

  • It is not a programming language or scripting framework like Selenium/WebDriver or Playwright — there is no source file of test code to check into a repository (though the underlying assets are versionable).
  • It is not limited to web UIs — the same tool and workflow test desktop apps (WinForms, Java Swing), mainframes, SAP GUI, mobile apps, PDF documents, databases, and REST/SOAP APIs.
  • It is not just a "recorder" — while it can capture actions, professional Tosca usage centres on the reusable Module model, not brittle recorded scripts.

The Four Pillars

1. TBox Scanning    → builds a Module (UI/API model) from the real application
2. Test Cases       → ordered Test Steps that reference Modules and supply data
3. Execution        → Execution Lists that run test cases and record results
4. Requirements     → traceability linking business requirements to test coverage
💡 Tip: Every other concept in this course (Modules, TestSteps, Buffers, Recovery Scenarios, DEX) is built on top of these four pillars. If you understand how they connect, the rest of Tosca falls into place quickly.

BEGINNER2. The Model-Based Testing Philosophy

Traditional automation frameworks encode "how to interact with the UI" directly inside each test script — a locator, a click, an assertion, repeated in every file that touches that screen. When the UI changes, every script that hard-codes that locator breaks, and someone has to hunt them all down.

Tosca's Answer: Separate the Model from the Logic

Tosca splits automation into two independent layers:

  • The Module (the model): a single definition of a screen's controls and how to find them technically.
  • The Test Case (the logic): a sequence of business-meaningful steps that reference the Module's attributes and supply data.
Application UI changes: the "Login" button ID changes from #btnLogin to #loginSubmit

Traditional scripted automation:
  → grep the codebase for "btnLogin"
  → find it hard-coded in 40 test scripts
  → update all 40 files, re-run, hope nothing was missed

Tosca:
  → open Module: LoginPage
  → re-scan or fix the LoginButton attribute's technical selector — once
  → all 40 test cases that reference LoginPage.LoginButton are fixed instantly
Real-world analogy: Think of the Module as a LEGO brick mould. Scanning shapes the mould once; every test case that snaps that brick into place automatically gets the updated shape if the mould is corrected. You never have to reshape a thousand already-built models by hand.

Why This Matters for Maintenance Cost

Industry studies consistently show that the majority of automated-test effort is spent on maintenance, not initial creation. By centralising "how do I find and touch this control" in one place (the Module), Tosca dramatically cuts the ongoing maintenance burden — this is the platform's core value proposition, more than any individual feature.

BEGINNER3. Tosca Commander (TCM): The Workbench

Tosca Commander, universally abbreviated TCM, is the Windows desktop IDE where every Tosca asset is created, edited, executed, and reviewed. It is organised as a tree of sections down the left-hand navigation pane.

TCM Section Purpose Typical Contents
Modules The scanned UI/API model layer LoginPage, Dashboard, POST_Login (API module)
TestCases Test logic — ordered steps referencing modules TC001_Login, TC020_PlaceOrder, Test Suites
Execution Run configuration and historical results ExecutionLists, ExecutionEntries, logs, screenshots
Requirements Traceability matrix and risk classification User stories linked to covering test cases
Libraries Reusable technical assets (recovery scenarios, PCDs) Recovery Test Cases, Parameter Container Definitions

💡 Tip: New Tosca users often try to work top-down through the TCM ribbon menus. Experienced testers work almost entirely through the tree's right-click context menus — Scan Application, Add Test Step, Create Execution List — because that is where 90% of daily actions live.

INTERMEDIATE4. The Repository and How Assets Are Stored

Everything you create in TCM — Modules, TestCases, Execution Lists, Requirements — is persisted to a central SQL Server or Oracle database called the Common Repository. This is a critical architectural difference from file-based automation frameworks: there is no "test.js" file sitting on your laptop's disk that only you can see.

Why a Database Instead of Files?

  • Single source of truth: every team member connects to the same repository, so there's no "which branch has the latest module" ambiguity.
  • Structured querying: Tosca Query Language (TQL) can search across the entire repository — e.g. find every test case that uses a specific module attribute — something that is painful to do with grep across thousands of script files.
  • Built-in locking: check-out/check-in (covered in the Workspaces guide) prevents two people from silently overwriting each other's work.
⚠️ Common Pitfall: Because everything lives in a database, Tosca cannot be "diffed" with a plain text diff tool the way a Git-tracked script file can. Larger teams typically pair Tosca with its XML export/import features or a plugin to get change history into source control — plan for this in your DevOps design rather than discovering it mid-project.

Local Repository vs Shared Repository

Local (single-user) Repository: 
Stored as: local database file (e.g. SQL Server Express, LocalDB)
Used for: solo learning, proof-of-concept, demos
Limitation: no multi-user collaboration, no DEX agent sharing
Common (shared) Repository: 
Stored as: central SQL Server / Oracle instance
Used for: real project teams
Benefit: check-out/check-in, Workspaces, shared Execution history

INTERMEDIATE5. Technical vs Business Parameters

Every Module Attribute that TBox records has a Technical Parameter — the raw engine-level property, such as Value, Checked, or SelectedItem. On its own, a technical parameter is meaningful to the automation engine but not to a business stakeholder reading a test case.

Testers wrap technical parameters with a Business Parameter: a human-readable alias that appears in the Test Step. This is what makes a Tosca test case readable by a non-technical reviewer.

// Technical Parameter (TBox-defined, maps to control property)
Module: UsernameField
  TechnicalParameter: Value   ← what you type into the field

// Business Parameter (created by tester, maps to technical param)
Module: UsernameField
  BusinessParameter: Username → maps to → Value

// Test Step uses business parameter
Step: Enter credentials
  Username = "alice@test.com"
Why this decoupling matters: if a developer renames the underlying HTML attribute, or the field moves to a different control type entirely, the technical parameter mapping is fixed once inside the Module. The business parameter name — and therefore every test case that reads "Username = alice@test.com" — never has to change.

INTERMEDIATE6. The End-to-End Tosca Workflow

Nearly every Tosca project follows the same lifecycle, regardless of application type:

1. Scan application UI          → TBox creates Module tree
2. Define Business Parameters   → wrap technical params with readable names
3. Build Test Cases             → drag Module steps into an ordered sequence
4. Parameterise with Test Data  → bind values via {P:param}, Excel, or DB (TDM)
5. Add to Execution List        → group test cases; run locally or via DEX
6. Review Results               → logs, screenshots, pass/fail per step
7. Trace to Requirements        → confirm coverage; run Test Optimisation

ADVANCED7. Tosca vs Traditional Script-Based Automation

Understanding when Tosca's model excels — and where its trade-offs bite — helps you set realistic expectations on a project.

Dimension Script-Based (Selenium/Playwright) Tosca (Model-Based)
Who can author tests Developers / SDETs comfortable with code Manual testers, BAs, and engineers alike
Maintenance on UI change Locate and fix every affected script Fix once in the Module; all test cases inherit the fix
Version control Native — plain text files in Git Database-backed; requires XML export or plugin for Git
Complex custom logic Full programming language available Steering (Buffers/Conditions/Loops) covers most cases; true edge logic needs custom TBox/extensions
Licensing Mostly open-source Commercial enterprise license
Cross-technology reach Typically one technology per framework (web, mobile, API separately) One tool spans web, desktop, SAP, mainframe, mobile, API, PDF
💡 Tip: Enterprises with SAP-heavy, multi-technology estates and large non-developer QA teams tend to see the biggest ROI from Tosca. Small, code-native teams building a single web app may find a scripted framework faster to iterate with.

ADVANCED8. Risk-Based Test Optimisation (TO)

Because Requirements, risk levels, and test-case coverage all live in the same repository, Tosca can computationally determine the smallest set of test cases that still covers every requirement at its declared risk level. This feature is called Test Optimisation (TO) and is one of Tosca's flagship differentiators versus purely scripted tools, which have no concept of "requirement risk" baked into the framework.

// Full regression: 200 test cases
// After Test Optimisation (focus on High/Critical risks):

Optimised set: 43 test cases
  ✓ Covers all Critical requirements
  ✓ Covers all High requirements
  – Skips 157 Low-risk test cases (still logged as skipped)

Execution time: 43 × 30s = ~22 minutes
  vs. 200 × 30s = 100 minutes (full run)
  → 78% time reduction with same risk coverage
When to reach for TO: nightly/CI gate runs where full regression can't fit the pipeline window. Full regression is still run periodically (e.g. weekly) to catch anything the optimised set skipped.

INTERMEDIATE9. Common Pitfalls for Newcomers

  • Recording instead of modelling: using Tosca purely as a macro recorder produces brittle, unmaintainable test cases — the same anti-pattern Tosca was designed to avoid. Always build proper Modules with business parameters.
  • Skipping Business Parameters: leaving test steps bound directly to technical parameters makes test cases unreadable to non-technical reviewers and defeats the decoupling benefit.
  • Treating TCM like a file-based IDE: forgetting that assets live in a shared database leads to surprises around locking (see Workspaces & Collaboration) — always check out before editing shared assets.
  • Ignoring Requirements linkage: without linking test cases to requirements, Test Optimisation has nothing to optimise against, and coverage gaps go unnoticed until production defects surface.

BEGINNER10. Best Practices

1. Model Before You Automate

Spend time getting the Module structure right (clear names, correct ActionModes, business parameters) before building dozens of test cases on top of it. A well-built Module pays for itself many times over.

2. Establish a Naming Convention Early

Modules:      PageName / ScreenName (PascalCase)
TestCases:    TC### _ ShortDescription
Buffers:      B_ meaningful name
Parameters:   P_ meaningful name

3. Keep Test Cases Business-Readable

A reviewer with no Tosca training should be able to read a Test Case's step list and understand what business scenario it verifies.

4. Reuse via Embedded Test Cases

Extract common flows (login, logout, navigation) into shared, reusable test cases rather than duplicating steps everywhere.

5. Connect Requirements from Day One

Link every test case to the requirement(s) it verifies as you build it, not retroactively — this keeps the traceability matrix trustworthy and enables Test Optimisation.
