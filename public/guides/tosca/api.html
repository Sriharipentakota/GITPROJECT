BEGINNER1. What Is ServiceV?

Definition

Tosca's ServiceV Engine (formerly the Tosca API Engine) brings the same model-based, no-code approach used for UI testing to REST, SOAP, GraphQL, and messaging-based APIs. Instead of scanning a screen, you define a Service Endpoint Module capturing the API's URL, HTTP method, headers, and body schema — then build Test Steps exactly as you would for a UI Module.

Real-world analogy: API testing in Tosca is like using a universal remote control. The remote (ServiceV module) knows the signal format for each device (endpoint). You press the button (test step), supply the channel number (request data), and the remote verifies the TV changed to the right channel (response assertion) — no need to understand the infrared encoding protocol.

ServiceV vs UI Testing: What's the Same, What's Different

Aspect UI Testing ServiceV (API Testing)
Model source TBox scan of live controls Manually defined endpoint, or imported from Swagger/WSDL
Module attributes Control properties (Value, Checked) Request fields, headers, response fields
Test Step structure Same TestCase/TestStep model Same TestCase/TestStep model
Assertions Verify against control value Verify against status code, header, or JSON/XML body field

BEGINNER2. Anatomy of a Service Endpoint Module

// REST API Module structure (created via ServiceV scan)
Module: POST_Login
  Endpoint: POST {P:BaseURL}/api/auth/login
  Headers:
    Content-Type: application/json
  Request Body (JSON):
    username: {P:Username}
    password: {P:Password}
  Response:
    StatusCode [Verify]:  200
    Body.token [Output]:  → {B:AuthToken}

Just like a UI Module, each field can be assigned an ActionMode — Input for request fields you're sending, Verify for response assertions, Output for response values you want to capture into a Buffer for later use.

BEGINNER3. Building Your First API Test Case

Step by step in TCM: 
1. Right-click Modules → Add Module → Service Endpoint (ServiceV)
2. Define method (POST), URL, headers, and request body schema
3. Define expected Response fields and mark ActionModes
4. Drag the module into a new TestCase
5. Fill in request values using {P:...} parameters
6. Run the TestCase → response is validated against your assertions
TestCase: TC_API_AuthFlow
Step 1: POST /api/auth/login
         username = {P:APIUser}
         password = {P:APIPass}
         [Response] StatusCode = 200  ← verify
         [Response] token → {B:Token} ← capture

INTERMEDIATE4. Chaining Requests with Buffers

Real-world API test scenarios almost always involve chaining: authenticate once, then use the returned token to authorize subsequent calls. This is handled exactly like UI-to-UI buffer chaining — capture with Output, reference with {B:...}.

// Chained request using token
Module: GET_UserProfile
  Endpoint: GET {P:BaseURL}/api/user/me
  Headers:
    Authorization: Bearer {B:AuthToken}
  Response:
    StatusCode [Verify]: 200
    Body.name [Verify]:  {P:ExpectedName}
TestCase: TC_API_AuthFlow
Step 1: POST /api/auth/login
         username = {P:APIUser}
         password = {P:APIPass}
         [Response] StatusCode = 200  ← verify
         [Response] token → {B:Token} ← capture

Step 2: GET /api/user/profile
         Authorization = "Bearer {B:Token}"
         [Response] StatusCode = 200
         [Response] body.email [Verify] = {P:APIUser}
💡 Tip: Buffers are the connective tissue for any multi-request API test flow — login → create resource → verify resource → delete resource, capturing an ID at each step to feed the next.

INTERMEDIATE5. JSONPath and XPath Assertions

ServiceV lets you target specific fields deep inside a JSON or XML response body directly, rather than asserting against the entire raw payload text.

// TOSCA uses JSONPath to target response fields
Response assertions:
  $.status           [Verify] = "success"
  $.data.userId      [Verify] = "12345"
  $.data.roles[0]    [Verify] = "admin"
  $.pagination.total [Output] → {B:TotalCount}

// XML (SOAP) uses XPath
  /Envelope/Body/GetOrderResponse/OrderId [Verify] = "ORD-001"
Response Format Path Language Example
JSON (REST, GraphQL) JSONPath $.data.roles[0]
XML (SOAP) XPath /Envelope/Body/GetOrderResponse/OrderId

ADVANCED6. Importing from Swagger/OpenAPI and WSDL

Rather than manually typing out every endpoint's URL, headers, and body schema, ServiceV can import an entire API's contract from a Swagger/OpenAPI specification (REST) or a WSDL file (SOAP), auto-generating Service Endpoint Modules for every operation the contract defines.

// Conceptual import workflow
1. TCM → Modules → Import → Swagger/OpenAPI (or WSDL for SOAP)
2. Point to the spec file or a live spec URL
3. TCM generates one Module per endpoint/operation defined
4. Review generated modules — rename attributes to business terms
5. Build Test Cases referencing the imported modules as usual
Why this saves time: a REST API with 40 documented endpoints would take hours to model by hand field-by-field. Importing the OpenAPI spec produces all 40 endpoint Modules in minutes, letting testers focus effort on writing meaningful Test Cases rather than re-transcribing a contract that's already documented elsewhere.

ADVANCED7. Service Virtualization (the "SV" Side)

The "SV" half of ServiceV stands for Service Virtualization: standing up a virtual, simulated service that mimics a real backend dependency's request/response behaviour. This decouples your test suite from third-party services or incomplete backend components that aren't reliably available.

// Conceptual virtual service definition
VirtualService: Mock_PaymentGateway
  Listens on: {P:MockBaseURL}/payments/charge
  When request.amount > 0:
    Respond 200 { "status": "approved", "transactionId": "TXN-{{random}}" }
  When request.amount <= 0:
    Respond 400 { "status": "rejected", "reason": "invalid amount" }
Use Case Why Virtualize
Third-party payment gateway Avoid real charges and rate limits during testing
Backend still under development Test the consuming application before the real service exists
Unreliable external dependency Remove flakiness caused by a service outside your team's control

INTERMEDIATE8. Combining API and UI Steps in One Test Case

Because ServiceV Modules and UI Modules share the same Test Case/Test Step model, a single scenario can freely mix API calls and UI actions — for example, seeding data via an API call before driving the UI, or verifying a UI action's side effect by calling an API afterward.

TestCase: TC_EndToEnd_OrderFlow
Step 1: [API] POST /api/testdata/seedUser  → {B:UserId}
Step 2: [UI]  LoginPage.Username = {P:TestUser}
Step 3: [UI]  LoginPage.Password = {P:TestPassword}
Step 4: [UI]  LoginPage.LoginButton [click]
Step 5: [UI]  Dashboard.PlaceOrderButton [click]
Step 6: [API] GET /api/orders?userId={B:UserId} [Verify] status=200
Step 7: [API] Body.orders[0].status [Verify] = "Created"
💡 Tip: This hybrid pattern is extremely useful for setup/teardown efficiency — seeding or cleaning up test data via a fast API call instead of clicking through slow UI screens just to establish preconditions.

INTERMEDIATE9. Common Pitfalls

  • Asserting the whole response body as a literal string: brittle against any harmless field reordering or additional fields — use JSONPath/XPath to target only the fields that matter.
  • Hard-coding tokens instead of chaining: pasting a static, soon-to-expire auth token into a Parameter instead of capturing a fresh one via Buffer each run.
  • Not virtualizing flaky third-party dependencies: letting an unreliable external API cause intermittent failures across your entire suite.
  • Skipping status code assertions: checking only the body content and missing cases where the API returns an error status with an unexpectedly "valid-looking" body.

BEGINNER10. Best Practices

1. Always Assert the Status Code

Every API Test Step should verify the HTTP status code, not just body content.

2. Import Contracts Instead of Hand-Modelling

Use Swagger/OpenAPI or WSDL import whenever a machine-readable contract exists.

3. Chain, Don't Hard-Code, Dynamic Values

// Good
[Response] token → {B:Token}
Authorization = "Bearer {B:Token}"

// Avoid
Authorization = "Bearer eyJhbGciOi..." (static, will expire)

4. Target Specific Fields with JSONPath/XPath

Avoid whole-body string comparisons; assert only the fields relevant to the scenario.

5. Virtualize Unreliable Dependencies Early

Don't wait for flaky third-party failures to pile up — proactively virtualize services outside your team's control.
