BEGINNER1. What Is a Recovery Scenario?

Definition

A Recovery Scenario is an error handler that Tosca triggers automatically when a Test Step fails. Instead of letting one failed step abort the whole Test Case — and potentially block every remaining entry in an Execution List — you define a recovery that cleans up the broken state and either retries the step, skips ahead, or exits gracefully.

Real-world analogy: Recovery Scenarios are like an airbag system in a car. You don't re-engineer the car every time an accident happens — the airbag deploys automatically, protects the occupants (the subsequent test cases), and the car can be driven again after recovery. The driver (test run) continues rather than being completely totalled.

Why This Matters at Scale

In a nightly regression of hundreds of Test Cases, a single unhandled unexpected dialog (a session-timeout popup, a "rate this app" prompt) can otherwise cascade into dozens of unrelated failures downstream — because every subsequent step keeps failing to find the controls it expects while that dialog sits on top of the screen. A Recovery Scenario stops that cascade at its source.

BEGINNER2. Anatomy of a Recovery Scenario

A Recovery Scenario is itself a Test Case — an ordered list of steps — with one extra property at the end: a declared Recovery Action telling Tosca what to do once recovery steps finish running.

// Common recovery test case pattern
TC_RecoverFromUnexpectedDialog:
  Step 1: UnexpectedDialog.CloseButton [click]
  Step 2: Screenshot → save to results
  Step 3: [Recovery Action] = Skip
💡 Tip: Because a Recovery Scenario is a regular Test Case, you build and edit it with the exact same TCM tools you use for any other Test Case — there is no special recovery-authoring mode to learn.

BEGINNER3. Recovery Actions

The Recovery Action, set as the final instruction in a Recovery Scenario, tells Tosca what happens to the original failed step and the rest of the Test Case after recovery steps have run:

// Recovery actions (what happens after recovery TC runs)
Retry         → re-attempt the failed step (up to N times)
Skip          → skip the failed step, continue the test case
NextTestCase  → abort this TC, start the next in Execution List
Exit          → stop the entire Execution List
Recovery Action When to Use
Retry The failure was transient and the recovery steps restored a state where the original step should now succeed (e.g. re-login after a session timeout)
Skip The failed step is not critical to the rest of the scenario (e.g. dismissing an optional survey popup)
NextTestCase The failure means this specific scenario cannot continue meaningfully, but other Test Cases in the list are unaffected
Exit The failure indicates a systemic environment problem (e.g. application is down) where continuing any further test is pointless

INTERMEDIATE4. Attachment Levels: Step, TestCase, ExecutionList

Recovery Scenarios can be attached at three different scopes, letting you decide how broadly a given handler should apply:

Attachment Level Scope Example
TestStep Handles failure of one specific step only A flaky "Submit" button that occasionally needs a second click
TestCase Handles any step failure within that Test Case Session timeout recovery applicable to any step in a long checkout flow
ExecutionList Global handler applied across every Test Case in the run Unexpected alert dialogs that could appear anywhere in the application 
// Attaching a Recovery Scenario
TestStep → Properties → Recovery Scenario → Select TC_CloseDialog
Priority: 1   (lower = higher priority)
Condition: Always / OnError / OnVerificationFailed

INTERMEDIATE5. Priority and Conditions

Multiple Recovery Scenarios can be attached at the same or overlapping scopes. Tosca evaluates them in priority order — lower priority numbers run first — and each carries a Condition narrowing exactly when it should trigger.

Condition Fires When
Always Any failure of the associated step/case, regardless of cause
OnError An unexpected exception occurred (element not found, timeout)
OnVerificationFailed Specifically a Verify/Checkpoint step's assertion mismatch
⚠️ Common Pitfall: Attaching an OnError recovery meant for "unexpected dialog appeared" to also fire OnVerificationFailed can mask genuine functional defects — if a Verify step legitimately fails because the feature is broken, a recovery that automatically retries or skips it may hide a real bug from your reports. Scope Conditions narrowly to the failure type you're actually trying to handle.

INTERMEDIATE6. Common Recovery Patterns

// Recovery TC: TC_ClosePopup
Step 1: BrowserEngine.SwitchToAlert [if exists]
Step 2: AlertDialog.AcceptButton [click]
Step 3: [Recovery Action] = Retry   ← re-try original step

// Attached to:
ExecutionList level → Priority 1
// Fires any time an unexpected alert blocks a step
// Recovery TC: TC_HandleSessionTimeout
Step 1: LoginPage.Username → {P:Username}
Step 2: LoginPage.Password → {P:Password}
Step 3: LoginPage.LoginButton [click]
Step 4: [Recovery Action] = Retry   ← retry original step after re-login

// Attached at TestCase level with condition: OnError
// When session expires mid-test → auto re-login → retry
Scenario Pattern
Unexpected alert/dialog Close it, then Retry the original step
Session expiry Re-authenticate, then Retry
Non-critical popup (survey, tour) Dismiss it, then Skip
Application completely unreachable Screenshot/log, then Exit

ADVANCED7. Recovery Scenario Chains and Fallbacks

When several distinct failure modes can occur at the same attachment level, Tosca evaluates attached Recovery Scenarios in priority order until one condition's trigger matches. This effectively lets you build a fallback chain of handlers.

ExecutionList-level Recovery Scenarios (evaluated in priority order):
Priority 1: TC_CloseCookieBanner    (Condition: Always)
Priority 2: TC_CloseSurveyPopup     (Condition: Always)
Priority 3: TC_HandleSessionTimeout (Condition: OnError)
Priority 4: TC_GenericScreenshotAndSkip (Condition: Always — catch-all)

// If a step fails and no dialog/timeout is actually present,
// execution falls through to the catch-all at Priority 4
Why a catch-all matters: a final, low-priority "take a screenshot and Skip" recovery ensures that even genuinely unanticipated failures are logged with diagnostic evidence rather than causing an unhandled abort of the entire Execution List.

ADVANCED8. Testing Your Recovery Scenarios

A Recovery Scenario that has never actually been triggered is an untested piece of automation — exactly the kind of risk Tosca is meant to reduce elsewhere. Deliberately exercising the failure path before relying on it in production regression runs is essential.

// Deliberate trigger technique
1. Temporarily point a Test Step at a Module Attribute
   that is guaranteed to fail (e.g. wrong expected text)
2. Run the Test Case → confirm the Recovery Scenario fires
3. Confirm the Recovery Action behaves as expected
   (Retry actually retries; Skip actually continues; etc.)
4. Revert the Test Step to its correct configuration
💡 Tip: Keep a small, dedicated "Recovery Validation" Test Case or folder that intentionally triggers each Recovery Scenario, so regressions in recovery logic itself are caught the same way regressions in application behaviour are.

INTERMEDIATE9. Common Pitfalls

  • Recovery masking real defects: an overly broad OnError/Always recovery that retries past a genuine, reproducible failure hides the defect from your test report.
  • Infinite retry loops: a Retry recovery attached to a step whose failure condition never resolves (e.g. a permanently broken selector) can loop until a timeout, wasting execution time on every run.
  • No catch-all at the ExecutionList level: leaving unanticipated failures completely unhandled, causing avoidable cascading failures across an entire nightly run.
  • Untested recovery logic: a Recovery Scenario written once and never deliberately triggered may itself be broken and fail silently when it's actually needed.

BEGINNER10. Best Practices

1. Identify Failure Modes Deliberately

Common candidates:
- Unexpected dialogs / popups / cookie banners
- Session timeouts / re-authentication needs
- Slow-loading spinners causing premature timeouts
- Network blips on external service calls

2. Scope Conditions Narrowly

Prefer OnError over Always when the recovery is meant for exceptions, not for genuine assertion failures — protect your ability to see real defects.

3. Always Cap Retry Attempts

Never leave a Retry recovery without an explicit maximum attempt count.

4. Layer Recovery from Specific to General

Attach narrow, specific recoveries at the Step level; broader catch-alls at the ExecutionList level with a lower priority (higher number).

5. Deliberately Test Every Recovery Scenario

Trigger each one at least once before trusting it in a real regression run, and re-validate after any change to its logic.
