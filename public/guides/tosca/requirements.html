BEGINNER1. What Is the Requirements Section?

Definition

Tosca's Requirements section provides a traceability matrix linking business requirements to the Test Cases that verify them. Every requirement is tagged with a risk level and linked to one or more Test Cases. If a linked Test Case fails, Tosca immediately shows which requirement is at risk — turning an abstract test failure into a concrete statement about business impact.

Real-world analogy: Requirements traceability is like a building inspection checklist cross-referenced with the building code. Each code clause (requirement) maps to specific inspection items (test cases). Test Optimisation is the inspector focusing only on load-bearing walls (critical requirements) when time is short — the cosmetic items (low-risk) get deferred without compromising structural safety.

BEGINNER2. Risk Levels

Each Requirement is assigned a risk classification that drives both prioritisation and, later, Test Optimisation decisions.

Requirements/
├── US001: User can log in with valid credentials
│     Risk: Critical
│     LinkedTests: TC001_Login, TC010_SSOLogin
├── US002: User sees dashboard after login
│     Risk: High
│     LinkedTests: TC001_Login (step 5 verifies dashboard)
└── US003: Password must be 8+ characters
      Risk: Medium
      LinkedTests: TC005_PasswordValidation
Risk Level Typical Meaning
Critical Core business function; failure blocks users entirely or causes major financial/compliance impact
High Important function with significant but not catastrophic impact if broken
Medium Noticeable but workaround-able impact
Low Cosmetic or edge-case functionality

BEGINNER3. Linking Test Cases to Requirements

Step by step in TCM: 
1. Create or import a Requirement in the Requirements section
2. Set its Risk level (Critical / High / Medium / Low)
3. Open a Test Case that verifies this requirement
4. Drag the Requirement onto the Test Case (or vice versa) to create the link
5. Repeat for every Test Case that contributes coverage to this requirement

A single Requirement can be linked to multiple Test Cases (full coverage often needs more than one scenario), and a single Test Case can cover multiple Requirements — the relationship is many-to-many.

INTERMEDIATE4. The Coverage Matrix

Once links exist, TCM can render a coverage matrix — a grid showing which Test Cases cover which Requirements, immediately surfacing any Requirement with zero linked Test Cases.

Requirement       | Risk    | TC001 | TC005 | TC010 | Coverage
US001 Login       | Critical|  ✓    |       |  ✓    |  100%
US002 Dashboard   | High    |  ✓    |       |       |  100%
US003 Password    | Medium  |       |  ✓    |       |  100%
US004 Logout      | Low     |       |       |       |   0%  ← gap!

// US004 has no test case → alert in TOSCA dashboard
⚠️ Common Pitfall: A coverage gap on a Low-risk requirement is often acceptable to defer; a coverage gap on a Critical or High-risk requirement is a serious finding that should block a release sign-off. Review the matrix filtered by risk level, not just raw coverage percentage.

ADVANCED5. Test Optimisation (TO)

Because Requirements, risk levels, and coverage links all live in the same repository, Tosca can computationally determine the minimum set of Test Cases that still covers every Requirement at its declared risk level. This is Test Optimisation (TO) — one of Tosca's flagship differentiators, since purely scripted frameworks have no native concept of "requirement risk" to optimise against.

// Test Optimisation (TO) workflow
1. Set risk level on each requirement
2. Mark test cases as covering specific requirements
3. Run "Optimise" → TOSCA selects minimum covering set
4. Execution List is auto-populated with optimised TC set
// Full regression: 200 test cases
// After Test Optimisation (focus on High/Critical risks):

Optimised set: 43 test cases
  ✓ Covers all Critical requirements
  ✓ Covers all High requirements
  – Skips 157 Low-risk test cases (still logged as skipped)

Execution time: 43 × 30s = ~22 minutes
  vs. 200 × 30s = 100 minutes (full run)
  → 78% time reduction with same risk coverage
When to reach for TO: nightly/CI gate runs where a full 100-minute regression doesn't fit the pipeline window. Full regression should still run periodically (e.g. weekly) to catch anything the optimised set intentionally skipped.

ADVANCED6. Importing Requirements from ALM Tools

Requirements rarely originate inside Tosca itself — they typically live in a dedicated ALM (Application Lifecycle Management) tool. Tosca's integration layer can import Requirements from tools like Jira, Azure DevOps, and IBM DOORS, keeping the traceability matrix automatically synchronised rather than manually re-entered.

// Conceptual sync configuration
Integration: Jira
  Project:     PROJ
  IssueType:   Story
  SyncField:   Risk ← maps to Jira custom field "Business Impact"
  SyncMode:    Two-way / One-way (Jira → Tosca)
💡 Tip: Keeping this sync live (rather than a one-time import) prevents the common failure mode where the traceability matrix silently drifts out of date as new stories are added to the backlog after the initial import.

INTERMEDIATE7. Using TQL for Coverage Queries

Tosca Query Language (TQL) can query the Requirements/Test Case relationship directly, letting you answer coverage questions programmatically rather than eyeballing the matrix UI.

// Conceptual TQL query: find uncovered Critical/High requirements
SELECT Requirement.Name, Requirement.Risk
FROM Requirements
WHERE Requirement.Risk IN ("Critical", "High")
  AND Requirement.LinkedTestCaseCount = 0
Why this earns its keep: on a project with hundreds of requirements, a saved TQL query surfacing "high-risk requirements with zero coverage" can run as a standing health-check before every release, rather than relying on someone remembering to scroll through the full matrix.

INTERMEDIATE8. Requirements-Driven Reporting to Stakeholders

Because coverage and risk data are structured, Tosca Reports (see Execution & Reporting) can present results framed around business requirements rather than raw test case names — far more meaningful to a product owner or compliance auditor than a list of internal Test Case IDs.

Technical View Requirements-Framed View
"TC001_Login: Passed, TC010_SSOLogin: Failed" "US001 (Critical – User Login): Partial risk exposure — 1 of 2 covering tests failed"

INTERMEDIATE9. Common Pitfalls

  • Linking test cases retroactively, if at all: building the whole suite first and treating traceability as an afterthought, resulting in a permanently incomplete matrix.
  • Inconsistent risk assignment: different team members applying "Critical" and "High" inconsistently, undermining Test Optimisation's selection quality.
  • Stale ALM sync: a one-time import from Jira that's never refreshed, silently drifting out of sync with the real backlog.
  • Never running full regression: relying exclusively on the optimised subset forever, allowing defects in deliberately-skipped low-risk areas to accumulate unnoticed.

BEGINNER10. Best Practices

1. Link Requirements as You Build, Not Afterward

Create the Requirement-to-Test Case link at the same time you build the Test Case, while the connection is still fresh in mind.

2. Calibrate Risk Levels as a Team

// Establish shared definitions, e.g.:
Critical = revenue-blocking or regulatory
High     = major feature, no workaround
Medium   = feature with acceptable workaround
Low      = cosmetic / rarely used path

3. Review the Coverage Matrix Before Every Release

Filter by Critical/High risk and treat any gap as a release-blocking finding.

4. Keep ALM Sync Live

Prefer a continuously synced integration over a one-time import.

5. Run Full Regression Periodically Alongside Optimised Runs

Use Test Optimisation for fast CI gates, but schedule full regression (e.g. weekly) to catch anything the optimised set skips.
