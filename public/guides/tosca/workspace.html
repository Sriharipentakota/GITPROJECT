BEGINNER1. The Common Repository Model

Definition

Tosca's Common Repository is a central SQL/Oracle database that every team member connects to, ensuring everyone works against the same single version of all test assets — Modules, Test Cases, Execution Lists, Requirements. There is no per-developer local copy of the "codebase" the way there is with file-based version control.

Real-world analogy: The Tosca repository is like a shared Google Doc with track-changes and private drafts. The main document (common repository) is always the official version. Workspaces are personal drafts — you refine your writing privately, then propose a merge into the main document. If someone else edited the same sentence, Google Docs highlights the conflict for manual resolution.

BEGINNER2. Check-Out / Check-In Locking

Multi-user access is coordinated through check-out/check-in locking: when you edit a Test Case or Module, you check it out — locking it for others — make your changes, then check it back in, at which point the new version becomes immediately available to the whole team.

// Check-out / Check-in flow
Right-click asset → Check Out     → locks asset for you
[make changes]
Right-click asset → Check In      → saves and unlocks
State What It Means
Checked in (default) Anyone can check it out to edit; everyone sees the latest committed version
Checked out by you You can edit freely; others see it as locked and read-only
Checked out by someone else You can view but not edit until they check it back in

BEGINNER3. Workspaces: Private Sandboxes

Workspaces are private sandboxes within the common repository. A tester can check out assets into their personal Workspace, develop and test changes in isolation, then merge them back to the shared repository — conceptually similar to a feature branch in Git, but implemented at the database level rather than as file diffs.

// Workspace operations
TCM → Workspaces → New Workspace  → creates private sandbox
Move asset to Workspace           → isolated development
Merge Workspace → merge back to common repository
💡 Tip: Working in a Workspace prevents unstable, in-progress changes from breaking other testers' runs — teammates continue running the last checked-in, stable version of an asset while you develop your changes in isolation.

INTERMEDIATE4. A Full Team Workflow Example

// Alice: develop new Login module in workspace
1. Alice creates Workspace_Alice
2. Checks out LoginPage module → moves to workspace
3. Adds new attribute: RememberMeCheckbox
4. Runs local tests in workspace → passes
5. Merges Workspace_Alice → Common Repository
6. Bob can now see and use RememberMeCheckbox

// Bob: blocked scenario (without workspace)
1. Bob opens LoginPage module → sees "Checked out by Alice"
2. Cannot edit until Alice checks in
// → Use workspaces to avoid this bottleneck
The key insight: without a Workspace, a simple check-out/check-in already prevents two people from corrupting each other's edits — but it also fully blocks Bob from making any progress on that asset until Alice finishes. A Workspace lets Alice develop over multiple days without indefinitely locking the shared asset for everyone else.

INTERMEDIATE5. Merge Conflicts and Resolution

When two users have modified the same asset concurrently (e.g. in separate Workspaces) and both attempt to merge back, TCM detects the conflict and presents a visual resolution dialog rather than silently overwriting one person's change.

// Two users edit same test case simultaneously
Alice: modifies TC001 Step 3 value to "admin@new.com"
Bob:   modifies TC001 Step 3 value to "user@new.com"

// When Bob merges:
TCM shows Merge Conflict dialog
  Alice's version: "admin@new.com"
  Bob's version:   "user@new.com"
  Current value:   "alice@test.com" (original)
→ Bob chooses: Keep Mine / Take Theirs / Merge manually
⚠️ Common Pitfall: Reflexively clicking "Keep Mine" on every conflict without reading what the other change actually was can silently discard a teammate's legitimate fix. Always read both versions before resolving.

ADVANCED6. Workspaces vs Git Branching

Testers coming from a software development background naturally reach for a Git mental model when learning Workspaces. The analogy is useful but imperfect — understanding where it breaks down avoids confusion.

Aspect Git Branch Tosca Workspace
Storage Full repository clone/branch as files Database-level isolation within one shared repository
Offline work Fully supported — commit locally without network Requires live connection to the Common Repository
History/diffing Rich native commit history and text diffs More limited built-in history; XML export needed for true diffing
Conflict detection Line-level text merge conflicts Asset-level (whole Module/TestCase field) merge conflicts

ADVANCED7. Integrating with External Version Control

Because the repository database itself isn't naturally diff-friendly, larger teams often pair Tosca's Workspace model with its XML export/import capability (or a dedicated plugin) to get meaningful change history into an external system like Git.

// Conceptual XML export/import for external VCS tracking
TCM → Repository → Export → XML  → produces versionable XML files
[commit XML files to Git for history/diff/audit trail]

TCM → Repository → Import → XML  → restores/migrates assets
[used for environment promotion or disaster recovery]
💡 Tip: This XML export/import path is also commonly used to promote a stable set of Modules and Test Cases from a development repository into a separate QA or Production Tosca repository, independent of any day-to-day Workspace activity.

INTERMEDIATE8. Repository Permissions and Access Control

Connecting to the Common Repository requires configured credentials and, in most enterprise setups, role-based permissions restricting who can check out, edit, or delete specific folders of assets.

// Common Repository connection
TCM → Options → Repository → Server URL + DB credentials
Role Typical Permissions
Test Author Check out/in Test Cases and Modules in assigned folders
Automation Lead Full read/write across the repository, plus Execution List and PCD management
Read-only Stakeholder View Test Cases and Reports without edit rights

INTERMEDIATE9. Common Pitfalls

  • Forgetting to check in: leaving an asset checked out overnight or over a weekend, blocking teammates unnecessarily.
  • Editing shared assets without a Workspace: long-running changes directly against the Common Repository lock out collaborators for the entire development period.
  • Resolving conflicts without reading both versions: reflexively choosing "Keep Mine," silently discarding a teammate's fix.
  • No external change history: lacking an XML export/Git pairing, making it hard to answer "what changed and why" months later.

BEGINNER10. Best Practices

1. Always Check Out Before Editing

Never attempt to edit a shared asset without checking it out first — this is the baseline protection against concurrent overwrites.

2. Check In Promptly

Don't hold a check-out lock longer than necessary; check in as soon as your change is stable enough to share.

3. Use Workspaces for Anything Multi-Day

// Good ongoing practice
- Small, quick fix?      → Check out, edit, check in same session
- Feature development
  spanning days?         → Use a dedicated Workspace

4. Read Both Sides of Every Merge Conflict

Take the time to understand what changed on both sides before choosing Keep Mine / Take Theirs / Merge manually.

5. Pair Workspaces with XML Export for Auditability

If your organisation needs change history or compliance audit trails, establish a regular XML export into Git alongside normal Workspace usage.
