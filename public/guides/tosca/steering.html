BEGINNER1. What Is Steering?

Definition

Steering is Tosca's umbrella term for the mechanisms that add conditional logic and dynamic data flow to Test Cases — without writing code. It rests on three pillars: Buffers (capturing values), Conditions (branching), and Loops (repetition).

Real-world analogy: Steering is like a traffic light controller. Buffers are the sensors in the road measuring car count. Conditions are the logic rules ("if north traffic > south traffic, give north a green"). Loops are the timer that keeps checking every 30 seconds. No one rewrites the controller's code every time traffic patterns change — the rules adapt dynamically.

BEGINNER2. Buffers: Capturing Runtime Values

A Buffer stores a value captured from the application at runtime — text read from a label, a generated order ID, a date field — for use in later steps. Setting a Module Attribute's ActionMode to Output writes its control's current value into a named buffer.

// Buffer: capture a value at runtime
Step: OrderConfirmation.OrderID
  ActionMode: Output       → captures text to {B:OrderID}
💡 Tip: Buffers exist only for the duration of the Test Case run in which they were captured (unless deliberately passed between embedded Test Cases). Each execution starts with clean, uninitialized buffer state.

BEGINNER3. Referencing and Chaining Buffers

Once captured, a buffer's value is referenced anywhere with {B:BufferName} — in a later Verify step, in a Condition, in another module's input value, even across a chain of several steps.

// Use buffer in later step
Step: VerifyEmail.OrderReference [Verify]
  Value: {B:OrderID}       → asserts value matches captured ID
// Test Case: Place Order and Verify Confirmation
Step 1: PlaceOrderPage.SubmitBtn [click]
Step 2: ConfirmationPage.OrderNumber
         ActionMode = Output → {B:OrderID}
Step 3: ConfirmationPage.OrderNumber [Verify]
         Value = {B:OrderID}        ← self-verify readable
Step 4: EmailPage.SubjectLine [Verify]
         Value = "Order {B:OrderID} Confirmed"
// Buffer bridges steps 2 → 4 without hard-coding the ID
Why this matters: the order ID is generated fresh on every run — it could never be a literal or a Parameter. Buffers are the only mechanism for asserting consistency of values that are unknown until the application creates them.

INTERMEDIATE4. Conditions: If/Else Without Code

A Condition evaluates a Buffer or Parameter value and determines whether a block of Test Steps executes — Tosca's equivalent of an if/else statement, configured entirely through the TCM UI.

// Condition (if/else steering)
Condition: {B:UserRole} = "Admin"
  [If true]  TC_OpenAdminPanel
  [If false] TC_OpenUserDashboard
Condition Type Example
Equality {B:Status} = "Ready"
Inequality {B:StatusValue} != "Ready"
Numeric comparison {B:AttemptCount} < 10
Combined (AND/OR) {B:StatusValue} != "Ready" AND {B:AttemptCount} < 10

INTERMEDIATE5. While Loops

A While loop repeats a block of Test Steps as long as a condition remains true — used for polling, retry logic, or processing an unknown number of items.

// While loop
While: {B:RetryCount} < 3
  Step: CheckStatus
  Step: IncrementRetry     → buffer arithmetic
// Retry until status = "Ready" or 10 attempts
Buffer: AttemptCount = 0
Buffer: StatusValue  = ""

While: {B:StatusValue} != "Ready" AND {B:AttemptCount} < 10
  Step: StatusPage.StatusLabel
         ActionMode = Output → {B:StatusValue}
  Step: Math.Add
         {B:AttemptCount} + 1 → {B:AttemptCount}
  Step: Wait 2 seconds
⚠️ Common Pitfall: A While loop without a guaranteed exit condition (like the attempt counter above) can run indefinitely if the polled value never changes, effectively hanging the Test Case. Always pair a status-based While condition with a maximum attempt/timeout counter.

INTERMEDIATE6. For Iterations

A For block repeats a set of Test Steps a fixed number of times — useful when the repeat count is known ahead of time, unlike a While loop's condition-driven repetition.

// For iteration (repeat 5 times)
For: Iterations = 5
  Step: AddItemToCart
While loop (condition-driven): 
While: {B:Status} != "Ready"
  Step: PollStatus
// Repeats an unknown number of
// times until the condition changes
For loop (count-driven): 
For: Iterations = 5
  Step: AddItemToCart
// Always repeats exactly 5 times,
// regardless of any runtime value

ADVANCED7. Buffer Arithmetic and Manipulation

Buffers aren't limited to storing raw captured strings — Tosca's built-in steering modules support arithmetic and string operations on buffer values, which is essential for counters, running totals, and string composition inside loops.

// Increment a counter buffer
Step: Math.Add
  {B:AttemptCount} + 1 → {B:AttemptCount}

// Concatenate buffers into a composite value
Step: String.Concat
  {B:FirstName} + " " + {B:LastName} → {B:FullName}

// Compare and branch on buffer numeric value
Condition: {B:CartTotal} > 100
  [If true]  ApplyDiscountCode
💡 Tip: These arithmetic/string steering modules live alongside your regular Module attributes in TCM's built-in technical modules — you don't need a special TBox to use them; they're part of core Tosca functionality available in any Test Case.

ADVANCED8. Combining Buffers, Conditions, and Loops

Real-world steering usually combines all three pillars in a single Test Case. A typical pattern: poll a status field in a While loop, capture it into a Buffer each iteration, and branch with a Condition once the loop exits.

Buffer: AttemptCount = 0
Buffer: OrderStatus  = ""

While: {B:OrderStatus} != "Shipped" AND {B:AttemptCount} < 15
  Step: OrderStatusPage.StatusLabel
         ActionMode = Output → {B:OrderStatus}
  Step: Math.Add {B:AttemptCount} + 1 → {B:AttemptCount}
  Step: Wait 5 seconds

Condition: {B:OrderStatus} = "Shipped"
  [If true]  Step: NotifyEmail.SubjectLine [Verify] = "Your order has shipped"
  [If false] Step: [Recovery Action] = flag as timeout / Failed
Reading this pattern: the loop polls up to 15 times, waiting 5 seconds between checks, for the order to reach "Shipped" status. Once the loop exits (either condition satisfied), a Condition step verifies the outcome and reports accordingly — a fully dynamic, code-free polling-and-assertion pattern.

INTERMEDIATE9. Common Pitfalls

  • Unbounded While loops: forgetting a maximum-attempt guard on a condition that may never become true.
  • Overusing loops for simple repetition: using a While loop when a fixed-count For loop would be clearer and safer.
  • Deep, hard-to-follow nested Conditions: excessive branching inside a single Test Case makes it as hard to maintain as a tangled script — consider splitting into embedded Test Cases per branch.
  • Forgetting to initialise a Buffer before a loop: referencing {B:AttemptCount} in a condition before any step has set it can produce unexpected comparison behaviour.

BEGINNER10. Best Practices

1. Always Bound Your Loops

Every While loop should have a maximum iteration/timeout safeguard, even when the "expected" case resolves quickly.

2. Name Buffers for What They Hold, Not How They're Used

// Good
{B:OrderID}, {B:AuthToken}, {B:AttemptCount}

// Avoid
{B:Temp1}, {B:X}, {B:Value2}

3. Prefer For Loops When the Count Is Known

Reserve While loops for genuinely condition-driven repetition (polling, retries).

4. Keep Conditions Shallow

If branching logic grows deep, extract each branch into its own embedded Test Case rather than nesting many Conditions in one flat sequence.

5. Log Buffer Values During Debugging

When a steering-heavy Test Case behaves unexpectedly, temporarily add Verify steps on key buffers to inspect their value at each stage.

📋 Quick Reference Summary

Concept Key Points
Buffer Runtime-captured value, referenced as {B:Name}; set via ActionMode = Output.
Condition Evaluates a buffer/parameter to branch execution — Tosca's if/else.
While loop Repeats steps while a condition holds; always needs a bounded exit.
For loop Repeats steps a fixed number of times.
Buffer arithmetic Math/String steering modules manipulate buffer values (increment, concat).
Combined pattern Poll in a While loop, capture with Output, branch with a Condition on exit.
