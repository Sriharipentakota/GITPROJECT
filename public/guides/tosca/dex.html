BEGINNER1. What Is DEX?

Definition

DEX (Distributed Execution) is Tosca's parallel test execution infrastructure. Instead of running an entire Execution List serially on the tester's own machine, DEX distributes Test Cases across a pool of execution agents managed by a central DEX Server, cutting overall wall-clock run time by running multiple tests simultaneously.

Real-world analogy: DEX is like a food delivery dispatch centre. One central dispatcher (DEX Server) receives a large order (Execution List) and routes individual items to the nearest available delivery driver (agent). All drivers work in parallel; the dispatcher collects all delivery confirmations and sends one combined bill (results report) to the restaurant.

BEGINNER2. DEX Architecture: Server and Agents

// DEX architecture
DEX Server ← central orchestrator
  └── Agent Pool
      ├── Agent 1 (Windows / Chrome)
      ├── Agent 2 (Windows / Firefox)
      ├── Agent 3 (Linux / headless)
      └── Agent 4 (Mac / Safari)

A DEX agent is simply a machine with Tosca installed and the DEX Agent service running. It registers itself with the DEX Server and waits idle for work. When a run is triggered, the DEX Server slices the Execution List into units of work and dispatches each unit to an available agent; each agent runs its assigned slice independently and reports results back to the central repository.

Component Role
DEX Server Central orchestrator: receives the run request, slices work, dispatches to agents, aggregates results
DEX Agent A registered machine that executes an assigned slice of the Execution List
Common Repository Where all agents ultimately write their results, so the run appears as one unified report

BEGINNER3. Configuring an Execution List for DEX

// Configuring an Execution List for DEX
ExecutionList → Properties
  ExecutionMode: Distributed
  DEX Agent:     AgentGroup_QA
  Parallel:      4 (run 4 test cases simultaneously)
Step by step: 
1. Open the Execution List's Properties
2. Set ExecutionMode = Distributed
3. Choose the target agent group (a named pool of registered agents)
4. Set the desired parallelism (how many test cases run concurrently)
5. Run → the DEX Server takes over dispatching automatically

INTERMEDIATE4. Parallel Execution: The Time Savings

// Without DEX: 100 test cases × 30s each = 50 minutes (serial)

// With DEX (4 agents):
Agent 1: TC001–TC025  → 12.5 minutes
Agent 2: TC026–TC050  → 12.5 minutes
Agent 3: TC051–TC075  → 12.5 minutes
Agent 4: TC076–TC100  → 12.5 minutes
Total wall-clock time: ~13 minutes (4× faster)
Agent Count Theoretical Speedup Realistic Speedup
1 (baseline) 1x 1x
4 4x ~3–3.5x (dispatch/aggregation overhead)
10 10x ~7–8x, more if data contention is well managed
💡 Tip: Realistic speedup is always somewhat below the theoretical linear number due to dispatch overhead, agent startup time, and any shared-resource contention (see Section 8). Measure actual speedup on your own suite rather than assuming perfect linear scaling.

INTERMEDIATE5. Agent Tags and Requirements-Based Routing

Not every Test Case can run on any agent — a SAP transaction test needs an agent with SAP GUI installed; a Safari test needs a Mac agent. DEX solves this with tags on agents and matching requirements declared on Test Cases.

// Agents can have tags/requirements
Agent 1: Tags = ["Windows", "Chrome", "English"]
Agent 2: Tags = ["Windows", "SAP", "German"]
Agent 3: Tags = ["Mac", "Safari", "iOS"]

// Test cases declare required agent tags
TC_SAP_Invoice: RequiresAgent = ["SAP", "German"]
→ DEX routes it only to Agent 2

TC_Safari_Checkout: RequiresAgent = ["Mac", "Safari"]
→ DEX routes it only to Agent 3
⚠️ Common Pitfall: A Test Case with overly specific or conflicting tag requirements that no registered agent satisfies will sit unassigned indefinitely (or error out) during a DEX run. Audit your agent pool's tags against your Test Cases' requirements before scaling up parallelism.

ADVANCED6. Tosca Cloud (SaaS DEX)

Tosca Cloud is a cloud-hosted pool of DEX agents that can be scaled on demand, without the team managing its own physical or virtual agent machines. It integrates directly into the TCM Execution List through a cloud agent configuration, functioning as just another agent group from the Execution List's point of view.

Aspect Self-Hosted DEX Agents Tosca Cloud
Infrastructure ownership Your team provisions and maintains VMs Tricentis manages the agent pool
Scaling Manual — add more VMs as needed On-demand, elastic scaling
Best for Environments requiring specific internal network access, specialised software (SAP, mainframe emulators) Standard web/API testing needing burst capacity without capital investment

ADVANCED7. Triggering a DEX Run from CI

ToscaCI (covered in the CI/CD Integration guide) can trigger a Distributed Execution run directly from a build pipeline, letting a CI stage benefit from parallelism without any manual TCM interaction.

// Starting a DEX run from CI
ToscaCI.exe run
  --executionEnvironment "DEX"
  --agentGroup "QA_Agents"
  --executionList "Full_Regression"
Typical pipeline shape: Deploy → ToscaCI triggers a DEX-distributed Full_Regression run across 8 QA agents → pipeline waits on the aggregated exit code → publishes the merged JUnit XML result, all without the pipeline needing to know or care how many physical agents were involved.

INTERMEDIATE8. Test Data Considerations Under Parallelism

Introducing parallel execution surfaces a class of problems that simply don't exist in serial runs: two agents might simultaneously grab the same "available" test user, order record, or shared resource, causing intermittent, hard-to-reproduce failures.

// Problem: two agents both pick "the next available test user" from a shared Excel row
Agent 1: uses TestUser_003 for TC010
Agent 2: uses TestUser_003 for TC045   ← collision!
→ Both tests fail unpredictably depending on execution order

// Solution: partition data per agent, or use TDM Server reservation
Agent 1: assigned TestUser_001–010
Agent 2: assigned TestUser_011–020
// or: TDM Server reserves+releases records automatically
💡 Tip: See the Test Data Management guide's coverage of the Tricentis TDM Server's reservation feature — this is precisely the problem it's designed to solve at scale.

INTERMEDIATE9. Common Pitfalls

  • Assuming linear speedup: planning capacity around theoretical Nx speedup instead of the realistic, somewhat lower figure due to overhead.
  • Untagged or mis-tagged agents: Test Cases silently failing to get scheduled because no agent in the pool matches their declared requirements.
  • Shared mutable test data: data collisions between agents that don't manifest until parallelism is introduced, producing "it worked yesterday" flakiness.
  • Over-provisioning parallelism beyond data/environment capacity: running more parallel Test Cases than the target environment (e.g. a shared QA database) can actually handle without contention.

BEGINNER10. Best Practices

1. Tag Agents and Test Cases Deliberately

Keep tag vocabulary consistent (OS, browser, language, specialised software) and audit for gaps before scaling.

2. Partition or Reserve Shared Test Data

Design data sources so concurrent agents cannot collide on the same record.

3. Start Small, Measure, Scale

Run with 2 agents → measure actual speedup
Run with 4 agents → measure again
// Only scale further once you confirm the environment
// and data layer can support the added concurrency

4. Separate Smoke (Fast, Low Parallelism) from Full Regression (High Parallelism)

A quick smoke gate may not even need DEX; save the parallel agent pool for the larger regression run where the time savings matter most.

5. Monitor Agent Health

Regularly confirm registered agents are online and correctly tagged — stale or crashed agents silently reduce your effective parallelism.
