BEGINNER1. What Is the Mobile Engine?

Definition

Tosca's Mobile Engine enables automated testing of native iOS and Android apps, as well as mobile-optimised web apps in mobile browsers. It uses the exact same scan-model-and-assemble approach as desktop web testing — scan the app once to build a Module tree, then build Test Cases against it exactly as you would for a web application.

Real-world analogy: Mobile testing in Tosca is like having the same driving test examiner assess candidates on different car models (iOS, Android). The examiner follows the same checklist regardless of the car — check mirrors, signal, brake — and adapts naturally to each car's controls. The test script (checklist) doesn't change; only the vehicle (device) does.

Under the Hood: XCUITest and UIAutomator2

For iOS, Tosca communicates through Apple's XCUITest framework; for Android, it uses UIAutomator2/Appium. Testers don't need to interact with these frameworks directly — Tosca abstracts them behind the same Module/TestStep model used everywhere else in the platform.

BEGINNER2. Device Configuration

Every mobile Test Case requires a Device Configuration, specifying which physical device or emulator to target, what OS version, and which app to launch.

// Device Configuration (set in TCM → Modules → Mobile)
DeviceConfig: iPhone15_iOS17
  Platform:      iOS
  DeviceName:    iPhone 15
  OSVersion:     17.0
  AppBundleID:   com.example.myapp
  LaunchMode:    App (native) | Browser (mobile web)
Property Meaning
Platform iOS or Android
DeviceName / OSVersion Which physical/emulated device profile to target
AppBundleID The app package/bundle identifier to launch (native apps only)
LaunchMode Whether to launch the native app or a mobile browser session
💡 Tip: A Device Configuration is attached to the Execution List, not baked into individual Test Cases — this is what makes running the same Test Case against multiple devices simply a matter of swapping which configuration is attached.

BEGINNER3. Scanning a Mobile App

// Scanning a mobile app
1. Connect device / start emulator
2. TCM → Scan → Choose Mobile Engine
3. Interact with app → TOSCA records controls
4. Controls become Module Attributes (same as web)
Step by step: 
1. Connect a physical device via USB, or start an emulator/simulator
2. Ensure the Mobile Engine Host machine can see the device
3. In TCM, right-click Modules → Scan Application → Mobile Engine
4. Tap through the app's screens; TOSCA highlights and records
   each recognised control just like TBox Web does for a browser
5. Rename attributes with business-friendly names as usual

INTERMEDIATE4. Gestures: Tap, Swipe, Pinch

Mobile interaction includes gesture types that have no direct desktop-web equivalent. Tosca's Mobile Engine supports these as built-in Test Step actions.

// Gestures in test steps
Swipe:  direction=Up, duration=500ms
Pinch:  scale=0.5
Tap:    coordinate-based or control-based
Gesture Typical Use
Tap Equivalent of a click; can target a recognised control or raw screen coordinates
Swipe Scrolling a list, dismissing a card, navigating a carousel
Pinch Zooming in/out on maps, images, or PDF viewers within the app

INTERMEDIATE5. Building a Mobile Test Case

Module: iOS_LoginScreen
  Attribute: UsernameField   [Input]   → tap + type
  Attribute: PasswordField   [Input]   → tap + type
  Attribute: SignInButton     [Input]   → tap
  Attribute: WelcomeText     [Verify]

TestCase: TC_Mobile_Login
  Step 1: iOS_LoginScreen.UsernameField = {P:MobileUser}
  Step 2: iOS_LoginScreen.PasswordField = {P:MobilePass}
  Step 3: iOS_LoginScreen.SignInButton  ← tap (no value)
  Step 4: iOS_LoginScreen.WelcomeText  [Verify] = "Hello!"

This should look immediately familiar — it is structurally identical to a web login Test Case. The Module Attribute's ActionMode (Input/Verify) and the Test Case's step ordering follow exactly the same rules as any other Tosca technology.

ADVANCED6. Native App vs Mobile Web Testing

Aspect Native App Mobile Web
Launch mechanism AppBundleID launches the installed app directly Mobile browser navigates to a URL
Underlying engine XCUITest (iOS) / UIAutomator2 (Android) TBox Web, same as desktop browser testing
Gestures available Full native gesture set (tap, swipe, pinch, native alerts) Standard web interactions plus touch-emulated gestures
Best for Dedicated iOS/Android apps distributed via app stores Responsive web apps also accessed via desktop browsers

ADVANCED7. Cross-Platform Matrices with DEX

A single logical scenario (e.g. "user can log in") often needs verification across several device/OS combinations. Rather than duplicating the Test Case per device, DEX's agent-routing (see the Distributed Execution guide) lets one Test Case run against multiple Device Configurations in parallel.

ExecutionList: Mobile_Regression
  Agent Requirements per TC:
    TC_Login:
      Run on Agent[iPhone15_iOS17]
      Run on Agent[Pixel7_Android13]
      Run on Agent[Galaxy_Android14]
  → 3 parallel runs, one per device
  → Results show per-device pass/fail
Why this matters: mobile fragmentation (many device/OS combinations) is one of the biggest testing challenges in mobile development. Reusing one Test Case definition across a device matrix via DEX avoids the maintenance nightmare of N duplicated Test Cases for N devices.

INTERMEDIATE8. Device Farms and Real Devices vs Emulators

Mobile test execution can target either emulators/simulators (software-simulated devices) or real physical devices connected to a Mobile Engine Host machine, or devices provisioned from a cloud device farm through Tosca Cloud/DEX.

Target Trade-off
Emulator/Simulator Fast, cheap, easy to scale — but may miss real hardware-specific bugs (camera, sensors, performance)
Real device (local) Authentic behaviour — but limited by physical device inventory and USB/host capacity
Cloud device farm Wide real-device coverage on demand — subject to cloud provider availability and cost

INTERMEDIATE9. Common Pitfalls

  • Relying solely on emulators: missing real-hardware issues (camera permissions, GPS, push notifications) that only manifest on physical devices.
  • Duplicating Test Cases per device instead of using DEX routing: multiplying maintenance effort unnecessarily.
  • Coordinate-based taps instead of control-based: raw coordinate taps break the moment screen resolution or layout changes; prefer targeting recognised Module Attributes.
  • Ignoring native OS dialogs: permission prompts (camera, location, notifications) that appear unpredictably on first launch, requiring a Recovery Scenario to handle gracefully.

BEGINNER10. Best Practices

1. Prefer Control-Based Interaction Over Raw Coordinates

Scan and reference actual Module Attributes rather than hard-coding screen coordinates for taps.

2. Build a Small Device Matrix, Not an Exhaustive One

// Good starting matrix
- Latest iOS + one common iPhone model
- Latest Android + one common mid-range device
- Previous major OS version of each, if support requires it

3. Handle OS Permission Dialogs with Recovery Scenarios

Attach a Recovery Scenario at the Execution List level that dismisses common permission prompts (see the Recovery Scenarios guide).

4. Use DEX to Multiply Coverage, Not Test Case Count

Write one Test Case per scenario; let DEX agent routing run it against your device matrix.

5. Mix Emulators for Speed and Real Devices for Confidence

Use emulators for fast day-to-day feedback; schedule periodic real-device runs (or a cloud device farm) before major releases.
