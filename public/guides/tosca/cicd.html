BEGINNER1. What Is ToscaCI?

Definition

ToscaCI is a command-line tool that triggers Tosca Execution Lists from a build server without ever opening TCM's graphical interface. It is the bridge between Tosca's GUI-driven test authoring and the fully automated, headless world of CI/CD pipelines.

Real-world analogy: ToscaCI in a pipeline is like a quality inspector on a factory assembly line. After each assembly stage (deploy), the inspector runs automated checks (Tosca tests). If the checks pass, the product moves to the next station. If they fail, the line halts and the fault is logged — defects never reach the customer.

Jenkins, Azure DevOps, GitHub Actions, and GitLab CI all use ToscaCI the same way: as a command-line step invoked after deployment, blocking (or informing) the rest of the pipeline based on the test outcome.

BEGINNER2. ToscaCI Command-Line Basics

// ToscaCI basic run
ToscaCI.exe run
  --workspace "http://toscaserver:8080/Tricentis/Tosca"
  --executionList "Smoke_Tests"
  --resultdir "C:\CI\Results"
  --timeout 600
Argument Purpose
--workspace The Tosca repository/workspace connection to use
--executionList Which Execution List to run
--resultdir Where to write result files (JUnit XML, logs, screenshots)
--timeout Maximum seconds to wait before considering the run stuck

BEGINNER3. Exit Codes and Pipeline Gating

ToscaCI communicates the outcome of a run back to the CI server through its process exit code — the same mechanism every command-line tool uses to signal success or failure to a shell or pipeline runner.

// Exit codes
0  → All tests passed
1  → One or more tests failed
2  → Execution error (agent unavailable, config issue)
💡 Tip: Every mainstream CI system treats a non-zero exit code from a pipeline step as "this stage failed," automatically halting or flagging the pipeline — no custom parsing logic is needed just to gate the build on Tosca's outcome.

INTERMEDIATE4. Jenkins Pipeline Integration

// Jenkins pipeline (Declarative)
stage('TOSCA Smoke') {
  steps {
    bat 'ToscaCI.exe run --executionList "Smoke" --resultdir ".\\results"'
    junit '.\\results\\ExecutionResults.xml'
  }
  post { failure { archiveArtifacts '.\\results\\*.png' } }
}

This declarative stage runs the smoke Execution List, publishes the JUnit-format results natively into Jenkins' Test Results UI, and — only on failure — archives any captured screenshots as build artifacts for investigation.

INTERMEDIATE5. Azure DevOps Pipeline Integration

# azure-pipelines.yml
stages:
- stage: Deploy
  jobs:
  - job: DeployToQA
    steps:
    - script: deploy.sh --env qa

- stage: SmokeTest
  dependsOn: Deploy
  jobs:
  - job: ToscaSmoke
    steps:
    - task: CmdLine@2
      inputs:
        script: |
          ToscaCI.exe run \
            --executionList "Smoke_QA" \
            --resultdir "$(Build.ArtifactStagingDirectory)"
    - task: PublishTestResults@2
      inputs:
        testResultsFormat: JUnit
        testResultsFiles: '**\ExecutionResults.xml'

Here the SmokeTest stage depends on Deploy completing first, and the built-in PublishTestResults task consumes ToscaCI's JUnit output natively — the same pattern used for any other test framework in Azure DevOps.

INTERMEDIATE6. GitHub Actions Integration

# .github/workflows/tosca.yml
name: TOSCA Regression
on: [push]
jobs:
  tosca:
    runs-on: windows-latest
    steps:
      - name: Run TOSCA via DEX Cloud
        run: |
          ToscaCI.exe run \
            --executionEnvironment "Cloud" \
            --executionList "Full_Regression" \
            --resultdir "${{ github.workspace }}/results"
      - name: Publish results
        uses: dorny/test-reporter@v1
        with:
          name: TOSCA Results
          path: results/ExecutionResults.xml
          reporter: java-junit
Note the DEX integration: combining --executionEnvironment "Cloud" with ToscaCI lets a GitHub Actions runner trigger a full parallel regression on Tosca Cloud agents on every push, without the CI runner itself needing to host any test execution capability — see the Distributed Execution (DEX) guide for the agent-side details.

ADVANCED7. The Smoke-Gate-Then-Regression Pattern

A common enterprise pattern chains two Tosca stages with different purposes: a fast smoke gate that blocks obviously broken deployments quickly, followed by a slower full regression that runs only if the smoke gate passes.

Deploy → Smoke TOSCA run (gate) → Full Regression TOSCA run → Publish report
Stage Duration Purpose
Smoke gate Minutes Catch catastrophic deployment failures fast, before investing in a long run
Full regression Tens of minutes to hours Comprehensive feature coverage, typically parallelised via DEX
Why gate first: the smoke gate runs in minutes and blocks a bad deployment before spending 30+ minutes on the full suite — avoiding wasted compute and faster feedback for the team when something is fundamentally broken.

ADVANCED8. Artifacts, Logs, and Failure Diagnostics in CI

A CI-triggered Tosca run should leave behind enough evidence for someone to diagnose a failure without re-running the pipeline. This typically means archiving three categories of output as pipeline artifacts:

Artifact Type Purpose
JUnit XML (ExecutionResults.xml) Machine-readable pass/fail summary consumed by the CI's native test reporting UI
Screenshots Visual evidence of the application state at the moment of failure
Tosca execution logs Full step-level detail for deep debugging beyond what fits in the JUnit summary
⚠️ Common Pitfall: Publishing only the JUnit summary and discarding screenshots/logs after the pipeline run means a failure investigated a day later has no visual evidence — the team is stuck re-running the whole regression just to see what actually happened.

INTERMEDIATE9. Common Pitfalls

  • No smoke gate before full regression: running a 2-hour regression against a deployment that's fundamentally broken, wasting compute and delaying feedback.
  • Discarding evidence on success only: archiving screenshots/logs conditionally in a way that also accidentally discards them for genuine flaky failures.
  • Hard-coding environment details in the ToscaCI call: instead of using pipeline variables/parameters, making the same script unusable across QA, Staging, and Production pipelines.
  • Ignoring exit code 2 (execution error): treating it the same as exit code 1 (test failures) when it actually signals an infrastructure/agent problem needing different triage.

BEGINNER10. Best Practices

1. Always Gate with a Fast Smoke Suite First

Reserve full regression for after a smoke gate confirms the deployment is fundamentally healthy.

2. Publish JUnit XML Natively

junit '.\results\ExecutionResults.xml'
// or PublishTestResults@2 / test-reporter@v1
// — use your CI's built-in JUnit support, don't build custom parsing

3. Archive Screenshots and Logs on Failure

Make failure evidence available without requiring a pipeline re-run to reproduce.

4. Parameterise Environment and Execution List by Pipeline Stage

Use pipeline variables for --workspace, --executionList, and PCD selection rather than hard-coding a single environment into the script.

5. Distinguish Exit Code 1 from Exit Code 2

Route test failures (1) to the QA team's triage process, and execution errors (2) to the automation/infrastructure team — they need different responses.
