BEGINNER1. What is a Closure?

A closure is a function that remembers the variables from the scope it was created in, even after that outer scope has finished executing. Closures happen automatically any time you write a function inside another function.

Real-world analogy: A closure is like a backpack you take when leaving a room. When the outer function finishes running (you leave the room), it's gone — but the inner function took a backpack with whatever variables it needed, and still has access to them. 
function outer() {
    const message = "Hello from outer";

    function inner() {
        console.log(message); // inner can see outer's variable
    }

    return inner;
}

const myFn = outer(); // outer() has already finished running
myFn(); // "Hello from outer" — message is STILL accessible!

BEGINNER2. How Closures Form

Every function in JavaScript forms a closure over its surrounding (lexical) scope — it's not something you opt into, it just happens as a natural consequence of how scoping works.

function makeGreeter(greeting) {
    // 'greeting' lives in makeGreeter's scope
    return function(name) {
        // this inner function "closes over" greeting
        return `${greeting}, ${name}!`;
    };
}

const sayHello = makeGreeter("Hello");
const sayHi = makeGreeter("Hi");

console.log(sayHello("Alice")); // "Hello, Alice!"
console.log(sayHi("Bob"));      // "Hi, Bob!"
// Each returned function remembers its OWN 'greeting' from when it was created
💡 Tip: The closure captures the VARIABLE, not just a snapshot of its value at creation time. If the outer variable changes later, the closure sees the updated value (see Section 6).

INTERMEDIATE3. Practical Use: Private State

Closures are the main way JavaScript achieves "private" variables — data that can only be read or changed through specific functions, not accessed directly from the outside.

function createBankAccount(initialBalance) {
    let balance = initialBalance; // truly private — no way to reach it directly

    return {
        deposit(amount) {
            balance += amount;
            return balance;
        },
        withdraw(amount) {
            if (amount > balance) return "Insufficient funds";
            balance -= amount;
            return balance;
        },
        getBalance() {
            return balance;
        }
    };
}

const account = createBankAccount(1000);
console.log(account.deposit(500));   // 1500
console.log(account.withdraw(200));  // 1300
console.log(account.balance);        // undefined — cannot access directly!

INTERMEDIATE4. Factory Functions

A factory function returns a new closure each time it's called. Each call produces completely INDEPENDENT state — calling the factory twice does not share variables between the two results.

function makeCounter() {
    let count = 0;
    return {
        increment() { return ++count; },
        reset() { count = 0; }
    };
}

const counterA = makeCounter();
const counterB = makeCounter();

counterA.increment(); // 1
counterA.increment(); // 2
counterB.increment(); // 1 — completely independent from counterA!

console.log(counterA.increment()); // 3
console.log(counterB.increment()); // 2
Independent closures (separate calls): 
const add5 = makeAdder(5);
const add10 = makeAdder(10);
// Each has its own private 'n'
Shared closure (same call, multiple functions): 
const acc = createBankAccount(0);
acc.deposit(100);
acc.withdraw(30);
// Both methods share the SAME 'balance'

ADVANCED5. The Module Pattern

Combining an IIFE (Immediately Invoked Function Expression) with a closure produces the classic module pattern — a way to expose a small public API while hiding implementation details, predating ES modules.

const ShoppingCart = (function() {
    let items = []; // private — inaccessible from outside this IIFE

    function calculateTotal() { // private helper function
        return items.reduce((sum, item) => sum + item.price, 0);
    }

    return { // public API — only these are exposed
        addItem(item) {
            items.push(item);
        },
        getTotal() {
            return calculateTotal();
        },
        getItemCount() {
            return items.length;
        }
    };
})();

ShoppingCart.addItem({ name: "Book", price: 15 });
ShoppingCart.addItem({ name: "Pen", price: 2 });
console.log(ShoppingCart.getTotal());      // 17
console.log(ShoppingCart.getItemCount());  // 2
// console.log(ShoppingCart.items);        // undefined — fully private

ADVANCED6. Closures Capture by Reference

A closure doesn't take a snapshot of a variable's value at the moment it's created — it keeps a live REFERENCE to the variable itself. If the outer variable changes afterward, every closure over it sees the new value.

function createLogger() {
    let logCount = 0;

    function log(message) {
        logCount++;
        console.log(`[${logCount}] ${message}`);
    }

    function getCount() {
        return logCount; // reads the SAME logCount that log() updates
    }

    return { log, getCount };
}

const logger = createLogger();
logger.log("first");  // "[1] first"
logger.log("second"); // "[2] second"
console.log(logger.getCount()); // 2 — sees the live, updated value

ADVANCED7. The Classic Loop Bug

The most famous closure gotcha: using var inside a loop when creating callbacks. Because var is function-scoped, all the closures created in the loop share the exact same variable.

// ❌ BUG: every callback shares one function-scoped 'i'
const buttons = [];
for (var i = 0; i < 3; i++) {
    buttons.push(function() {
        console.log("Button", i);
    });
}
buttons[0](); // "Button 3" (not 0!)
buttons[1](); // "Button 3" (not 1!)
buttons[2](); // "Button 3" (not 2!)
// By the time any callback runs, the loop has finished and i is 3 for ALL of them

// ✅ FIX 1: use let — creates a NEW binding for each iteration
const fixed = [];
for (let i = 0; i < 3; i++) {
    fixed.push(function() {
        console.log("Button", i);
    });
}
fixed[0](); // "Button 0"
fixed[1](); // "Button 1"
fixed[2](); // "Button 2"

// ✅ FIX 2 (pre-ES6): IIFE to capture the current value each iteration
const iifeFixed = [];
for (var j = 0; j < 3; j++) {
    iifeFixed.push((function(capturedJ) {
        return function() { console.log("Button", capturedJ); };
    })(j));
}
iifeFixed[0](); // "Button 0"

ADVANCED8. Memoization with Closures

Memoization caches the results of expensive function calls, using a closure to hold the cache between calls.

function memoize(fn) {
    const cache = new Map(); // private cache, held via closure

    return function(...args) {
        const key = JSON.stringify(args);
        if (cache.has(key)) {
            console.log("Cache hit for", key);
            return cache.get(key);
        }
        const result = fn(...args);
        cache.set(key, result);
        return result;
    };
}

function slowSquare(n) {
    console.log("Computing...");
    return n * n;
}

const fastSquare = memoize(slowSquare);
console.log(fastSquare(5)); // "Computing..." then 25
console.log(fastSquare(5)); // "Cache hit for [5]" then 25 — no recomputation!

INTERMEDIATE9. Common Pitfalls

1. Memory Retention

function attachHandler(largeData) {
    // If the returned function is kept around forever (e.g. a global event
    // listener), 'largeData' can never be garbage-collected, even if unused.
    return function handleClick() {
        console.log("clicked");
    };
}
// Only close over what you actually need to avoid unnecessary retention

2. Expecting a Snapshot Instead of a Live Reference

function delayedLogs() {
    let value = "initial";
    setTimeout(() => console.log(value), 100); // captures the VARIABLE, not "initial"
    value = "changed";
}
delayedLogs(); // logs "changed" after 100ms, not "initial"!

3. Overusing Closures Where a Class Would Be Clearer

// For simple cases, closures are great. But for many methods and
// inheritance, a class is often more readable than deeply nested closures:
class BankAccount {
    #balance; // truly private field (modern alternative to closures)
    constructor(initial) { this.#balance = initial; }
    deposit(amount) { this.#balance += amount; return this.#balance; }
}

INTERMEDIATE10. Best Practices

1. Use Closures for Genuine Private State

// ✅ Good use case — encapsulation without exposing internals
function createCounter() {
    let count = 0;
    return { increment: () => ++count, get: () => count };
}

2. Prefer let Over var in Loops That Create Closures

// ✅ Avoids the classic loop bug entirely
for (let i = 0; i < items.length; i++) {
    setTimeout(() => console.log(items[i]), 100);
}

3. Don't Close Over More Than You Need

// ✅ Only keep what's actually used alive
function makeHandler(id) {
    return () => console.log(id); // just holds 'id', not a giant surrounding object
}

4. Name Returned Functions for Easier Debugging

// ✅ Named function expression shows up clearly in stack traces
function createValidator(rules) {
    return function validate(input) {
        return rules.every(rule => rule(input));
    };
}

Concept Key Points
Closure A function plus the outer variables it remembers, even after the outer function returns.
Private state Closures are JavaScript's classic mechanism for encapsulation before private class fields.
Factory functions Each call creates an independent closure with its own private variables.
