BEGINNER1. Why Handle Errors?

Error handling lets your program recover gracefully from problems instead of crashing outright — a failed network request shouldn't take down your entire application.

Real-world analogy: Error handling is like a circus safety net. The try block is the acrobat's risky performance. The catch block is the net — if the performer falls, the net catches them and the show continues instead of ending in disaster. 
// Without error handling, an uncaught error stops execution entirely
JSON.parse("not valid json"); // throws SyntaxError — script halts here!
console.log("This line never runs");

// With error handling, the program keeps going
try {
    JSON.parse("not valid json");
} catch (err) {
    console.log("Failed to parse, using default instead");
}
console.log("This line DOES run");

BEGINNER2. try / catch / finally

function divide(a, b) {
    try {
        if (b === 0) {
            throw new Error("Division by zero");
        }
        return a / b;
    } catch (err) {
        console.log("Caught:", err.message);
        return null;
    } finally {
        console.log("divide() finished"); // ALWAYS runs, error or not
    }
}

console.log(divide(10, 2));  // logs "divide() finished", returns 5
console.log(divide(10, 0));  // logs "Caught: Division by zero", "divide() finished", returns null
💡 Tip: finally is ideal for cleanup work that must happen regardless of outcome — closing a file handle, hiding a loading spinner, releasing a lock, or logging that an operation completed.

finally Runs Even After a return

function test() {
    try {
        return "from try";
    } finally {
        console.log("finally still runs, even though try already returned!");
    }
}
console.log(test());
// Output: "finally still runs..." THEN "from try"

BEGINNER3. The Error Object

Every Error object carries three key properties that help you diagnose what went wrong.

try {
    null.someMethod(); // will throw a TypeError
} catch (err) {
    console.log(err.name);    // "TypeError"
    console.log(err.message); // "Cannot read properties of null (reading 'someMethod')"
    console.log(err.stack);   // the full call stack trace, useful for debugging
}
Property Description
.nameThe error type, e.g. "TypeError", "RangeError"
.messageHuman-readable description of what went wrong
.stackThe call stack at the moment the error was created (non-standard but universally supported)

INTERMEDIATE4. Built-In Error Types

Error Type When It Happens Example
TypeError Wrong type used for an operation null.toString()
ReferenceError Using an undeclared variable console.log(notDefined)
RangeError Value outside an allowed range new Array(-1)
SyntaxError Invalid code structure — usually caught at parse time JSON.parse("{bad}")
URIError Malformed URI passed to a URI function decodeURIComponent("%") 
try {
    decodeURIComponent("%");
} catch (err) {
    console.log(err instanceof URIError); // true
}

try {
    let x = notDeclaredAnywhere;
} catch (err) {
    console.log(err instanceof ReferenceError); // true
}

INTERMEDIATE5. Throwing Your Own Errors

Use throw to signal that something has gone wrong in YOUR code, not just when a built-in operation fails. You can throw any value, but throwing an Error object is best practice — it automatically captures a stack trace.

function withdraw(balance, amount) {
    if (amount > balance) {
        throw new Error("Insufficient funds");
    }
    return balance - amount;
}

try {
    withdraw(100, 500);
} catch (err) {
    console.log(err.message); // "Insufficient funds"
}

// You CAN throw a plain string or object, but you lose .stack and consistent shape
// throw "just a string";      // ❌ works, but discouraged
// throw { code: 500 };        // ❌ also works, also discouraged
throw new Error("Prefer this — always an Error object"); // ✅

ADVANCED6. Custom Error Classes

Extend the built-in Error class to create your OWN error types — this lets calling code distinguish between different failure categories using instanceof.

class ValidationError extends Error {
    constructor(field, message) {
        super(message);           // sets this.message
        this.name = "ValidationError"; // otherwise it would just say "Error"
        this.field = field;       // custom extra data
    }
}

class NotFoundError extends Error {
    constructor(resource) {
        super(`${resource} not found`);
        this.name = "NotFoundError";
    }
}

function validateAge(age) {
    if (typeof age !== "number") {
        throw new TypeError("age must be a number");
    }
    if (age < 0) {
        throw new ValidationError("age", "Age cannot be negative");
    }
}

try {
    validateAge(-5);
} catch (err) {
    if (err instanceof ValidationError) {
        console.log(`Validation failed on ${err.field}: ${err.message}`);
    } else if (err instanceof TypeError) {
        console.log("Type problem:", err.message);
    } else {
        throw err; // unknown error type — let it propagate
    }
}

ADVANCED7. Re-throwing Errors

Sometimes a catch block can only handle SOME kinds of errors. For anything else, re-throw it (throw err;) so it can bubble up to a caller better equipped to deal with it.

function loadConfig(json) {
    try {
        return JSON.parse(json);
    } catch (err) {
        if (err instanceof SyntaxError) {
            console.log("Invalid config format, using defaults");
            return {};
        }
        throw err; // unexpected error type — don't swallow it silently
    }
}

// A caller further up can add its OWN handling
function startApp() {
    try {
        const config = loadConfig(rawInput);
        console.log(config);
    } catch (err) {
        console.error("Fatal startup error:", err);
        process.exit?.(1); // (Node.js example — exits the process)
    }
}
⚠️ Never Silently Swallow Errors: An empty catch {} block hides bugs and makes debugging painful — you lose all visibility into what actually went wrong. At minimum, log the error even if you can't fully handle it.

ADVANCED8. Error Handling in Async Code

async/await — Use try/catch

async function fetchUser(id) {
    try {
        const res = await fetch(`/api/users/${id}`);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return await res.json();
    } catch (err) {
        console.error("fetchUser failed:", err.message);
        return null;
    } finally {
        hideSpinner();
    }
}
function hideSpinner() { console.log("spinner hidden"); }

Promise Chains — Use .catch()

fetch("/api/data")
    .then(res => res.json())
    .catch(err => console.error("Request failed:", err));
⚠️ try/catch Does NOT Catch Async Callback Errors: Wrapping a setTimeout or event-listener callback in try/catch does NOT catch errors thrown INSIDE that callback — the callback runs later, outside the original try block's execution. 
try {
    setTimeout(() => {
        throw new Error("This escapes the try/catch!");
    }, 100);
} catch (err) {
    console.log("This will NEVER run"); // the throw happens too late, in a new turn
}
// The error becomes an uncaught exception instead —
// put the try/catch INSIDE the callback itself:
setTimeout(() => {
    try {
        throw new Error("Now this IS caught");
    } catch (err) {
        console.log("Caught:", err.message);
    }
}, 100);

INTERMEDIATE9. Common Pitfalls

1. Catching Too Broadly

// ❌ Silently hides ALL errors, including bugs you'd want to know about
try {
    riskyOperation();
} catch (err) {
    // nothing here — errors vanish without a trace
}

// ✅ At minimum, log it
try {
    riskyOperation();
} catch (err) {
    console.error("riskyOperation failed:", err);
}

2. Forgetting try/catch Around await

// ❌ An unhandled rejection here can crash a Node process or show a browser warning
async function load() {
    const data = await fetchData(); // no try/catch — rejection propagates uncaught
}

// ✅ Always guard risky awaits
async function loadSafe() {
    try {
        const data = await fetchData();
    } catch (err) {
        console.error(err);
    }
}

3. Throwing Non-Error Values

// ❌ Loses stack trace and a consistent shape for catch blocks to rely on
throw "Something broke";

// ✅ Always throw real Error objects (or subclasses)
throw new Error("Something broke");

4. Comparing Error Types with .name Instead of instanceof

// ❌ Fragile — string comparison, easy to typo
if (err.name === "TypeError") { }

// ✅ Reliable — works correctly with inheritance too
if (err instanceof TypeError) { }

INTERMEDIATE10. Best Practices

1. Always Throw Error Objects, Never Plain Values

// ✅ Preserves stack trace and consistent structure
throw new Error("Invalid input");

2. Create Custom Error Classes for Domain-Specific Failures

// ✅ Callers can distinguish failure types cleanly
class PaymentError extends Error {
    constructor(message) {
        super(message);
        this.name = "PaymentError";
    }
}

3. Use finally for Guaranteed Cleanup

// ✅ Runs whether the operation succeeds or fails
try {
    connection.open();
    doWork();
} finally {
    connection.close();
}

4. Re-throw Errors You Don't Know How to Handle

// ✅ Don't swallow unexpected error types
catch (err) {
    if (err instanceof ValidationError) return handleValidation(err);
    throw err;
}

5. Wrap Every await in try/catch (or Handle at a Higher Level)

// ✅ Predictable async failure handling
async function safeCall() {
    try {
        return await riskyAsyncOp();
    } catch (err) {
        return fallbackValue;
    }
}

📋 Quick Reference Summary

Concept Key Points
try/catch/finally Wrap risky code; catch handles errors; finally always runs for cleanup.
Error object .name, .message, .stack — inspect these to diagnose failures.
Built-in types TypeError, ReferenceError, RangeError, SyntaxError, URIError.
Custom errors Extend Error, call super(message), set this.name for clean instanceof checks.
Re-throwing Let unhandled error types bubble up rather than swallowing them silently.
Async errors Use try/catch with await, or .catch() on promise chains — not a try/catch around a callback registration.
