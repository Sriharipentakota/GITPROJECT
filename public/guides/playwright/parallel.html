BEGINNER1. Workers — Independent Test Processes

Playwright achieves parallelism using workers — independent Node.js processes, each with its own browser instance. Workers don't share memory, which means tests running in different workers can never accidentally interfere with each other's in-process state.

Why this matters for speed: a 10-minute serial test suite can compress to roughly 2 minutes on a 4-worker CI runner — the same total work spread across four independent "lanes" running simultaneously.

BEGINNER2. Default Behavior: Per-File Parallelism

By default, Playwright parallelizes at the file level: different spec files run concurrently across workers, but tests within the same file run serially, one after another, in a single worker.

tests/login.spec.ts    → Worker 1: test1 → test2 → test3
tests/checkout.spec.ts → Worker 2: test1 → test2 → test3
tests/search.spec.ts   → Worker 3: test1 → test2 → test3

INTERMEDIATE3. fullyParallel: true

Setting fullyParallel: true breaks the file-level grouping entirely — every individual test, regardless of which file it's in, gets its own worker slot and can run concurrently with any other test.

export default defineConfig({
  fullyParallel: true,   // every test in its own worker — fastest mode
});
⚠️ Common Pitfall: fullyParallel is only safe when tests have no shared state and don't depend on running in a particular order. A suite full of tests that secretly rely on running after one another will produce confusing, intermittent failures once this is enabled.

INTERMEDIATE4. Controlling Worker Count

// playwright.config.ts
export default defineConfig({
  workers: process.env.CI ? 4 : undefined, // fixed in CI, auto locally
});
npx playwright test --workers=8       // explicit count
npx playwright test --workers=50%     // half of available CPU cores

The default is half the number of logical CPU cores. Setting workers: 1 disables parallelism entirely — useful when debugging a flaky test that only fails under concurrent load.

INTERMEDIATE5. describe.parallel and describe.serial

Modifier Effect
test.describe.parallel() Opts a describe block into parallel execution within its file, even without fullyParallel
test.describe.serial() Forces tests to run in strict sequence, even when fullyParallel is globally enabled

Ordered Lifecycle Test

test.describe.serial('blog post lifecycle', () => {
  let postId: string;

  test('create post', async ({ page }) => {
    await page.goto('/admin/posts/new');
    await page.getByLabel('Title').fill('Hello World');
    await page.getByRole('button', { name: 'Publish' }).click();
    await page.waitForURL(/\/posts\/(\d+)/);
    postId = page.url().split('/').pop()!;
  });

  test('edit post', async ({ page }) => {
    await page.goto(`/admin/posts/${postId}/edit`);
    await page.getByLabel('Title').fill('Hello World (revised)');
    await page.getByRole('button', { name: 'Save' }).click();
  });

  test('delete post', async ({ page }) => {
    await page.goto(`/admin/posts/${postId}`);
    await page.getByRole('button', { name: 'Delete' }).click();
  });
});
💡 Tip: Reach for describe.serial sparingly — sharing state between tests (like postId above) couples them tightly, meaning a failure in "create post" cascades into "edit" and "delete" failing too, which can make root-causing a failure slower.

ADVANCED6. Worker-Scoped Fixtures for Expensive Setup

import { test as base } from '@playwright/test';

const test = base.extend({
  expensiveClient: [async ({}, use) => {
    const client = await createHeavyClient();
    await use(client);
    await client.close();
  }, { scope: 'worker' }],   // created once per worker, shared by every test in it
});

Because a worker persists across many tests, a worker-scoped fixture amortizes an expensive one-time cost (like establishing a database connection or authenticating a shared client) across every test that runs in that worker, instead of repeating it per test.

ADVANCED7. Avoiding Shared Mutable State

// ❌ BAD — shared module-level counter causes a race condition
let count = 0;
test('a', async () => { count++; });
test('b', async () => { count++; });

// ✅ GOOD — each test is self-contained, uses only page-local state
test('a', async ({ page }) => { /* uses only page-local state */ });
test('b', async ({ page }) => { /* uses only page-local state */ });
⚠️ Common Pitfall: Module-level variables (declared outside any test() call) are shared across every test in the same worker, but each worker has its own independent copy — so a counter that "seems to work" locally with one worker can produce wildly different, non-deterministic results once multiple workers run concurrently in CI.

ADVANCED8. Sharding Across CI Machines

For very large suites, sharding splits the entire test suite across multiple CI machines — a level of parallelism above workers, distributing work across separate hosts entirely.

# Machine 1
npx playwright test --shard=1/3 --reporter=blob
# Machine 2
npx playwright test --shard=2/3 --reporter=blob
# Machine 3
npx playwright test --shard=3/3 --reporter=blob

# After all shards finish, merge their blob reports into one HTML report
npx playwright merge-reports --reporter html ./blob-report

GitHub Actions Sharding Matrix

jobs:
  test:
    strategy:
      matrix:
        shardIndex: [1, 2, 3]
        shardTotal: [3]
    steps:
      - run: npx playwright test
               --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }}
               --reporter=blob
      - uses: actions/upload-artifact@v4
        with:
          name: blob-report-${{ matrix.shardIndex }}
          path: blob-report/

  merge-reports:
    needs: test
    steps:
      - uses: actions/download-artifact@v4
        with: { pattern: blob-report-*, merge-multiple: true }
      - run: npx playwright merge-reports --reporter html ./blob-report
Workers vs. sharding: workers parallelize within one machine's CPU cores; sharding parallelizes across separate machines entirely. Combine both — each shard machine still runs its subset of tests across multiple workers.

ADVANCED9. Common Pitfalls

⚠️ Pitfall 1 — Database collisions under parallelism: If two parallel tests both create a user with the same hardcoded email, one will fail with a "duplicate" error. Generate unique test data (e.g. with a UUID or timestamp suffix) so concurrently-running tests never collide.
⚠️ Pitfall 2 — Forgetting maxFailures for fast feedback: On a very large parallel suite, a systemic bug (like a broken deployment) can cause hundreds of unrelated failures before you notice. Setting maxFailures: 10 in the config stops the run early once a threshold of failures is reached, saving CI time and cost.
