BEGINNER1. What Is a Fixture?

A fixture is a named function that sets up a resource before a test runs and tears it down automatically afterward. Tests request the fixtures they need by destructuring them from the callback argument — Playwright only creates the fixtures a given test actually asks for, nothing more.

test('uses the page fixture', async ({ page }) => {
  await page.goto('/');
  // Playwright created `page` for you and will close it when this test ends
});
Why fixtures beat manual setup/teardown: setup and teardown code live in one place (the fixture definition) instead of being copy-pasted into every test's beforeEach/afterEach. Fixtures also compose — a fixture can depend on other fixtures, building a clean dependency graph.

BEGINNER2. Built-In Fixtures

Every test has access to these without any imports or configuration:

Fixture What it provides
page A ready-to-use browser tab (Page) inside an isolated context
context The BrowserContext that owns page
browser The shared Browser instance for the current worker
browserName String: 'chromium', 'firefox', or 'webkit'
request An APIRequestContext for making direct HTTP calls 
test('uses built-ins', async ({ page, context, browser, request, browserName }) => {
  console.log(browserName);          // 'chromium' | 'firefox' | 'webkit'
  await page.goto('/');
});

INTERMEDIATE3. Creating a Custom Fixture

Custom fixtures are created with test.extend(). The fixture function receives dependencies plus a special use callback: code before await use(value) is setup, the value is handed to the test at that point, and code after use() is teardown.

import { test as base } from '@playwright/test';

const test = base.extend<{ loggedInPage: Page }>({
  loggedInPage: async ({ page }, use) => {
    // Setup: log in
    await page.goto('/login');
    await page.getByLabel('Email').fill('user@example.com');
    await page.getByLabel('Password').fill('secret');
    await page.getByRole('button', { name: 'Sign in' }).click();
    await expect(page).toHaveURL('/dashboard');

    await use(page);   // ← the test runs here

    // Teardown: nothing needed; page closes automatically
  },
});

test('dashboard shows user name', async ({ loggedInPage: page }) => {
  await expect(page.getByTestId('user-name')).toContainText('user');
});
⚠️ Common Pitfall: You must import the extended test (usually re-exported from a shared fixtures file), not the base test from @playwright/test, in every spec file that needs the custom fixture. Importing the wrong one gives a confusing "fixture is not defined" error.

INTERMEDIATE4. Fixture Scope: test, worker, file

Scope Lifetime Good for
'test' (default) Fresh instance created and torn down for every test Anything test-specific — a page, a page object
'worker' One instance shared by every test in the same worker process Expensive setup: database connections, one-time seeding
'file' One instance shared by every test in a single spec file Setup that's expensive but not safe to share across files 
const test = base.extend<{}, { db: Database }>({
  db: [async ({}, use) => {
    const db = await Database.connect(process.env.DATABASE_URL);
    await use(db);
    await db.close();
  }, { scope: 'worker' }],
});

test('creates a user', async ({ db, page }) => {
  const id = await db.insert('users', { name: 'Alice' });
  await page.goto(`/users/${id}`);
});
💡 Tip: Worker-scoped fixtures are declared with a two-element array: [fixtureFn, { scope: 'worker' }], not just the function on its own.

INTERMEDIATE5. auto Fixtures

Setting auto: true makes Playwright run a fixture for every test in scope, even when the test doesn't destructure it — useful for cross-cutting setup like freezing the clock or seeding shared state.

const test = base.extend({
  mockTime: [async ({ page }, use) => {
    await page.clock.setFixedTime(new Date('2024-01-01'));
    await use();
  }, { auto: true }],
});

test('defaults to today', async ({ page }) => {
  // frozen clock applies automatically — no explicit request needed
  await page.goto('/invoices/new');
  await expect(page.getByLabel('Date')).toHaveValue('2024-01-01');
});

ADVANCED6. Composing Fixtures

Fixtures can depend on other fixtures — including your own custom ones — by destructuring them in the fixture function's parameters.

const test = base.extend({
  adminPage: async ({ page, db }, use) => {  // depends on the db fixture
    await db.seed('admin-user');
    await page.goto('/admin');
    await use(page);
  },
});

Playwright resolves the dependency graph automatically — if adminPage is requested, db is set up first, in the correct order, exactly once per its own scope.

ADVANCED7. Traditional Hooks

test.describe('checkout flow', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/cart');
  });
  test.afterEach(async ({ page }) => {
    await page.getByRole('button', { name: 'Clear cart' }).click();
  });
  test.beforeAll(async () => { /* runs once per describe/worker */ });
  test.afterAll(async  () => { /* runs once per describe/worker */ });
});

Hooks are scoped to the describe block (or the whole file, at the top level) they're declared in — simple and familiar if you've used other JS test frameworks like Jest or Mocha.

ADVANCED8. Fixtures vs Hooks — When to Use Which

Use a fixture when: 
// Setup is reused across MULTIPLE files
// or needs automatic teardown ordering
// or needs different scopes (worker/file)
const test = base.extend({
  apiClient: async ({}, use) => {
    const client = createClient();
    await use(client);
    await client.close();
  },
});
Use a hook when: 
// Setup is genuinely local to ONE file
// and doesn't need to be shared/reused
test.describe('one-off feature', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/feature-x');
  });
});

File-scoped overrides via test.use({ … }) sit between the two — they let a single file or describe block override a fixture's value (like storageState) without redefining the fixture itself:

test.use({ storageState: 'auth/admin.json' });

ADVANCED9. Common Pitfalls

⚠️ Pitfall 1 — Putting teardown before use(): Code written before await use(value) is setup; code after it is teardown. Writing cleanup logic before use() runs it before the test even starts, which is never what you want.
⚠️ Pitfall 2 — Overusing worker scope for stateful resources: A worker-scoped fixture is shared across every test in that worker — if one test mutates it in a way that leaks into the next test (e.g. leaving data in a shared database), you get order-dependent flakiness that's hard to trace. Reset any shared mutable state explicitly, or keep it 'test'-scoped.

Concept Key Points
Built-ins page, context, browser, browserName, request — available in every test.
test.extend() Creates custom fixtures; setup before use(), teardown after use().
Scope 'test' (default, fresh per test), 'worker' (shared per worker), 'file' (shared per file).
auto: true Runs a fixture for every test without it being explicitly requested.
Composition Fixtures can depend on other fixtures; Playwright resolves the order automatically.
test.use({...}) File/describe-scoped override of a fixture's value (e.g. storageState).
