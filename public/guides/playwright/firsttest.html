BEGINNER1. Anatomy of a Test File

Every Playwright test file is a normal TypeScript (or JavaScript) module. It starts with a single import that gives you the two functions you'll use constantly: test to define a test case, and expect to make assertions.

import { test, expect } from '@playwright/test';

test('home page loads', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveTitle(/Home/);
});

Breaking this down:

  • test('description', callback) — the first argument is a human-readable title shown in reports
  • async ({ page }) => { … } — the callback receives fixtures via destructuring; page is the most common one
  • Playwright creates the page (a browser tab) before your callback runs, and closes it automatically afterward — you never call new Page() or page.close() yourself
Fixtures explained simply: think of the object you destructure — { page } — as a box of pre-built tools Playwright hands you. You only ask for the tools you actually use in that particular test.

BEGINNER2. Why Everything Needs await

Every browser operation — navigating, clicking, typing, asserting — is asynchronous because it involves real communication with a browser process. That's why the test callback is declared async, and why nearly every line inside it is prefixed with await.

// ❌ WRONG — missing await
test('broken test', async ({ page }) => {
  page.goto('/login');                 // starts navigating, doesn't wait
  page.getByLabel('Email').fill('a');  // may run before the page exists!
});

// ✅ CORRECT — every async call awaited
test('correct test', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('a');
});
⚠️ Common Pitfall: A missing await is the single biggest source of flaky Playwright tests. The test moves on to the next line before the browser finishes the current action, causing intermittent, hard-to-reproduce failures. ESLint's eslint-plugin-playwright has a rule (playwright/missing-playwright-await) that catches this automatically — enable it.

BEGINNER3. Your First Real Test

import { test, expect } from '@playwright/test';

test('Playwright homepage has correct title', async ({ page }) => {
  await page.goto('https://playwright.dev/');

  // Auto-retrying title assertion — no manual wait needed
  await expect(page).toHaveTitle(/Playwright/);
});

Notice the assertion is also awaited. Web-first assertions like toHaveTitle() poll the page repeatedly until the condition is true or the timeout elapses — so this line will pass the instant the title updates, without you writing any wait logic.

A More Complete Flow

test('user can log in', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('secret123');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await expect(page).toHaveURL('/dashboard');
  await expect(page.getByText('Welcome back')).toBeVisible();
});

BEGINNER4. Grouping Tests with test.describe

test.describe('name', () => { … }) groups related tests into a logical unit. This isn't just cosmetic — it scopes hooks (beforeEach/afterEach) to just that group, and it makes the HTML report far easier to scan.

test.describe('Login', () => {
  test('shows login form', async ({ page }) => {
    await page.goto('/login');
    await expect(page.getByRole('heading')).toBeVisible();
  });

  test('rejects wrong password', async ({ page }) => {
    await page.goto('/login');
    await page.getByLabel('Password').fill('wrong');
    await page.getByRole('button', { name: 'Sign in' }).click();
    await expect(page.getByText('Invalid credentials')).toBeVisible();
  });
});
💡 Tip: Nested describe blocks are allowed and useful for deeply structured suites, e.g. describe('Checkout') containing describe('Payment') and describe('Shipping').

INTERMEDIATE5. Sharing Setup with beforeEach

test.describe('Product page', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/products/1');
  });

  test('shows product name', async ({ page }) => {
    await expect(page.getByRole('heading', { level: 1 })).toBeVisible();
  });

  test('add to cart button is enabled', async ({ page }) => {
    await expect(page.getByRole('button', { name: 'Add to cart' })).toBeEnabled();
  });
});

beforeEach runs before every test in its describe block (or every test in the file, if declared at the top level). This keeps each test focused on what it's actually verifying instead of repeating navigation boilerplate.

❌ Without beforeEach (repetitive): 
test('a', async ({ page }) => {
  await page.goto('/products/1');
  // ...assertion
});
test('b', async ({ page }) => {
  await page.goto('/products/1');
  // ...assertion
});
✅ With beforeEach (DRY): 
test.beforeEach(async ({ page }) => {
  await page.goto('/products/1');
});
test('a', async ({ page }) => { /* ... */ });
test('b', async ({ page }) => { /* ... */ });

INTERMEDIATE6. test.only, test.skip, and test.fixme

Three modifiers help during day-to-day development:

Modifier Effect Typical use
test.only() Runs only this test in the file; all others are skipped Focusing on one test while iterating
test.skip() Never runs; shown as skipped in the report Temporarily disabling a broken or irrelevant test
test.fixme() Marks a known failure; runner won't fail the build on it Tracking a real bug without blocking CI 
test.only('debug checkout flow', async ({ page }) => {
  await page.goto('/checkout');
  await expect(page.getByText('Order summary')).toBeVisible();
});

// Skipped while test.only is present above
test.skip('payment step', async ({ page }) => { /* work in progress */ });
test.fixme('known failing bug', async ({ page }) => { /* … */ });
⚠️ Common Pitfall: test.only is meant for local development only. It's easy to accidentally commit it, silently disabling the rest of the file's coverage in CI. Add a lint rule or a pre-commit check that fails the build if test.only is found in the diff.

INTERMEDIATE7. Tags, Timeouts, and Annotations

Add a tag like @smoke directly in a test's title to filter which tests run at the CLI:

test('rejects wrong password @smoke', async ({ page }) => { /* … */ });
npx playwright test --grep "@smoke"

Override the per-test timeout or attach metadata for a slow or tracked test using the options object (second argument):

test('slow upload', { timeout: 60_000 }, async ({ page }) => { /* … */ });

test('tracked bug', {
  annotation: { type: 'issue', description: 'https://github.com/org/repo/issues/42' },
}, async ({ page }) => { /* … */ });

ADVANCED8. Common Beginner Mistakes

⚠️ Mistake 1 — Asserting on page.url() instead of expect(page).toHaveURL(): page.url() reads the current URL synchronously, at the exact instant it's called — it does not wait for an in-flight redirect to finish. Prefer the auto-retrying expect(page).toHaveURL().
⚠️ Mistake 2 — One giant test instead of several focused tests: Cramming an entire user journey into a single test() makes failures hard to localize — the report tells you "the test failed," not "the third of ten actions failed." Prefer several smaller, descriptively-named tests unless the flow is genuinely sequential (see the Parallel Execution guide for describe.serial).
⚠️ Mistake 3 — Not awaiting expect(): Just like actions, forgetting await on an assertion means the check runs "detached" — the test can finish and report success before the assertion has actually resolved, silently hiding failures.
💡 Tip: Run npx playwright test --ui while learning — the visual timeline makes it obvious exactly where a test stalled or failed, which is far faster to debug than reading a stack trace alone.

📋 Quick Reference Summary

Concept Key Points
Imports import { test, expect } from '@playwright/test' at the top of every spec file.
Test shape test('title', async ({ page }) => { … }) — fixtures via destructuring.

describe Groups tests, scopes hooks, improves report readability.
