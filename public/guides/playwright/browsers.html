BEGINNER1. The Three-Level Object Model

Playwright organizes browser automation into three nested levels:

  • Browser — the actual running browser process (Chromium, Firefox, or WebKit)
  • BrowserContext — an isolated session inside that browser, like a private/incognito window, with its own cookies, localStorage, cache, and permissions
  • Page — a single tab living inside a context
Why this matters: a single Browser process can host many completely isolated Contexts simultaneously. This is dramatically cheaper than launching a whole new browser process per test, which is why Playwright reuses one Browser across many tests but gives each test a fresh Context.

BEGINNER2. The Default page Fixture

In ordinary tests you never manually create a Browser, Context, or Page — the page fixture already gives you one, built using your project's use settings from playwright.config.ts.

test('uses the default page', async ({ page }) => {
  await page.goto('/');
  // Playwright already created a Browser, a Context, and this Page for you
});

You only need to reach for browser.newContext() explicitly when a test needs configuration that differs from the project defaults — a different viewport, locale, or set of granted permissions, for example.

INTERMEDIATE3. Creating a Custom Context

const context = await browser.newContext({
  viewport:         { width: 1280, height: 720 },
  locale:           'en-US',
  timezoneId:       'America/New_York',
  geolocation:      { latitude: 40.71, longitude: -74.01 },
  permissions:      ['geolocation', 'notifications'],
  storageState:     'auth.json',
  userAgent:        'Custom/1.0',
  ignoreHTTPSErrors: true,
  colorScheme:      'dark',
  recordVideo:      { dir: 'videos/' },
  extraHTTPHeaders: { 'X-Api-Key': 'secret' },
});

const page = await context.newPage();
await page.goto('https://example.com');

Locale-Specific Test Example

test('French locale date format', async ({ browser }) => {
  const context = await browser.newContext({
    locale: 'fr-FR',
    timezoneId: 'Europe/Paris',
    viewport: { width: 1440, height: 900 },
  });
  const page = await context.newPage();

  await page.goto('/dashboard');
  await expect(page.getByTestId('date-display')).toHaveText(/juillet/);

  await context.close();
});
Option Purpose Example
viewport Test responsive breakpoints { width: 375, height: 812 }
geolocation + permissions Simulate location-aware features Must grant 'geolocation' or the API is denied
storageState Pre-load a logged-in session 'auth.json'
colorScheme Test dark mode UI 'dark' or 'light'
recordVideo Capture the session as WebM { dir: 'videos/' }

INTERMEDIATE4. Context Isolation for Multi-User Tests

Because each context has its own cookie jar and storage, you can simulate two completely different users interacting with the same application in the same test, with zero risk of one user's session leaking into the other's.

test('admin can see message sent by guest', async ({ browser }) => {
  const adminCtx = await browser.newContext({ storageState: 'admin.json' });
  const guestCtx = await browser.newContext({ storageState: 'guest.json' });

  const adminPage = await adminCtx.newPage();
  const guestPage = await guestCtx.newPage();

  await guestPage.goto('/chat');
  await guestPage.getByLabel('Message').fill('Hello admin!');
  await guestPage.getByRole('button', { name: 'Send' }).click();

  await adminPage.goto('/chat');
  await expect(adminPage.getByText('Hello admin!')).toBeVisible();

  await adminCtx.close();
  await guestCtx.close();
});
Real-world use cases: testing real-time chat, collaborative document editing, multiplayer features, or any workflow where one user's action (e.g. an admin approving a request) must be reflected for another user.

INTERMEDIATE5. Saving and Reusing Auth via storageState

// Save current session (cookies + localStorage) to a file
await context.storageState({ path: 'auth.json' });

// Later — or in a different test — reload it instantly
const context2 = await browser.newContext({ storageState: 'auth.json' });

This pattern (covered in depth in the Authentication & State guide) turns a 2-second login into a near-instant file read, which adds up dramatically across a large suite.

ADVANCED6. Multiple Pages and Popups in One Context

A single context can hold several pages — useful for testing features that open a new tab, such as "Open in new tab" links or OAuth popups.

test('handle a popup window', async ({ context, page }) => {
  await page.goto('/docs');

  // Wait for the popup while triggering the action that opens it
  const [popup] = await Promise.all([
    context.waitForEvent('page'),
    page.getByRole('link', { name: 'Open in new tab' }).click(),
  ]);

  await popup.waitForLoadState();
  await expect(popup).toHaveURL(/\/docs\/full/);
});
💡 Tip: Always pair the triggering action with context.waitForEvent('page') inside Promise.all() — if you click first and then wait, there's a race condition where the popup could open before your listener is attached.

ADVANCED7. Cleanup and Resource Management

await context.close();   // closes every page within it automatically

When you create contexts explicitly (rather than relying on the built-in page fixture), you're responsible for closing them. Closing a context releases its cookies, cache, and any recorded video/trace resources, and closes all pages inside it — you don't need to close pages individually first.

⚠️ Common Pitfall: Forgetting to close manually-created contexts leaks memory across a long test run and can slow down or crash workers in large suites. If you use browser.newContext() directly (outside the built-in page/context fixtures), always wrap it so close() runs even if the test fails — a custom fixture with await use(context) handles this automatically via its teardown phase.

ADVANCED8. Common Pitfalls

⚠️ Pitfall 1 — Assuming contexts share state: Developers coming from single-session tools sometimes expect a second newContext() to inherit cookies set in the first. It never does — that's the entire point of isolation.
⚠️ Pitfall 2 — Granting permissions after navigation: Permissions like geolocation must be included in browser.newContext({ permissions: [...] }) before the page that requests them loads; granting them mid-test via context.grantPermissions() works too, but forgetting either step results in the browser silently denying the API.
💡 Tip: Use context.grantPermissions(['camera'], { origin: 'https://example.com' }) to scope a permission grant to a specific origin instead of the whole context.

📋 Quick Reference Summary

Concept Key Points
Browser The running browser process; Playwright reuses one across many tests.
BrowserContext Isolated session — own cookies, storage, permissions. Like incognito windows.
Page A tab inside a context; a context can hold multiple pages.
Default fixture page is auto-created from project use settings — no manual setup needed normally.
Custom context Use browser.newContext(options) for viewport, locale, geolocation, storageState, etc.
Multi-user Create separate contexts per user — complete isolation, no state bleed.
Cleanup context.close() closes all pages inside it; always close manually-created contexts.
