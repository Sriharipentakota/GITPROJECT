BEGINNER1. The Shape of playwright.config.ts

All configuration lives in one file at the project root, exported through defineConfig() — which gives you full TypeScript autocomplete for every option.

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  timeout: 30_000,
  use: {
    baseURL: 'http://localhost:3000',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],
});
Why one central file matters: instead of every test file hardcoding its own base URL or timeout, changing one line in the config updates behavior for the entire suite — critical when you promote a suite from a local dev server to a staging environment to CI.

BEGINNER2. The use Block — Browser Defaults

The use block sets defaults inherited by every project and every test:

use: {
  baseURL:    'http://localhost:3000',
  headless:   true,
  viewport:   { width: 1280, height: 720 },
  trace:      'on-first-retry',
  screenshot: 'only-on-failure',
  video:      'on-first-retry',
},
Option Purpose
baseURL Lets tests call page.goto('/path') instead of full URLs
headless Run without a visible browser window (default true)
viewport Default browser window size for every test
trace / screenshot / video Debugging artifact capture policy (see the Screenshots, Videos & Traces guide)

BEGINNER3. The projects Array — Multi-Browser Testing

Each entry in projects represents a distinct test configuration — most commonly a browser engine, but also useful for device emulation or role-based test suites (see the Authentication guide).

projects: [
  { name: 'chromium',      use: { ...devices['Desktop Chrome']  } },
  { name: 'firefox',       use: { ...devices['Desktop Firefox'] } },
  { name: 'webkit',        use: { ...devices['Desktop Safari']  } },
  { name: 'mobile-chrome', use: { ...devices['Pixel 5']         } },
  { name: 'mobile-safari', use: { ...devices['iPhone 13']       } },
],

Spreading ...devices['Desktop Chrome'] loads Playwright's built-in preset for that browser/device combination (viewport, user agent, touch support, etc.). Run a single project from the CLI with --project=chromium.

💡 Tip: Each project can override any part of use — for example giving only the mobile-chrome project a different baseURL to test a mobile-specific subdomain.

INTERMEDIATE4. Timeouts: test vs expect

timeout — per-test wall clock: 
export default defineConfig({
  timeout: 30_000, // whole test must
                   // finish in 30s
});
expect.timeout — assertion retry window: 
export default defineConfig({
  expect: { timeout: 5_000 }, // each
    // web-first assertion retries
    // for up to 5s
});

These are independent: a test can run for up to 30 seconds total, while any single expect(locator).toBeVisible() inside it gives up (and fails the test) after 5 seconds if the condition never becomes true.

INTERMEDIATE5. Retries and Workers

retries: process.env.CI ? 2 : 0,
workers: process.env.CI ? 1 : undefined,  // undefined = auto-detect
fullyParallel: true,

The standard pattern re-runs a failed test up to twice only in CI (where transient infrastructure flakiness is more common), while local runs fail immediately for fast feedback. fullyParallel: true runs every individual test in its own worker rather than only parallelizing across files (see the Parallel Execution guide for the full breakdown).

⚠️ Common Pitfall: Leaving retries high everywhere (including locally) can mask a genuinely flaky test that will eventually cause real problems in CI. Treat CI retries as a safety net, not a substitute for fixing the root cause of flakiness.

reporter: [['html'], ['dot']],

// Environment-specific reporting
reporter: process.env.CI
  ? [['html', { open: 'never' }], ['github']]
  : [['dot']],
Reporter Use case
html Rich interactive report with screenshots, video, traces
dot Minimal one-character-per-test console output
github Inline annotations on GitHub Actions pull requests
junit XML output for non-native CI dashboards
blob Intermediate format used for merging sharded CI runs

ADVANCED7. webServer — Auto-Starting Your App

webServer: {
  command:             'npm run dev',
  url:                 'http://localhost:3000',
  reuseExistingServer: !process.env.CI,
},

Playwright starts your dev server before the suite begins (waiting until url responds), and tears it down after — no separate terminal window needed, and no risk of tests running against a stale server left over from a previous session.

reuseExistingServer: !process.env.CI explained: locally, if you already have npm run dev running in another terminal, Playwright detects the port is occupied and reuses it instead of erroring — a nice developer-experience touch. In CI, this is always false so every run starts from a clean server.

ADVANCED8. globalSetup and globalTeardown

globalSetup:    './global-setup.ts',
globalTeardown: './global-teardown.ts',

These TypeScript files run once for the entire suite, before/after all tests and all workers. The canonical use case is authenticating once and saving the browser's storageState so individual tests skip the login flow entirely (see the Authentication & State guide for the full pattern).

// global-setup.ts
import { chromium } from '@playwright/test';

export default async function globalSetup() {
  const browser = await chromium.launch();
  const page = await browser.newPage();

  await page.goto('http://localhost:3000/login');
  await page.getByLabel('Email').fill('admin@example.com');
  await page.getByLabel('Password').fill('password');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await page.context().storageState({ path: 'auth.json' });
  await browser.close();
}

ADVANCED9. Common Pitfalls

⚠️ Pitfall 1 — Setting workers too high locally: More workers than CPU cores doesn't make tests faster — it causes resource contention that can make things slower and flakier. Let workers default to undefined (auto) locally and only pin an explicit number for CI where resources are known and fixed.
⚠️ Pitfall 2 — Forgetting project-level overrides inherit, not replace: A project's use block merges with (doesn't fully overwrite) the top-level use block — so you only need to specify the fields that actually differ for that project.
💡 Tip: Keep webServer.url pointing at a lightweight health-check route if your app's homepage is slow to render — Playwright only needs a 2xx/3xx response to consider the server ready, not a fully rendered page.

📋 Quick Reference Summary

Concept Key Points
use block Browser-level defaults inherited by all projects: baseURL, viewport, trace, screenshot, video.
projects Defines target browsers/devices; each can override use; filter with --project.
timeout vs expect.timeout Per-test wall clock vs. per-assertion auto-retry window — independent settings.
retries/workers Typically CI-only retries; workers default to auto locally, fixed in CI.
webServer Auto-starts and tears down your dev server; reuseExistingServer for local convenience.
globalSetup/Teardown Run once per suite — canonical use is one-time login + storageState.
