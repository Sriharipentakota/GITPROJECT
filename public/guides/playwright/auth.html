BEGINNER1. Why Reuse Authentication State?

Logging in through the UI before every single test is slow and repetitive. A login that takes 2 seconds costs 200 seconds across 100 tests — pure overhead unrelated to what those tests are actually verifying.

Playwright lets you save a browser context's cookies, localStorage, and sessionStorage to a JSON file after logging in once, then reload that state instantly in any subsequent test.

The math: one login (2s) + 100 instant file-based state loads (~0s each) vs. 100 logins (200s). At scale, this is the difference between a 3-minute suite and a 15-minute one.

BEGINNER2. Saving State with storageState()

await page.goto('/login');
await page.getByLabel('Email').fill('user@example.com');
await page.getByLabel('Password').fill('secret');
await page.getByRole('button', { name: 'Sign in' }).click();
await page.waitForURL('/dashboard');

await page.context().storageState({ path: 'playwright/.auth/user.json' });

This writes a JSON file containing every cookie and every localStorage/sessionStorage entry for the context — everything the app needs to consider the browser "logged in."

INTERMEDIATE3. The Auth Setup Project Pattern

The recommended, idiomatic pattern uses a dedicated setup project that logs in once before the real test projects run.

// auth.setup.ts
import { test as setup } from '@playwright/test';
const authFile = 'playwright/.auth/user.json';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.TEST_EMAIL!);
  await page.getByLabel('Password').fill(process.env.TEST_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForURL('/dashboard');

  await page.context().storageState({ path: authFile });
});
💡 Tip: Note that setup here is imported as test as setup — it's the same underlying API, just aliased for readability so it's obvious this file is a setup step, not a real test.

INTERMEDIATE4. Wiring Dependencies in playwright.config.ts

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /auth\.setup\.ts/ },
    {
      name: 'chromium',
      use: {
        ...devices['Desktop Chrome'],
        storageState: 'playwright/.auth/user.json',
      },
      dependencies: ['setup'],
    },
  ],
});

The dependencies: ['setup'] array guarantees Playwright runs the setup project first and waits for it to complete before starting the chromium project — so the state file is guaranteed to exist by the time real tests need it. Each new browser context in the chromium project then loads that state automatically via use.storageState.

ADVANCED5. Testing Multiple Roles

Maintain a separate state file — and a separate setup project — per role (admin, editor, viewer) to test role-based access control end-to-end.

// playwright.config.ts
projects: [
  { name: 'setup:user',  testMatch: /user\.setup\.ts/  },
  { name: 'setup:admin', testMatch: /admin\.setup\.ts/ },
  {
    name: 'user-tests',
    use: { storageState: 'playwright/.auth/user.json' },
    dependencies: ['setup:user'],
  },
  {
    name: 'admin-tests',
    use: { storageState: 'playwright/.auth/admin.json' },
    dependencies: ['setup:admin'],
  },
],

You can also override just one test's role without a whole extra project, using test.use():

test.use({ storageState: 'playwright/.auth/admin.json' });
test('admin can delete posts', async ({ page }) => {
  await page.goto('/posts');
  await expect(page.getByRole('button', { name: 'Delete' })).toBeVisible();
});

INTERMEDIATE6. HTTP Basic Auth

// playwright.config.ts
use: { httpCredentials: { username: 'user', password: 'pass' } }

httpCredentials handles sites protected by HTTP Basic Auth at the network layer — a completely different mechanism from a login form, and one that storageState does not cover.

ADVANCED7. Manual Cookie and Storage Control

// Cookies
const cookies = await context.cookies();
await context.addCookies([{
  name: 'sid', value: 'abc', domain: 'example.com', path: '/'
}]);
await context.clearCookies();

// localStorage / sessionStorage (via page.evaluate)
await page.evaluate(() => localStorage.setItem('token', 'abc123'));
const token = await page.evaluate(() => localStorage.getItem('token'));
await page.evaluate(() => sessionStorage.clear());

These fine-grained APIs are useful when you need to inject or inspect a specific piece of state without going through a full login flow — for example, setting a feature flag stored in localStorage before a test.

ADVANCED8. API-Based Login (Fastest)

If your backend exposes a login API endpoint, authenticating directly via request is dramatically faster than driving the UI login form — often around 100ms instead of 1-2 seconds.

// auth.setup.ts
import { test as setup, request } from '@playwright/test';

setup('authenticate via API', async ({ page }) => {
  const apiCtx = await request.newContext({ baseURL: 'https://example.com' });

  const resp = await apiCtx.post('/api/auth/login', {
    data: { email: 'user@example.com', password: 'secret' },
  });
  const { sessionToken } = await resp.json();

  await page.context().addCookies([{
    name: 'session', value: sessionToken, domain: 'example.com', path: '/'
  }]);

  await page.context().storageState({ path: 'playwright/.auth/user.json' });
  await apiCtx.dispose();
});
UI login (slower, more realistic): 
await page.goto('/login');
await page.getByLabel('Email').fill(email);
await page.getByLabel('Password').fill(pw);
await page.getByRole('button', { name: 'Sign in' }).click();
// ~1-2 seconds
API login (faster, less end-to-end coverage): 
const resp = await apiCtx.post('/api/auth/login', {
  data: { email, password: pw },
});
// ~100ms
💡 Tip: Keep one UI-based login test to verify the login form itself still works end-to-end — then use the faster API method for every other test's setup, where the login flow isn't what's actually being tested.

ADVANCED9. Common Pitfalls

⚠️ Pitfall 1 — Committing real credentials or state files: Never commit playwright/.auth/*.json files or hardcoded passwords to version control — use environment variables for credentials and add the auth directory to .gitignore.
⚠️ Pitfall 2 — Stale or expired state files: If your app's session tokens expire (e.g. after 24 hours), a cached storageState from a previous CI run will cause every test to fail with "not authenticated" errors. Regenerate the state file at the start of every CI run rather than caching it across runs indefinitely.
