BEGINNER1. What Makes Locators Special

A Playwright Locator is not a direct reference to a DOM element — it's a lazy, re-usable recipe for finding one. page.getByRole('button') doesn't search the DOM the moment you write it; it only queries when you actually call an action or assertion on it (e.g. .click() or expect(...).toBeVisible()).

This laziness is what enables auto-waiting: every time a locator is used, Playwright re-queries the DOM and waits for the element to be visible, attached, and stable before interacting — without you writing a single manual wait.

Old-style selector (fragile): a raw CSS selector captured once represents a specific DOM node at a specific moment. If that node is removed and re-added (common in React/Vue re-renders), old automation tools throw a stale-element error. A Playwright locator simply re-finds the matching element the next time it's used.

BEGINNER2. The Locator Priority Order

Playwright's own documentation recommends this priority, from most to least resilient:

Priority Method Matches
① getByRole() ARIA role + accessible name — how screen readers see the page
② getByLabel() Form inputs linked to their visible <label>
③ getByPlaceholder() Unlabelled inputs, by placeholder text
④ getByText() / getByAltText() / getByTitle() Visible text, image alt text, or title attributes
⑤ getByTestId() Explicit data-testid attribute
⑥ CSS / XPath Raw DOM structure — last resort

Higher-priority strategies are more resilient because they mirror how a real user or assistive technology identifies the element, so they survive styling and markup refactors that would break a CSS class selector.

BEGINNER3. Semantic Locators in Depth

page.getByRole('button', { name: 'Submit' })
page.getByRole('textbox', { name: 'Email' })
page.getByRole('heading', { level: 1 })
page.getByLabel('Password')
page.getByPlaceholder('Enter your email')
page.getByText('Welcome back')
page.getByText('Welcome', { exact: false })   // substring match
page.getByAltText('Company logo')
page.getByTitle('Close dialog')
page.getByTestId('checkout-btn')

Complete Form Example

test('fill and submit login form', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Email address').fill('user@example.com');
  await page.getByLabel('Password').fill('secret123');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await expect(page).toHaveURL('/dashboard');
});
💡 Tip: getByRole() understands implicit roles — a plain <button> has role button automatically, and an <a href> has role link, so you rarely need to add ARIA attributes just to make elements locatable.

INTERMEDIATE4. CSS and XPath as a Last Resort

page.locator('.submit-btn')
page.locator('#email-input')
page.locator('input[type="email"]')
page.locator('xpath=//button[@type="submit"]')

These work fine, but couple your test directly to implementation details (a CSS class or DOM position) that frontend developers change freely without thinking of tests. Reach for them only when no semantic role, label, or test id is available and you cannot add one.

❌ Fragile CSS selector: 
await page.locator('.btn.btn-primary.mt-3').click();
// Breaks the moment a class name changes
✅ Resilient role locator: 
await page.getByRole('button', { name: 'Save' }).click();
// Survives styling and markup refactors

INTERMEDIATE5. Chaining Locators

Chaining scopes a search to inside a parent element — essential once a page has repeated components like cards or list rows.

page.locator('.product-card').getByRole('button', { name: 'Add to cart' })
page.getByRole('listitem').getByRole('link')
test('like the second product card', async ({ page }) => {
  await page.goto('/products');

  const secondCard = page.locator('.product-card').nth(1);

  // getByRole here searches ONLY within secondCard
  await secondCard.getByRole('button', { name: 'Like' }).click();

  await expect(secondCard.getByTestId('like-count')).toHaveText('1');
});

INTERMEDIATE6. Filtering and Indexing

// Filtering: narrow a set of matches by content
page.getByRole('listitem').filter({ hasText: 'Special offer' })
page.getByRole('row').filter({ has: page.getByRole('checkbox') })

// Indexing: pick one of several matches
page.getByRole('option').first()
page.getByRole('option').last()
page.getByRole('row').nth(2)      // 0-indexed

Filtering a Cart to Remove One Item

test('remove only the "Playwright" item from the cart', async ({ page }) => {
  await page.goto('/cart');

  const playwrightRow = page.getByRole('row').filter({ hasText: 'Playwright' });
  await playwrightRow.getByRole('button', { name: 'Remove' }).click();

  await expect(page.getByRole('row').filter({ hasText: 'Playwright' })).toHaveCount(0);
});
filter({ hasText }) vs. filter({ has }): hasText matches on visible text content; has matches when the row contains a nested locator (e.g. only rows that contain a checked checkbox). They can be combined for very precise scoping.

ADVANCED7. Strict Mode

By default, Playwright locators run in strict mode: if a locator resolves to more than one element when you try to act on it, Playwright throws an error rather than guessing which one you meant.

// ❌ Throws if there are multiple buttons named "Delete"
await page.getByRole('button', { name: 'Delete' }).click();

// ✅ Narrow explicitly
await page.getByRole('button', { name: 'Delete' }).first().click();
await page.getByRole('row').filter({ hasText: 'Order #42' })
  .getByRole('button', { name: 'Delete' }).click();
⚠️ Common Pitfall: Strict mode errors are a feature, not a bug — they surface ambiguity you would otherwise discover as a flaky, hard-to-explain test (Playwright silently clicking the wrong "Delete" button). Resist the urge to reach for .first() as a quick fix without checking whether you actually meant to scope more precisely.

ADVANCED8. Common Pitfalls

⚠️ Pitfall 1 — Over-relying on getByTestId(): Test IDs are a useful escape hatch, but sprinkling them everywhere means your tests no longer verify the app is accessible — a button with no accessible name but a data-testid passes your tests while failing real screen-reader users. Prefer role/label locators when the element already has a sensible accessible name.
⚠️ Pitfall 2 — Using indexes on a dynamic list: .nth(2) is fragile against a list whose order can change (sorting, filtering, async loading). Prefer .filter({ hasText }) to identify the specific row by its content instead of its position whenever possible.
💡 Tip: Playwright's VS Code extension and Codegen (npx playwright codegen) suggest the best available locator automatically as you click around a real page — a great way to learn the priority order by example.

📋 Quick Reference Summary

Concept Key Points
Locators are lazy No DOM query until an action/assertion runs — re-evaluated every time.
Priority order getByRole → getByLabel → getByPlaceholder → getByText → getByTestId → CSS/XPath.
Chaining parent.getByRole(…) scopes the search inside a component.
Filtering .filter({ hasText }) / .filter({ has }) narrows a list by content.
Indexing .first(), .last(), .nth(n) — prefer filtering by content when order can change.
Strict mode Multiple matches throw an error instead of silently picking one.
