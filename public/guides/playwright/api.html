BEGINNER1. The Built-In HTTP Client

Playwright includes its own HTTP client, APIRequestContext — no axios, node-fetch, or supertest dependency required. Every test automatically has access to it via the request fixture, which is pre-configured with your config's baseURL and any extraHTTPHeaders.

test('health check responds OK', async ({ request }) => {
  const res = await request.get('/api/health');
  expect(res.ok()).toBeTruthy();
});
Why this matters: since it's part of the same test runner and shares the same config, you write API tests with the exact same test()/expect() syntax as UI tests — no context switching between tools.

BEGINNER3. POST, PUT, PATCH, DELETE

const created = await request.post('/api/users', {
  data: { name: 'Alice', email: 'alice@example.com' },
});
expect(created.status()).toBe(201);
const { id } = await created.json();

await request.put(`/api/users/${id}`,  { data: { name: 'Bob' } });
await request.patch(`/api/users/${id}`, { data: { active: false } });
await request.delete(`/api/users/${id}`);

Full CRUD Cycle

test('user CRUD via API', async ({ request }) => {
  const created = await request.post('/api/users', {
    data: { name: 'Alice', email: 'alice@test.com' },
  });
  expect(created.status()).toBe(201);
  const { id } = await created.json();

  const fetched = await request.get(`/api/users/${id}`);
  await expect(fetched).toBeOK();
  expect((await fetched.json()).name).toBe('Alice');

  const deleted = await request.delete(`/api/users/${id}`);
  expect(deleted.status()).toBe(204);

  const missing = await request.get(`/api/users/${id}`);
  expect(missing.status()).toBe(404);
});

INTERMEDIATE4. Inspecting the Response

Method Returns
res.ok() Boolean — true for status 200–299
res.status() Exact numeric HTTP status code
await res.json() Parsed JSON body
await res.text() Raw text body
res.headers() Response headers as a plain object 
await expect(response).toBeOK();   // preferred assertion form in tests

INTERMEDIATE5. Headers, Forms, and Multipart Uploads

// Custom headers, e.g. auth tokens
const res = await request.get('/api/protected', {
  headers: { Authorization: `Bearer ${token}` },
});

// Form-encoded body
await request.post('/api/submit', { form: { name: 'Alice' } });

// Multipart file upload
await request.post('/api/upload', {
  multipart: { file: { name: 'report.pdf', mimeType: 'application/pdf',
                        buffer: Buffer.from('…') } },
});
💡 Tip: Use data: { … } for a JSON body (Playwright sets Content-Type: application/json automatically), form: { … } for application/x-www-form-urlencoded, and multipart: { … } only when the endpoint genuinely expects multipart/form-data (typically file uploads).

ADVANCED6. Three Use Cases for API Testing

Use case What it looks like
Pure API test Validate a REST/GraphQL endpoint directly — no browser opened at all
Setup/teardown Create/delete test data via API, dramatically faster than clicking through the UI
Hybrid test Seed via API, then assert the UI correctly reflects that state

API Seed + UI Assertion Hybrid Test

test('newly created product appears in the catalog', async ({ request, page }) => {
  const res = await request.post('/api/products', {
    data: { name: 'Playwright Pro', price: 99 },
  });
  expect(res.status()).toBe(201);
  const { id } = await res.json();

  await page.goto('/catalog');
  await expect(page.getByTestId(`product-${id}`)).toBeVisible();
  await expect(page.getByTestId(`product-${id}`)).toContainText('Playwright Pro');

  await request.delete(`/api/products/${id}`);   // cleanup via API
});
Why hybrid tests matter: seeding state via the UI (clicking "New Product" and filling a form) is slow and adds an extra point of failure unrelated to what you're actually testing (the catalog display). Seeding via API isolates the assertion to exactly the behavior you care about.

ADVANCED7. page.request vs Standalone Contexts

page.request — shares browser cookies: 
const res = await page.request.get('/api/me');
// Uses the SAME session cookies
// as the logged-in browser page
request.newContext() — fully independent: 
const api = await request.newContext({
  baseURL: 'https://api.example.com',
  extraHTTPHeaders: { 'x-api-key': process.env.API_KEY! },
});
await api.dispose();  // always release when done

page.request is ideal when the server authenticates via browser session cookies and you want to make API calls "as" the currently logged-in user. request.newContext() is the right choice in globalSetup, where no browser or page exists yet.

// global-setup.ts
import { request } from '@playwright/test';

export default async function globalSetup() {
  const api = await request.newContext({ baseURL: process.env.BASE_URL });
  const loginRes = await api.post('/api/auth/login', {
    data: { email: 'admin@test.com', password: 'secret' },
  });
  await api.storageState({ path: 'auth/admin.json' });
  await api.dispose();
}

ADVANCED8. Common Pitfalls

⚠️ Pitfall 1 — Forgetting to dispose standalone contexts: Every request.newContext() holds open connections; forgetting await api.dispose() in globalSetup or a fixture teardown can leak resources across a long-running suite.
⚠️ Pitfall 2 — Testing pure logic entirely through the UI: If a bug is really about backend validation (e.g. "email must be unique"), a pure API test that posts directly to the endpoint is faster, more precise, and less brittle than driving the same check through a full UI form.
💡 Tip: Use API calls for teardown even in UI-heavy tests — deleting test data via request.delete() in an afterEach is far more reliable than trying to click through a UI cleanup flow that might itself be broken.
