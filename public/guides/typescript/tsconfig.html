INTERMEDIATE1. What is tsconfig.json?

Definition

tsconfig.json is the configuration file that tells the TypeScript compiler (tsc) which files to compile and how strictly to check them. Its presence in a directory also marks that directory as the root of a TypeScript project for editors and tools.

Real-world analogy: tsconfig.json is like a recipe's oven settings — it doesn't change the ingredients (your code), but it controls temperature and timing (strictness, target JS version) that determine how the final dish comes out. 
// Generate a starter tsconfig.json
// npx tsc --init

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"]
}
💡 Tip: Running plain tsc with no arguments compiles the entire project according to the nearest tsconfig.json, walking up from the current directory.

INTERMEDIATE2. target and lib

target — Which JavaScript Version to Emit

target controls both the JavaScript syntax the compiler outputs (e.g. whether classes compile down to functions) and which built-in APIs TypeScript assumes exist without extra libraries.

{
  "compilerOptions": {
    "target": "ES2022"   // modern - classes, async/await, optional chaining all native
  }
}

// class Foo {} compiled with target: "ES5" becomes verbose constructor-function code;
// compiled with target: "ES2022" it stays as class Foo {}

lib — Which Type Declarations to Include

lib lets you add or override the ambient type declarations available (like DOM APIs or newer array methods), independent of the compiled JS syntax.

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"]
    // DOM types (document, window) are only included if you add them here,
    // typically needed for browser-facing code but not for a Node.js backend
  }
}

INTERMEDIATE3. module and moduleResolution

module — The Output Module Format

{
  "compilerOptions": {
    "module": "ESNext"      // keeps import/export as-is - for bundlers (Vite, esbuild, webpack)
    // "module": "CommonJS" // compiles to require()/module.exports - classic Node.js
    // "module": "NodeNext" // follows Node's own ESM/CJS resolution rules based on package.json
  }
}

moduleResolution — How Import Paths Are Located

{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "bundler"   // modern default recommended for apps using a bundler
    // "moduleResolution": "node10" // classic Node.js CommonJS-style resolution (older name: "node")
    // "moduleResolution": "nodenext" // pairs with "module": "NodeNext"
  }
}

Frontend app with Vite/webpack ESNext bundler
Node.js backend (CommonJS) CommonJS node10
Node.js backend (native ESM) NodeNext nodenext

ADVANCED4. The strict Family of Flags

strict: true is a shorthand that enables an entire family of individually toggleable safety checks at once.

{
  "compilerOptions": {
    "strict": true
    // Equivalent to enabling all of the following individually:
    // "noImplicitAny": true,
    // "strictNullChecks": true,
    // "strictFunctionTypes": true,
    // "strictBindCallApply": true,
    // "strictPropertyInitialization": true,
    // "noImplicitThis": true,
    // "useUnknownInCatchVariables": true,
    // "alwaysStrict": true
  }
}

What Each Key Flag Actually Does

// noImplicitAny: true
function process(data) { /* ❌ Error: 'data' implicitly has an 'any' type */ }

// strictNullChecks: true
let name: string = null;   // ❌ Error - null not assignable to string

// strictPropertyInitialization: true
class User {
    name: string;   // ❌ Error - not initialized in constructor or at declaration
    constructor() {}
}
⚠️ Common Pitfall: Turning on strict: true for an existing loosely-typed codebase can surface hundreds of errors at once. New projects should enable it from day one; existing ones often migrate incrementally by enabling individual sub-flags first.

INTERMEDIATE5. Included Files: include, exclude, files

{
  "compilerOptions": { "target": "ES2022" },
  "include": ["src/**/*"],           // glob patterns of files to compile
  "exclude": ["node_modules", "dist", "**/*.test.ts"],  // subtract from include
  "files": ["src/main.ts"]           // exact file list, used for small/simple projects
}
💡 Tip: node_modules, bower_components, and the configured outDir are excluded by default even without an explicit exclude entry — you rarely need to list node_modules yourself.

INTERMEDIATE6. Output Control: outDir, rootDir, declaration

{
  "compilerOptions": {
    "rootDir": "./src",       // where your source .ts files live
    "outDir": "./dist",       // where compiled .js files are written
    "declaration": true,      // also emit matching .d.ts files
    "declarationMap": true,   // enable "go to definition" into the original .ts source
    "sourceMap": true         // emit .js.map files for debugging compiled output
  }
}

// src/utils.ts -> dist/utils.js + dist/utils.d.ts + dist/utils.js.map
Real-world use case: Library authors publishing to npm typically set declaration: true so consumers get full type information for the package without needing the original TypeScript source.

ADVANCED7. Interop Flags: esModuleInterop and skipLibCheck

esModuleInterop

{
  "compilerOptions": {
    "esModuleInterop": true,       // allows `import express from "express"` for CJS packages
    "allowSyntheticDefaultImports": true   // usually implied by esModuleInterop
  }
}

// Without esModuleInterop:
import * as express from "express";
// With esModuleInterop: true:
import express from "express";

skipLibCheck

{
  "compilerOptions": {
    "skipLibCheck": true   // skips type-checking of all .d.ts files, including node_modules
  }
}
⚠️ Common Pitfall: skipLibCheck is nearly always turned on in real projects — without it, type conflicts between different versions of the same @types package pulled in by different dependencies can produce errors you have no control over.

ADVANCED8. Path Mapping with baseUrl and paths

paths lets you define custom import aliases, resolved by the compiler (and, separately, by your bundler/runtime, which needs its own matching alias configuration).

{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@components/*": ["src/components/*"],
      "@utils/*": ["src/utils/*"]
    }
  }
}
// Without path mapping
import { Button } from "../../../components/Button";

// With path mapping
import { Button } from "@components/Button";
💡 Tip: paths only affects type-checking and editor navigation — bundlers like Vite or webpack need their own alias configuration (e.g. resolve.alias) to actually resolve these imports at build/runtime.

ADVANCED9. Project References and extends

extends — Sharing a Base Config

// tsconfig.base.json
{
  "compilerOptions": {
    "target": "ES2022",
    "strict": true,
    "skipLibCheck": true
  }
}

// tsconfig.json
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist"
  },
  "include": ["src/**/*"]
}

Project References — Multi-Package Builds

// packages/app/tsconfig.json
{
  "compilerOptions": { "composite": true },
  "references": [
    { "path": "../shared" }
  ]
}

// Build with:
// tsc --build
Real-world use case: Monorepos with multiple packages (e.g. shared, api, web) use project references so tsc --build only recompiles packages whose dependencies actually changed, dramatically speeding up incremental builds.

ADVANCED10. Best Practices

1. Start New Projects with strict: true

// ✅ Good
{ "compilerOptions": { "strict": true } }

2. Always Enable skipLibCheck

// ✅ Good - avoids noise from third-party type conflicts
{ "compilerOptions": { "skipLibCheck": true } }

3. Match module/moduleResolution to Your Actual Runtime

// ✅ Good - pick the row from the table in section 3 that matches your setup

4. Use extends to Share Config Across a Monorepo

// ✅ Good
{ "extends": "../../tsconfig.base.json" }

5. Emit Declarations When Publishing a Library

// ✅ Good
{ "compilerOptions": { "declaration": true, "declarationMap": true } }

6. Keep include/exclude Precise

// ✅ Good - avoids accidentally compiling test files into a production build
{ "include": ["src/**/*"], "exclude": ["**/*.test.ts", "**/*.spec.ts"] }

📋 Quick Reference Summary

Option Key Points
target JavaScript version emitted and assumed available (e.g. ES2022)
lib Which ambient type declarations (DOM, ESNext APIs) are available
module / moduleResolution Output module format and how import specifiers are resolved
strict Enables the full family of type-safety flags (noImplicitAny, strictNullChecks, etc.)
outDir / rootDir / declaration Controls compiled output location and whether .d.ts files are emitted
esModuleInterop Smooths CommonJS/ES module default-import differences
skipLibCheck Skips type-checking .d.ts files; avoids third-party type conflicts
baseUrl / paths Defines import aliases for the type checker (bundler needs matching config)
extends / references Share base config and enable fast incremental multi-package builds
