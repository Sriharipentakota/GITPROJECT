BEGINNER1. What is TypeScript and Why Types?

Definition

TypeScript is a strongly typed superset of JavaScript that compiles down to plain JavaScript. It adds a static type system on top of JavaScript, letting you describe the shape of data before your code runs, so mistakes are caught by the compiler instead of by your users.

Real-world analogy: JavaScript is like a form with no field labels — you can put anything anywhere. TypeScript adds labels ("Name: text", "Age: number") so you immediately notice when someone tries to put a word where a number belongs.

Why do we need types?

  • Catch errors early: Typos and mismatched data are flagged at compile time, not at 2am in production
  • Self-documenting code: Function signatures tell you exactly what to pass in and what comes out
  • Better tooling: Autocomplete, refactoring, and "go to definition" all become dramatically more reliable
  • Safer refactors: Rename a property and the compiler shows you every place that breaks

Your First TypeScript File

// greet.ts
function greet(name: string): string {
    return `Hello, ${name}!`;
}

console.log(greet("Alice"));   // Output: Hello, Alice!
// console.log(greet(42));     // ❌ Compile error: Argument of type 'number'
//                                 is not assignable to parameter of type 'string'.
💡 Tip: TypeScript code (.ts) is compiled ("transpiled") to JavaScript (.js) using the tsc compiler. Browsers and Node.js never run .ts files directly.

How TypeScript Fits into the Toolchain

// Compile a single file
tsc greet.ts
// Produces greet.js, which you run with node greet.js

// Watch mode - recompiles on save
tsc greet.ts --watch

// Compile an entire project using tsconfig.json
tsc

BEGINNER2. Basic Primitive Types

TypeScript mirrors JavaScript's primitive types and lets you label variables, parameters, and return values with them.

string, number, boolean

let username: string = "morgan";
let age: number = 29;
let isAdmin: boolean = false;

username = "casey";   // ✅ OK - still a string
// age = "29";        // ❌ Error: Type 'string' is not assignable to type 'number'
Type Example Values Notes
string "hi", 'hi', `hi ${name}` Any textual data, including template literals
number 42, 3.14, 0xFF No separate int/float — all numbers share one type
boolean true, false Never 0/1 or truthy/falsy values
bigint 100n For integers beyond Number.MAX_SAFE_INTEGER
symbol Symbol("id") Unique, immutable identifiers

bigint and symbol

let big: bigint = 9007199254740993n;
let id: symbol = Symbol("userId");

// bigint and number cannot be mixed directly
// let total = big + 1;   // ❌ Error: mixing BigInt and number

BEGINNER3. Type Annotations on Variables, Parameters, and Returns

An annotation is the : Type syntax you attach after a name to declare what it's allowed to hold.

Variable Annotations

let score: number;   // declared, not yet assigned
score = 95;           // ✅ OK
// score = "95";      // ❌ Error

const title: string = "TypeScript Guide";

Function Parameter and Return Annotations

function add(a: number, b: number): number {
    return a + b;
}

add(2, 3);        // 5
// add(2, "3");   // ❌ Error: Argument of type 'string' is not
//                   assignable to parameter of type 'number'

Optional and Default Parameters

function buildUrl(path: string, host?: string): string {
    return `${host ?? "https://api.example.com"}${path}`;
}

buildUrl("/users");                        // uses default host
buildUrl("/users", "https://dev.local");   // explicit host

function greet(name: string = "Guest"): string {
    return `Hi, ${name}`;
}

greet();          // "Hi, Guest"
greet("Priya");   // "Hi, Priya"
⚠️ Common Pitfall: Optional parameters (host?) must come after required ones. TypeScript will reject a required parameter placed after an optional one.

INTERMEDIATE4. The any and unknown Types

any — Opting Out of Type Checking

any tells the compiler "trust me, don't check this." It disables type safety entirely for that value.

let payload: any = { id: 1 };
payload = "now a string";     // ✅ allowed, no error
payload.toUpperCase();        // ✅ compiles, but crashes at runtime if not a string
payload();                    // ✅ compiles, crashes at runtime - payload isn't callable
⚠️ Common Pitfall: Overusing any defeats the entire purpose of TypeScript. It's sometimes necessary (e.g. gradually migrating a JS codebase), but should be the exception, not the default.

unknown — The Type-Safe any

unknown can hold any value too, but you must narrow it before using it.

let input: unknown = getUserInput();

// input.toUpperCase();   // ❌ Error: Object is of type 'unknown'

if (typeof input === "string") {
    input.toUpperCase();  // ✅ OK - narrowed to string inside this block
}

function getUserInput(): unknown {
    return "some text";
}
any (Unsafe): 
let x: any = fetchData();
x.doAnything();   // no compiler help
unknown (Safe): 
let x: unknown = fetchData();
if (typeof x === "object" && x) {
    // safely narrowed
}
💡 Tip: Prefer unknown over any whenever a value's shape is genuinely not known ahead of time, such as data from JSON.parse or an external API.

INTERMEDIATE5. The void, null, undefined and never Types

void — No Meaningful Return Value

function logMessage(message: string): void {
    console.log(message);
    // no return statement, or "return;" with no value
}

null and undefined

let a: null = null;
let b: undefined = undefined;

// With strictNullChecks enabled (recommended), a variable typed
// 'string' cannot also be null or undefined unless you say so:
let name: string | null = null;
name = "Sam";     // ✅ OK
name = null;      // ✅ OK

never — Values That Never Occur

never represents a function that never returns normally — either it always throws or loops forever.

function fail(message: string): never {
    throw new Error(message);
}

function infiniteLoop(): never {
    while (true) {
        // runs forever
    }
}
Type Meaning Typical Use
void Function returns nothing useful Event handlers, logging functions
null Intentional absence of a value Explicit "empty" state
undefined Value has not been assigned Uninitialized variables, missing properties
never Code path is unreachable Throwing functions, exhaustive switch checks

INTERMEDIATE6. Object Type Annotations

You can describe the shape of an object inline, without needing a separate named type.

let user: { id: number; name: string; isActive: boolean } = {
    id: 1,
    name: "Dana",
    isActive: true
};

// user.email;          // ❌ Error: Property 'email' does not exist
// user = { id: 2 };    // ❌ Error: missing 'name' and 'isActive'

Optional Properties

let profile: { name: string; bio?: string } = { name: "Lee" };
profile.bio = "TypeScript enthusiast";   // ✅ OK, bio is optional

Readonly Properties

let point: { readonly x: number; readonly y: number } = { x: 0, y: 0 };
// point.x = 10;   // ❌ Error: Cannot assign to 'x' because it is a read-only property
When to use inline object types vs interfaces: Inline types are fine for quick, one-off shapes. For anything reused across your codebase, prefer an interface or type alias (covered in the Interfaces guide) so you don't repeat yourself.

INTERMEDIATE7. Literal Types

Literal types narrow a primitive down to one exact value (or a small set of values), which is extremely useful for flags, statuses, and configuration options.

let direction: "up" | "down" | "left" | "right";
direction = "up";      // ✅ OK
// direction = "north"; // ❌ Error: Type '"north"' is not assignable

let httpStatus: 200 | 404 | 500;
httpStatus = 200;      // ✅ OK
// httpStatus = 201;   // ❌ Error

const vs let with Literal Types

const method = "GET";        // type is literally "GET" (never changes)
let method2 = "GET";         // type widens to string (could change later)

function request(method: "GET" | "POST", url: string) {
    // ...
}

request(method, "/api");    // ✅ OK - "GET" matches the literal union
// request(method2, "/api"); // ❌ Error - method2 is widened to 'string'
💡 Tip: This is exactly why const is preferred for literal-typed values — let "widens" the inferred type because the compiler assumes it might be reassigned.

INTERMEDIATE8. Type Inference vs Explicit Annotation

TypeScript can often figure out a type on its own without you writing it. This is called inference.

let count = 10;          // inferred as number
let label = "score";     // inferred as string
let items = [1, 2, 3];   // inferred as number[]

// count = "ten";        // ❌ Error - still checked, even without explicit annotation

When to Annotate Explicitly

  • Function parameters — TypeScript cannot infer these from usage alone
  • When the inferred type would be too wide or too narrow for your intent
  • Public API boundaries (exported functions), for clarity and stability
  • Empty structures like let results = []; which infer as any[]
// Parameters always need annotations
function double(n: number): number {
    return n * 2;
}

// Return type is usually inferred fine, but explicit annotation
// documents intent and catches accidental mismatches
function parseAge(input: string): number {
    return Number(input);
}
⚠️ Common Pitfall: let results = []; without an annotation infers any[], silently disabling type checks on every element you push. Prefer let results: number[] = [];.

ADVANCED9. Strictness and Compiler Flags

How aggressively TypeScript enforces these rules is controlled by flags in tsconfig.json (see the dedicated tsconfig guide for the full picture).

{
  "compilerOptions": {
    "strict": true,              // enables all strict flags below
    "strictNullChecks": true,    // null/undefined must be explicit
    "noImplicitAny": true,       // error when a type can't be inferred
    "strictFunctionTypes": true  // stricter checking of function parameters
  }
}

noImplicitAny in Action

// With noImplicitAny: true
function process(data) {   // ❌ Error: Parameter 'data' implicitly has an 'any' type
    return data.value;
}

// Fixed
function process(data: { value: number }) {
    return data.value;
}
Why turn strict mode on: Projects that start with strict: true catch far more bugs at compile time. Turning it on for an existing loose codebase can be painful, but new projects should almost always start strict.

ADVANCED10. Best Practices for Basic Types

1. Prefer unknown Over any

// ✅ Good
function handle(data: unknown) { /* narrow before use */ }

// ❌ Avoid
function handle(data: any) { /* no safety net */ }

2. Let Inference Work for Local Variables

// ✅ Good - obvious from the right-hand side
const total = 0;
const name = "TypeScript";

// ❌ Redundant
const total: number = 0;
const name: string = "TypeScript";

3. Always Annotate Function Signatures

// ✅ Good - clear contract at a glance
export function calculateTax(amount: number, rate: number): number {
    return amount * rate;
}

4. Enable strict Mode From Day One

{ "compilerOptions": { "strict": true } }

5. Use Literal Unions Instead of Loose Strings

// ✅ Good
type Status = "pending" | "active" | "closed";

// ❌ Avoid
type Status = string;

Concept Key Points
string / number / boolean Core primitives, checked strictly at every assignment
any Disables checking entirely — use sparingly
unknown Safe alternative to any; must be narrowed before use
void / never No useful return value / function never returns
Object types Inline shapes with optional (?) and readonly modifiers
Literal types Narrow a primitive to exact allowed values
Inference Let TypeScript deduce obvious types; annotate function signatures
strict mode Turns on the full set of safety checks; enable from project start
