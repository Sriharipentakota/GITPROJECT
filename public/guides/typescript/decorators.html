INTERMEDIATE1. What are Decorators?

Definition

A decorator is a special kind of declaration attached to a class, method, accessor, property, or parameter using the @expression syntax, letting you observe, modify, or replace that declaration's behavior.

Real-world analogy: A decorator is like a gift wrapper — it takes the original item (a class or method), wraps additional behavior around it (logging, validation, timing), and hands back something that still works like the original but does more. 
function Logged(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    descriptor.value = function (...args: any[]) {
        console.log(`Calling ${propertyKey} with`, args);
        return original.apply(this, args);
    };
}

class Calculator {
    @Logged
    add(a: number, b: number): number {
        return a + b;
    }
}

new Calculator().add(2, 3);
// Logs: Calling add with [2, 3]
// Returns: 5
💡 Tip: Decorators are heavily used by frameworks like Angular (@Component, @Injectable) and by libraries like TypeORM and NestJS to reduce boilerplate for common patterns.

INTERMEDIATE2. Enabling Decorators

The classic ("legacy") decorator implementation requires an explicit compiler flag; TypeScript 5.0+ also supports the newer Stage 3 ECMAScript decorators without any flag.

// tsconfig.json - required for the legacy/experimental decorator implementation
{
  "compilerOptions": {
    "target": "ES2022",
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  }
}
⚠️ Common Pitfall: Without experimentalDecorators: true (for the legacy style), using @Decorator syntax either fails to compile or is interpreted using the newer Stage 3 semantics, which have different decorator signatures. Know which mode your project targets — see section 9.

INTERMEDIATE3. Class Decorators

A class decorator receives the class's constructor and can observe, modify, or replace it entirely.

function Sealed(constructor: Function) {
    Object.seal(constructor);
    Object.seal(constructor.prototype);
}

@Sealed
class Greeter {
    greeting: string;
    constructor(message: string) {
        this.greeting = message;
    }
}

// After @Sealed, no new properties can be added to Greeter or its prototype

Replacing the Constructor

function WithTimestamp(Base: T) {
    return class extends Base {
        createdAt = new Date();
    };
}

@WithTimestamp
class Order {
    constructor(public id: number) {}
}

const order = new Order(1) as Order & { createdAt: Date };
console.log(order.createdAt);   // a Date instance

INTERMEDIATE4. Method Decorators

A method decorator receives the target's prototype, the method name, and its property descriptor — the same shape used by Object.defineProperty.

function Measure(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    descriptor.value = function (...args: any[]) {
        const start = performance.now();
        const result = original.apply(this, args);
        console.log(`${propertyKey} took ${(performance.now() - start).toFixed(2)}ms`);
        return result;
    };
    return descriptor;
}

class ReportService {
    @Measure
    generateReport(rows: number): string {
        // simulate work
        return `Report with ${rows} rows`;
    }
}

new ReportService().generateReport(1000);

ADVANCED5. Accessor and Property Decorators

Accessor Decorator

function Configurable(value: boolean) {
    return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
        descriptor.configurable = value;
    };
}

class Point {
    private _x = 0;

    @Configurable(false)
    get x(): number {
        return this._x;
    }
}

Property Decorator

function Required(target: any, propertyKey: string) {
    let value: any;
    Object.defineProperty(target, propertyKey, {
        get() { return value; },
        set(newValue) {
            if (newValue === undefined || newValue === null) {
                throw new Error(`${propertyKey} is required`);
            }
            value = newValue;
        }
    });
}

class User {
    @Required
    name!: string;
}

const user = new User();
// user.name = null;   // throws: "name is required"
user.name = "Devi";     // ✅ OK

ADVANCED6. Parameter Decorators

Parameter decorators observe a specific parameter's position within a method — they cannot modify the parameter itself, but are commonly used to record metadata for dependency injection frameworks.

function LogParam(target: any, methodName: string, parameterIndex: number) {
    console.log(`Parameter ${parameterIndex} of ${methodName} is decorated`);
}

class NotificationService {
    send(@LogParam recipient: string, message: string): void {
        console.log(`Sending "${message}" to ${recipient}`);
    }
}

// Logs at class-definition time: "Parameter 0 of send is decorated"
Real-world use case: NestJS uses parameter decorators like @Body() and @Param() to record which constructor/method parameter should receive which piece of an incoming HTTP request.

ADVANCED7. Decorator Factories

A decorator factory is a function that returns a decorator, letting you customize its behavior with arguments at the point of use.

function MinLength(length: number) {
    return function (target: any, propertyKey: string) {
        let value: string;
        Object.defineProperty(target, propertyKey, {
            get() { return value; },
            set(newValue: string) {
                if (newValue.length < length) {
                    throw new Error(`${propertyKey} must be at least ${length} characters`);
                }
                value = newValue;
            }
        });
    };
}

class Account {
    @MinLength(8)
    password!: string;
}

const account = new Account();
// account.password = "short";       // throws
account.password = "supersecure";    // ✅ OK

ADVANCED8. Composing Multiple Decorators

Multiple decorators applied to the same declaration run in a well-defined order: evaluated top-to-bottom, but applied bottom-to-top (closest to the declaration first).

function First() {
    console.log("First: factory evaluated");
    return function (target: any, key: string, descriptor: PropertyDescriptor) {
        console.log("First: applied");
    };
}

function Second() {
    console.log("Second: factory evaluated");
    return function (target: any, key: string, descriptor: PropertyDescriptor) {
        console.log("Second: applied");
    };
}

class Example {
    @First()
    @Second()
    method() {}
}

// Output order:
// First: factory evaluated
// Second: factory evaluated
// Second: applied
// First: applied
💡 Tip: This "evaluate top-down, apply bottom-up" order matters when decorators wrap each other's behavior (e.g. logging + caching) — the innermost decorator (closest to the method) runs its wrapping logic first.

ADVANCED9. Legacy vs Stage 3 (ECMAScript) Decorators

TypeScript originally shipped an experimental decorator implementation years before decorators were standardized. TypeScript 5.0 added support for the finalized Stage 3 ECMAScript proposal, which has a different (simpler, more restricted) signature.

Aspect Legacy (experimentalDecorators) Stage 3 (standard, TS 5.0+)
Compiler flag needed ✅ Yes - experimentalDecorators: true ❌ No - works by default
Parameter decorators ✅ Supported ❌ Not part of the standard
Property descriptor access ✅ Full access Limited - uses a context object instead
Standardized in JavaScript ❌ No - TypeScript/Babel-specific ✅ Yes - real ECMAScript feature 
// Stage 3 style method decorator - receives a ClassMethodDecoratorContext
function LogCall(originalMethod: any, context: ClassMethodDecoratorContext) {
    const methodName = String(context.name);
    function replacement(this: any, ...args: any[]) {
        console.log(`Calling ${methodName}`);
        return originalMethod.call(this, ...args);
    }
    return replacement;
}

class Service {
    @LogCall
    run() {
        console.log("Running...");
    }
}
⚠️ Common Pitfall: Many popular libraries (older Angular, TypeORM, NestJS) still target the legacy decorator model. Check a library's documentation before assuming Stage 3 semantics apply — mixing the two mental models causes confusing bugs.

ADVANCED10. Best Practices

1. Know Which Decorator Model Your Project Uses

// ✅ Check tsconfig.json for experimentalDecorators before writing new decorators

2. Prefer Decorator Factories Over Bare Decorators for Configurability

// ✅ Good - accepts configuration
function Retry(times: number) { return function (/* ... */) {}; }

// ❌ Less flexible - hardcoded behavior
function RetryThreeTimes(/* ... */) {}

3. Keep Decorator Logic Focused and Side-Effect-Aware

A decorator should do one clear thing (logging, validation, timing) rather than several unrelated things bundled together.

4. Document the Order-Dependence of Composed Decorators

// ✅ Add a comment when order matters
class Handler {
    @Authorize()   // must run before @Log() wraps the result
    @Log()
    handle() {}
}

5. Avoid Decorators for Simple One-Off Logic

If a plain function wrapper or higher-order function achieves the same result without decorator syntax, prefer that for simpler debugging and broader compiler compatibility.

📋 Quick Reference Summary

Decorator Type Key Points
Class decorator Receives the constructor; can observe, modify, or replace it
Method decorator Receives target, key, and PropertyDescriptor; can wrap behavior
Accessor/Property decorator Customizes getters/setters or intercepts field assignment
Parameter decorator Records metadata about a specific parameter's position (legacy only)
Decorator factory Function returning a decorator, enabling configuration arguments
Composition order Factories evaluate top-down; decorators apply bottom-up
