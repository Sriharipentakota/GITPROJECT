INTERMEDIATE1. Why Error Types Are Tricky in TypeScript

Definition

JavaScript lets you throw literally anything — a string, a number, an object, or an Error instance. Because of this, TypeScript cannot know in advance what type a thrown or caught value actually is, which is why error handling needs deliberate type-safety patterns.

Real-world analogy: Catching an error in JavaScript is like reaching into a lost-and-found box — you might pull out a wallet, a glove, or a rock. TypeScript's job is to make you check what you actually grabbed before you try to "read the wallet's ID card." 
function risky(): void {
    throw "Something went wrong";   // ✅ legal JavaScript - a string, not an Error!
}

try {
    risky();
} catch (error) {
    // error's type here is the subject of the next section
    console.log(error);
}

INTERMEDIATE2. catch Variables and unknown

Since TypeScript 4.4, with strict mode enabled (specifically useUnknownInCatchVariables, on by default under strict), a catch variable is typed as unknown instead of the old, unsafe any.

try {
    JSON.parse("{ invalid json");
} catch (error) {
    // error: unknown
    // console.log(error.message);   // ❌ Error: 'error' is of type 'unknown'
    console.log(error);               // ✅ OK - just logging the raw value
}
💡 Tip: Before this setting existed (or with useUnknownInCatchVariables: false), error was typed any, letting you write error.message without any check — a silent trap since not everything thrown has a .message property.

INTERMEDIATE3. Narrowing Caught Errors Safely

try {
    JSON.parse("{ invalid json");
} catch (error) {
    if (error instanceof Error) {
        console.log(error.message);   // ✅ narrowed - safe to access .message
    } else {
        console.log("Unknown error:", String(error));
    }
}

A Reusable Helper

function getErrorMessage(error: unknown): string {
    if (error instanceof Error) {
        return error.message;
    }
    if (typeof error === "string") {
        return error;
    }
    return "An unknown error occurred";
}

try {
    throw new Error("Disk full");
} catch (error) {
    console.error(getErrorMessage(error));   // "Disk full"
}

INTERMEDIATE4. Custom Error Classes

Extending the built-in Error class lets you attach domain-specific data (a field name, an HTTP status code) while still behaving like a normal error for stack traces and logging.

class ValidationError extends Error {
    constructor(public field: string, message: string) {
        super(message);
        this.name = "ValidationError";
        // Required for correct instanceof checks when targeting older JS runtimes
        Object.setPrototypeOf(this, ValidationError.prototype);
    }
}

class NotFoundError extends Error {
    constructor(public resource: string, public id: number) {
        super(`${resource} with id ${id} was not found`);
        this.name = "NotFoundError";
        Object.setPrototypeOf(this, NotFoundError.prototype);
    }
}

function findUser(id: number) {
    if (id !== 1) {
        throw new NotFoundError("User", id);
    }
    return { id, name: "Devon" };
}

try {
    findUser(99);
} catch (error) {
    if (error instanceof NotFoundError) {
        console.log(`${error.resource} #${error.id} missing`);
    }
}
⚠️ Common Pitfall: When compiling to older JavaScript targets (ES5), extending built-ins like Error can break instanceof checks unless you explicitly call Object.setPrototypeOf(this, NewErrorClass.prototype) in the constructor.

ADVANCED5. Discriminated Unions for Error Handling

Rather than relying purely on instanceof chains, many TypeScript codebases model distinct failure cases as a discriminated union, giving the compiler full visibility into every possible outcome.

type ApiError =
    | { type: "network"; message: string }
    | { type: "validation"; field: string; message: string }
    | { type: "unauthorized" };

function handleApiError(error: ApiError): string {
    switch (error.type) {
        case "network":
            return `Network problem: ${error.message}`;
        case "validation":
            return `Invalid ${error.field}: ${error.message}`;
        case "unauthorized":
            return "Please log in again";
    }
}
💡 Tip: This pairs naturally with the Result pattern in the next section — the union describes every "shape" of failure your function can produce, and callers must account for each one.

ADVANCED6. The Result Pattern (Errors as Values)

Instead of throwing, some functions return a Result-shaped value describing success or failure explicitly — this forces every caller to handle the failure path, since the compiler won't let them reach .value without checking .ok first.

type Result =
    | { ok: true; value: T }
    | { ok: false; error: E };

function parseAge(input: string): Result {
    const age = Number(input);
    if (Number.isNaN(age) || age < 0) {
        return { ok: false, error: `"${input}" is not a valid age` };
    }
    return { ok: true, value: age };
}

const result = parseAge("thirty");
if (result.ok) {
    console.log(`Age is ${result.value}`);   // ✅ narrowed - value exists
} else {
    console.log(`Error: ${result.error}`);   // ✅ narrowed - error exists
}
When to prefer this over throw/catch: The Result pattern shines for expected, recoverable failures (invalid user input, a lookup that might miss) where you want the compiler to force every caller to handle both paths. Reserve throw for truly exceptional, unrecoverable situations.

ADVANCED7. Typing Error-First Callbacks and Rejections

function readConfig(
    path: string,
    callback: (error: Error | null, data?: string) => void
): void {
    // simulate an async file read
    const success = true;
    if (success) {
        callback(null, '{"env":"production"}');
    } else {
        callback(new Error("File not found"));
    }
}

readConfig("./config.json", (error, data) => {
    if (error) {
        console.error(error.message);
        return;
    }
    console.log(data);   // 'data' is 'string | undefined' here, still needs a check
});

Typing a Rejected Promise

function fetchWithTimeout(url: string, ms: number): Promise {
    return new Promise((resolve, reject) => {
        const timer = setTimeout(() => reject(new Error("Request timed out")), ms);
        fetch(url)
            .then((response) => {
                clearTimeout(timer);
                resolve(response);
            })
            .catch(reject);
    });
}

ADVANCED8. Exhaustive Error Handling with never

Just like with any discriminated union, adding a never-typed exhaustiveness check to your error-handling switch guarantees the compiler flags any new error variant you forget to handle.

type AppError =
    | { kind: "timeout" }
    | { kind: "notFound"; id: number }
    | { kind: "forbidden"; reason: string };

function describeError(error: AppError): string {
    switch (error.kind) {
        case "timeout":
            return "The request timed out";
        case "notFound":
            return `Resource ${error.id} was not found`;
        case "forbidden":
            return `Forbidden: ${error.reason}`;
        default: {
            const exhaustiveCheck: never = error;
            throw new Error(`Unhandled error kind: ${JSON.stringify(exhaustiveCheck)}`);
        }
    }
}
⚠️ Common Pitfall: Without the default exhaustiveness check, adding a new member to the AppError union later would silently fall through with no compile error, and the new case would go unhandled at runtime too.

ADVANCED9. Validating External Data Safely

Type assertions on external data (API responses, JSON.parse output, environment variables) are a compile-time-only promise. For real safety, pair them with runtime validation.

interface User {
    id: number;
    name: string;
}

function isUser(value: unknown): value is User {
    return (
        typeof value === "object" &&
        value !== null &&
        typeof (value as User).id === "number" &&
        typeof (value as User).name === "string"
    );
}

async function loadUser(id: number): Promise {
    const response = await fetch(`/api/users/${id}`);
    const data: unknown = await response.json();

    if (!isUser(data)) {
        throw new ValidationError2("user", "Response did not match the User shape");
    }
    return data;   // ✅ narrowed to User by the type guard
}

class ValidationError2 extends Error {
    constructor(public field: string, message: string) {
        super(message);
    }
}
💡 Tip: Libraries like Zod, Yup, or io-ts generate both a runtime validator and a matching static type from one schema definition, removing the need to hand-write type guards like the one above for every shape.

ADVANCED10. Best Practices

1. Never Assume catch Variables Are Error Instances

// ✅ Good
catch (error) {
    if (error instanceof Error) { console.error(error.message); }
}

2. Create Specific Error Subclasses for Domain Failures

// ✅ Good
class InsufficientFundsError extends Error {
    constructor(public available: number, public requested: number) {
        super(`Requested ${requested} but only ${available} available`);
    }
}

3. Use the Result Pattern for Expected, Recoverable Failures

// ✅ Good - forces callers to check before use
function tryDivide(a: number, b: number): Result {
    return b === 0 ? { ok: false, error: "Division by zero" } : { ok: true, value: a / b };
}
type Result = { ok: true; value: T } | { ok: false; error: E };

4. Add Exhaustiveness Checks to Every Error switch

// ✅ Good
default: {
    const _exhaustive: never = error;
    throw new Error(`Unhandled: ${_exhaustive}`);
}

5. Validate, Don't Just Assert, Data From Outside Your Program

// ✅ Good - real runtime safety net
const user = UserSchema.parse(await response.json());
declare const UserSchema: { parse(data: unknown): { id: number } };
